Local storage and authorship

Record

A record holds one schema’s fields, primary key, named alternate addresses, one revision, and database-set authorship. Replacement supplies the complete desired state. Omitted fields disappear.

The complete encoded record has a 64 KiB limit, including keys, alternates, one write stamp, authorship, metadata, and file markers. Its single attachment can be a blob or inline file; those bytes stay separate. A live record can have no payload fields.

Source: Record

Record authorship

Local writes set created_by at creation and updated_by on each change. Shared materialization keeps the earliest accepted creator and the winning writer separately.

Personal replacements retain created_by. An attachment-only replay keeps the winning fields’ writer and time. Shared creation means the earliest accepted write to that key, not arrival order. Per-change signed entries omit arbitrary remote metadata; native personal snapshots preserve stored metadata.

Source: Record authorship

Warm set

A read by key checks the warm set first. A disk fetch can keep the complete decoded record for a later call.

The default warm limit is 256 MiB. It covers decoded records, their keys, metadata, and file markers. Schema definitions and file bytes stay outside this charge. The least recently used unheld records leave first. Older read views and private writes use disk. A range page can admit its selected records without fetching them a second time.

Source: Warm set

Flush and acknowledgement

A native write saves its complete change before publishing memory and returning success. Normal record commits use one encrypted log frame and one ordered flush.

Normal logged commits append one frame and perform one ordered file flush. Large commits can seal pending work and write directly to a run. macOS uses F_BARRIERFSYNC, with F_FULLFSYNC as a fallback; Linux uses fdatasync. An explicit native flush receipt and each spool upload page also force the drive cache to storage. Local success does not confirm a cloud copy.

The write queue can group prepared requests into one native commit. Commit-log flush counts measure those native commits, not individual API requests.

Captured entries commit atomically with their records; encrypted files are written first. A retained ID, signing failure, or full spool can refuse a write. Personal /v1/write wakes the upload worker after the commit.

Owned shareable /v1/write still mirrors into signed history after the local commit. That later step can fail. Read the record before deciding whether to retry.

Ordinary snapshot capture seals pending commits, waits for the file-deletion ledger to clear, and forces a full-drive flush before pinning. The first-snapshot path flushes before its snapshot call seals any remaining log frames; newly sealed files and staged local-reference copies do not share that earlier full-drive flush.

Source: Flush and acknowledgement

Run block encryption

Separate derived keys protect each record and record-file home. Owned named databases derive their content keys from the node signing seed and database UUID. Received Share publications use their supplied content key.

Block compression skips inputs below 256 bytes. It is kept only if it saves at least 64 bytes and 10%, including its length header. Encryption still applies when compression is skipped. File sizes, clear footers, and some layout facts remain visible. Personal relay entries use a separate sealed payload. Shared entries still serialize clear fields. Neither transport rule changes local run encryption. The run reader loads and authenticates a complete block before exposing decoded bytes. Decompressed output is capped at 64 MiB; the former two-pass bounded reader is removed. Personal snapshots transfer native encrypted files unchanged. Their clear manifest exposes file paths, lengths, and digests, not record content.

The record commit log encrypts each frame with the record home key, a fresh identifier, and its commit counter. Replay authenticates frames before restoring logged values. Log file sizes and framing remain visible.

Source: Run block encryption

Prepared writes

LastDB prepares a complete change privately and checks that it fits. The write succeeds only after disk completion and memory publication.

Prepared data stays private. Each primary key appears at most once per API batch. A failed condition or oversized record refuses the request. Saved records enter memory after flush; large prepared sets can wait for a later fetch.

Preparation uses the format writer for records and their related changes. Before accepting the request, LastDB checks the final encoded record at each changed key.

Source: Prepared writes

Memory limits

The warm set and prepared writes have separate byte limits.

The warm set defaults to 256 MiB; held records can keep it above that target. Pending native writes have a 512 MiB allowance, including staged signed entries and encrypted attachment copies. Those bytes also count in the disk-space reservation. Read and backup work have their own bounds. These are not a total process-memory cap. The former process governor and allocator tuning are removed. Each run home can also retain 32 reader handles and their small lookup headers. Personal sync requests up to 90 stored relay items per page. One segment item expands to many entries, and its full blob is buffered during decoding; 90 is not a decoded-entry or memory cap. Its file sealing and opening still buffer whole files. Shared histories remain in memory. Snapshot hashing and HTTP transfer stream native files. Copying a local file reference into the snapshot still buffers that complete file.

The warm set estimates complete decoded records, including their keys, authorship, metadata, and file markers. Prepared native writes use a separate byte allowance.

The record home also retains unsealed commit-log records in its memory layer. It is separate from the warm set and pending-write allowance. The 256 MiB seal threshold counts encoded log-frame bytes before the next append, not total resident memory.

Source: Memory limits

Write queue

Prepared requests wait privately in order. Requests already ahead of the disk worker can share one complete commit. Later arrivals wait for the next commit.

Each request passes its own checks and waits for disk. Captured work is checked for retained IDs, spool capacity, and memory before it enters the queue. A group stops growing at 1,024 requests or 1,024 captured entries. A group that reaches a limit flushes before another request can join. An API mutation batch remains one complete request; grouped requests keep separate acceptance conditions.

Source: Write queue

Current disk state

CURRENT selects the sealed run files in each home. The record home can also have ordered commit-log frames above CURRENT’s frontier; reads replay or use those logged commits.

Reads hold both run-home roots. CURRENT saves base-compaction progress and the sealed frontier; a logged record home also replays consecutive frames above that frontier after restart. Snapshot capture seals the log before pinning files. An interrupted split commit can leave unused file bytes.

Source: Current disk state

Snapshot commit

A normal record-home commit appends and flushes a log frame before publishing logged memory. A later seal writes those records to a run and publishes CURRENT.

Record and file homes keep separate commits. File additions precede the record commit; file deletions follow it. The commit log covers record-home commits only. Spool entries are part of the record commit, so there is no separate staged-entry recovery step. Failed publication blocks further writes until reopen and retains files whose saved state is uncertain.

Source: Snapshot commit

Run home

A home is a folder of disk files. LastDB uses one run home for records and one for record files. The record home appends commits to a log before later seals create runs.

Only format 15 homes are accepted. New homes use it automatically. Older homes need their matching program; in-place conversion is unavailable. Opening checks that the lock file still names the locked inode. A busy home is reported separately from corrupt data. Startup removes regular hidden .tmp files after validating saved state. Logged commits replay above CURRENT on open.

Source: Run home

Record commit log

The record home normally appends each complete commit as one encrypted frame and flushes it in order. LastDB returns success after publishing the matching memory state.

A frame holds a complete home commit. The log uses numbered files; new files start when the active file reaches its 16 MiB target. A commit larger than half the maximum decompressed frame bypasses the log after a seal. Replay requires consecutive frontiers. A torn final frame is ignored; an unreadable interior frame or missing frontier refuses open. A clean stop seals commits and removes the log.

Each log file is created with private permissions and its directory entry is synced. Appends use the platform’s ordered file flush.

An orderly stop seals every logged commit and removes the commit-log directory. A crash leaves frames for replay.

The current non-logged RunHome opener replays and seals a leftover log before it continues with run commits.

Source: Record commit log

Logged memory layer

The record home keeps flushed commits in sorted memory segments until a seal writes them into a run. Point and range reads check this layer before older runs.

This is separate from the warm set and prepared-write allowance. Its byte count is encoded commit-log frame bytes, not resident memory. A seal freezes active segments while later commits continue. A commit first seals when those frame bytes already exceed 256 MiB; that threshold is checked before append, not a hard memory cap. Small layers also seal when weighted log bytes reach a limit between 64 KiB and 8 MiB; the weight adds estimated hidden run bytes for active tombstones.

The memory layer tracks commit count and encoded frame bytes. CURRENT advances only when a seal publishes a run; read roots report the combined sealed and logged frontier.

Replay rebuilds segments from complete frames above CURRENT. Replay does not estimate the old run bytes hidden by tombstones.

Source: Logged memory layer

Commit-log seal

A seal freezes logged memory, writes its newest value for each key to a run, publishes CURRENT, then prunes covered log files.

Background work starts at the calculated log-weight threshold or when a frozen seal needs completion. Large commits and commits made when the encoded log-frame bytes is already over 256 MiB seal before writing directly to a run. Snapshot capture seals, then tries at most 64 merge steps before it continues; the current code does not error if merge work remains after that bound. A clean stop seals and removes the log.

Sealing uses a spare log file so commits can continue while a frozen layer is written. Publication failure poisons the home; restart replays the durable log against CURRENT.

Ordinary snapshot capture seals once before it waits for the write gate and again under the gate. It then runs up to 64 merge steps, forces a full-drive flush, and pins the resulting roots.

The first-snapshot path calls the explicit native flush, then the snapshot call seals remaining frames into runs. It does not run ordinary capture’s merge-settlement loop or repeat its full-drive flush after sealing.

Source: Commit-log seal

Sorted run files

A run file stores keys in order, with a value or physical delete marker. Normal record commits first enter the commit log; a seal writes their newest values into a run. Published run files stay unchanged.

Data and lookup blocks target 16 KiB before encryption; large records can exceed that target. Encoded keys must fit 64 KiB. Values must fit within 32 MiB.

Source: Sorted run files

Run file lookup

A point read checks the logged memory layer, then newer runs before the compact base. Range reads combine logged values and relevant ordered run results.

Each run home caches at most 32 readers, removing the least recently used first. Each holds a file handle, cipher, footer, and decoded top block. It keeps no data blocks or records. Retired runs leave this cache; active reads may still hold them. Per-call lookup-block reuse ends with the read. Filter matches alone prove nothing, and returned values still count against the read limit.

Source: Run file lookup

Run file compaction

One background worker seals logged commits and combines files in both run homes. Commits and startup can start this work when the home needs it.

Each replacement file reserves disk space before its bytes are written. Insufficient space preserves the previous saved state. Active reads can delay file removal. Base work can reuse unaffected file ranges and combine adjacent small files. Explicit disk cleanup can run below the ordinary merge thresholds.

Source: Run file compaction

Log segments

Personal sync puts consecutive signed entries from one device stream into a blob. The relay stores one small item that names the blob at the segment’s last sequence number.

The sender makes one segment per batch. The blob holds each signed entry as JSON followed by a newline. The relay checks publisher access, sequence order, and that the blob is committed at the stated length; the node checks the blob digest, framing, stream, sequence range, final hash, then each entry’s signature and chain. Shared databases and older senders use inline entries. There is no separate segment size cap; the blob limit applies. The node holds a full segment in memory when it reads it.

Relay protocol: docs/designs/relay-protocol.md, Log segments. ExeMem stores the item as kind segment at entry#{node}#{device}#{last_seq:020}; the item itself is not charged. The committed blob is charged once.

The reference relay stores the descriptor at {last_seq}.json. A segment counts as one item toward the read limit. A read from within its sequence range starts with that segment, and the cursor advances to last_seq + 1.

The relay does not parse or verify signatures or the chain of entries inside the blob. The caller performs the ordinary entry signature and chain checks after the segment content checks.

Source: Log segments

Relay usage on this device

The node saves per-database counters for this device’s confirmed entries and blob uploads. It also records entry bytes released by trimming and file bytes released by sweeps. Status reads this local ledger.

This is not billing, an account inventory, or an exact current-storage total. Completeness means this device had no earlier uploads when tracking began, even if its first snapshot sequence was above 1. Older uploads are not backfilled. Other devices are absent, and cleanup may release their entries or files. A sweep records requested digests before deletion and checks the next relay listing to settle a lost reply. A crash between a snapshot or trim receipt and saving the ledger can leave an accounting gap. Counters do not prove recovery or delivery. The ledger lives outside the native store and is not part of its snapshot.

Sweep totals and unresolved drop requests survive across turns in the local accounting file. A retried or interrupted drop is settled against the next relay listing. A fresh reply counts only files that call says it removed.

The ledger detects earlier personal uploads from the native spool’s acknowledged position. Its counts use saturating arithmetic.

Entries sent in a segment count once by stream sequence and add no entry bytes. The segment blob contributes its bytes once to blob usage, so the same bytes are not counted as both entries and a blob.

Personal sync and shared logs

Personal database identity

The owner’s identity seed deterministically derives the personal database ID, birth material, and read key. Every owner device uses the same signing key and database, with its own device ID.

This identity rule applies to the main personal database. Named sibling databases remain separate. An older registry with a different personal ID fails to open; the code supplies no automatic conversion. Possession of the phrase grants the owner identity and read key. The one-off old-home adoption script and admin identity command were removed. Adding a first snapshot to a compatible home does not convert an incompatible identity or disk format.

Source: Personal database identity

Personal write spool

The personal store commits each signed entry in the same store transaction as its record or schema change. Encrypted attachment bytes stay in separate spool files until the relay confirms them.

The plaintext body is capped at 1 MiB. A captured request and grouped commit each hold at most 1,024 entries. Signed entries and encrypted files share a 1 GiB cap. A retained mutation ID is refused even when its body matches. Missing entries, wrong sequence numbers, or missing files block progress. The old accepted-v1 folder is refused; it is not converted automatically.

Spool entries, recent mutation IDs, and upload progress are records in disk-run. Confirmation commits the upload position, acknowledgement, and entry removals together. File removal follows that commit; startup removes leftover files outside the pending range.

A configured relay, an existing spool, or a signed restore enables capture. Once enabled, capture remains enabled across restarts. Fresh offline homes capture nothing. Named sibling and received stores do not create unused spools. Existing personal data needs a first snapshot before later entries upload.

ID cleanup retains at least the newest 10,000 acknowledged entries by sequence and every unacknowledged ID. Trimming is bounded and runs on acknowledgement, including the first after reopening. An older forgotten ID can become a new write.

Snapshots include the spool records in their native run files, but exclude accepted-files. Restore clears inherited spool records before the new device starts its own stream.

To open a home with accepted-v1, the older build must first send all writes. After it stops, confirm head equals acked and no pending.json remains, then move that old spool folder out of the home. Changing a format marker is not a conversion.

Source: Personal write spool

Personal device sync

The worker reads other owner devices and compares their entries with saved winning stamps. It then uploads the spool’s encrypted files before sending already signed entries in log segments. Native replay saves winners and progress together.

The sender reads up to 90 spool entries at a time and makes one segment per batch. A batch targets 2 MiB across signed entries and encrypted files; its first entry can exceed that target. The whole segment is held in memory while it is written and sent. Incoming relay pages request up to 90 stored items, not expanded entries. A segment is one item and loads in full into memory; its entries then pass through normal signature and chain checks. The worker resumes at the next sequence until it reaches the reported stream head; a short page is not the end. Only the main personal database uses this path. A daemon opened without capture refuses personal sync and reports that it needs a restart with a relay configured. A first snapshot can cover earlier uncaptured data. The relay needs stream-list, snapshot, and blob routes. Per-change bodies omit arbitrary record metadata; a native snapshot preserves metadata already in its files.

Each batch uploads its files, appends one segment for its consecutive entries, commits the acknowledged stream head, then confirms the spool separately. The head update and spool confirmation are separate operations, not one transaction.

The relay item is one stored item regardless of how many entries its blob holds. The node checks the blob digest, length, framing, stream identity, sequence run, and final entry hash before normal entry signature and chain checks.

Source: Personal device sync

Local write signing

The host gives the personal store an author with its signing key and device ID. During the local transaction, it encrypts the body and file, signs the next stream entry, and saves its hash, order, sequence, and winning stamps.

The next write can follow a finished entry while offline. A remote entry can be compared immediately, and upload cannot change the saved write.

A remote edit arrives while a local edit waits to upload. LastDB compares their saved stamps now. The fields and the single attachment have separate winners.

Captured writes reserve distinct milliseconds from a durable author clock, above the local stream’s previous order. Remote times within its safe bound can advance the clock; extreme remote values cannot exhaust it. This is not trusted global time. Signing, sequence exhaustion, or a local order at or beyond 1 January 2100 refuses the transaction. Relay acknowledgment has a separate stream head. Shared databases use their history path.

Personal sync progress

Personal sync saves each device’s applied position with its record or schema change. It also tracks which local entries the relay has acknowledged.

Schema removal finishes its paged, idempotent deletion before advancing the head. Invalid streams can freeze and remain skipped. There is no separate outgoing.json or outgoing-blobs retry store. Uploading does not change the record or its winning stamp. Shared databases still use separate history files. A read at a removed history position reports that the device is behind. Download errors appear in cloud status; a clean receive clears that error.

One native metadata row holds each device stream’s applied sequence, hash, order, and frozen flag. A remote record or schema put commits with its next head. This device’s head records relay acknowledgments.

The spool’s upload position and acknowledgement share one state record. They cannot advance independently.

Source: Personal sync progress

Sealed personal payloads

During a captured personal commit, the local author encrypts each body and external file with AES-256-GCM and a fresh nonce, then signs the entry. The database ID, owner key, device ID, and sequence are authenticated with the ciphertext.

Entry headers, stream identity, order, lengths, and sealed blob digests remain visible. Encryption buffers the complete file during commit; upload reads the saved encrypted file from disk. The receiver also buffers it to decrypt it. Shared record payloads use clear signatures and do not use this sealer.

Source: Sealed personal payloads

Whole-record last-writer-wins

Laptop A sets a file, laptop B sets another file later, then A changes only the title. Personal sync keeps A’s title and B’s file, whichever laptop uploads first.

Signed entries compare their order value, node key, and device ID. Personal replay also compares the sequence. Fields and alternate addresses share one winner. The single attachment takes the newest explicit blob, inline file, clear, or deletion.

Order comes from clocks, not trusted global time; signed values at or beyond 1 January 2100 are rejected. An edit with no attachment operation leaves its winner unchanged. Blob and inline writes replace each other. An attachment-only replay preserves the winning fields’ writer and time. For a required-blob record, replay saves winning fields while the blob is absent; a winning blob can restore them. A record deletion clears that saved state. Local absence and revision checks still apply. Losing values have no separate conflict archive.

Source: Whole-record last-writer-wins

Owned write mirroring

After an owned shareable write commits, the node prepares birth, schema, and record entries as needed and saves the signed batch to its authored log in one operation. The per-database shared write lock spans the local commit and this mirror. Pull-time materialization uses the same lock.

The selector can be the owned database name or ID and must resolve to saved birth material. Personal writes use the spool instead. The direct record change call uses the same write and mirror path as /v1/write. This does not connect every mutation route. Hash and hash-range records include canonical alternate addresses. Files and ranged hashes containing U+001F are refused before commit. Arbitrary record metadata is omitted; fields are signed in clear. A signing failure attempts history repair before returning 503. A failed signed batch leaves no newly signed prefix. Repair can fail, and the native record batch and signed log are still separate saves.

Source: Owned write mirroring

Shared logs and upload cursor

Each shared database keeps signed local and received history, plus its confirmed upload position. Restart rebuilds accepted history from these saved logs.

Files live under log-sync/<database-id>/. Each log has a 16 MiB limit. Authored entries rewrite their log on append; received entries rewrite theirs when the accepted entry hashes change. A failed received save leaves entries in memory and retries on a later pull. Missing files mean empty logs or cursor zero; invalid or unreadable files error. A cursor beyond its log is refused. Only a full relay stored-or-duplicate count advances it. Pending entries and receive page cursors are not saved. This is separate from the native record transaction.

Locally signed entries live in authored.json, accepted remote entries in received.json, and confirmed authored counts in uploaded.json. Restart loads births first, then combines both logs by deterministic signed position. Personal sync uses its native spool and stream heads instead.

Shared authored uploads take at most 32 entries at a time and split further at a 3 MiB serialization budget. A single entry above that budget stops the upload with an error; the confirmed cursor does not skip it.

Source: Shared logs and upload cursor

Signed history

A database history contains signed entries from node and device streams. Each stream starts at sequence 1 and links each later entry to its predecessor. Cross-stream references name entries the writer has seen.

Personal databases use the native write spool and saved stream heads. Their snapshots use a separate seed-derived stream shared by the owner’s devices. Shared databases save authored and received logs and rebuild history with births first and then deterministic signed positions; dependencies and repair markers remain in memory. Personal snapshots now permit removal of covered log entries. Shared snapshots and automatic lagging-device reset remain unavailable.

Worker, connection, and status

Background relay worker

The background worker exchanges personal and shared changes, handles leases and proposals, and runs due cloud cleanup. Snapshot uploads run separately.

LASTDB_RELAY_URL overrides the ExeMem address in saved credentials. Without either, the worker idles. A wake marker shortens a clean pause; completed work wakes another turn without repeatedly waking an idle worker. Personal send and receive are both attempted, except while a required first snapshot blocks that personal turn. Per-database errors remain visible while other work continues. Shared members known to lack deposit permission wait locally; an unexpected relay 403 waits up to 30 seconds or until grants or leases change.

Each turn uploads shared logs, pulls owned shares, renews configured leases, and decides member proposals. Personal sync receives before sending, then runs any due cloud sweep. A second shared upload sends publisher decisions before received-share work. Ordinary snapshot uploads run in a separate background task.

Source: Background relay worker

Relay client

The relay client signs each cloud request with the node’s identity and retries temporary refusals within a fixed limit.

Control requests allow 10 seconds to connect and 30 seconds per attempt. Responses cap at 8 MiB, and redirects are refused. Retries cover gateway 502–504, 500 unavailable, and selected 429 rate_limited provider or read failures. Configuration, quota, payment eligibility, and other refusals are not retried here. A non-timeout connection, request, or body error that returns within five seconds can also retry. Timeouts return without that retry. Connections are not kept in an idle pool. Total retry waiting is at most 1.75 seconds, in addition to request time. The worker uses one relay URL; LASTDB_RELAY_URL overrides saved credentials. A stored append does not prove complete recovery or delivery to every device.

Signed operations include log append, read, stream listing, trim, and blob requests. The signature binds the method, path, protocol version, database, body hash, time, and nonce. A temporary refusal can trigger up to three retries, each with a fresh signature.

Source: Relay client

Saved cloud credentials

One protected file holds the service address, account access key, and optional checked connection. Account commands, schema-service selection, and the relay worker use its reader.

The reader requires an ordinary private file owned by the current user. It rejects links, oversized files, and empty keys. The saved service address is now the default relay URL; LASTDB_RELAY_URL can override it. Personal entries come from the native spool; shared signed logs remain separate. Their presence is not proof of relay access or backup coverage.

The previous signed database-create exchange, 30-second enrollment wait, and per-database live confirmation cache are removed. wait_for_enrollment now returns immediately. Enrolled does not establish remote database readiness.

Node status

Status shows the running build, active work, cloud errors, and saved upload progress. Snapshot and sweep figures describe this node’s last saved observations.

The old detailed backup policy and progress routes remain removed. Received listings have a separate process-local publish report. A clean upload does not clear payment_hold or prove receive completeness. Unreadable state can report fallback counts alongside an error. No error or zero pending entries is not proof of complete backup. Snapshot status is this node’s knowledge, not a live claim about the relay’s newest snapshot. Personal receive failures, including a required history position that was removed, now appear as download errors. Per-database relay usage reports this device’s confirmed uploads and released log bytes, separately from billing and other devices.

Status includes socket workers, the last personal snapshot published or installed, and the inventory measured after the last cloud file sweep. Those snapshot and inventory records survive restart; they are not fresh relay queries.

The native spool report includes head, acknowledged sequence, retained bytes, recent ID count, first-snapshot requirement, gap state, and last confirmed upload sequence. It replaces reading the retired spool state files.

The record home reports commit-log flush count, mean and slowest append-and-flush time since opening, plus commits and encoded log bytes not yet sealed into runs. These counters reset on open. The byte count is not a measurement of total resident memory.

Finding signed streams

Shared writer discovery

For a shared database, the worker pulls known publisher devices and also discovers additional publisher streams. Current and historical Submit or Write grants identify member writer keys. It materializes records after pulling the publisher and member dependencies.

Writer-wide fallback is used only when stream discovery is unsupported (404, 405, or 501). Accepted received entries are saved; pending dependencies and page cursors are not. Alternate addresses are reconstructed, but shared files, arbitrary metadata, and bundle loading remain incomplete.

An empty relay page does not end the pull if it has a next cursor. A repeated cursor on an empty page, or more than 256 consecutive empty pages, stops the pull with an error.

Source: Shared writer discovery

Reference relay

The reference relay stores signed device streams and blobs. It gates access using the database’s signed birth and publisher grants.

The relay checks request signatures and grants; it does not run complete AcceptEntry validation. Appends and reads cap a batch at 90. A read without device_id pages one writer’s devices. Public any-read still requires a signed caller. Revoked members can read a single publisher stream to learn their revocation; writer-wide reads remain refused. Stream discovery uses the writer-wide grant check, and its head map is rebuilt from entries and saved removal positions at startup. An identical repeated append also repairs a head missing after a cancelled request. Signed JSON requests use the hosted platform’s 6 MiB payload ceiling. Read pages can stop below 90 entries to fit that ceiling and return a cursor for the next entry. Blob uploads stream separately and require the returned checksum header, matching bytes, and matching length. There is no blob-size cap unless --max-blob-bytes sets one. ExeMem DEV recovery has separate CI evidence; reference-relay source alone does not establish a deployment. Blob ownership is scoped to the database even when bytes share a digest. Transfer signatures bind the method, database, resource, and a 15-minute expiry. Repeated commits are idempotent. Append prevalidation detects conflicting duplicates before saving the batch, but it is not a crash-atomic file transaction.

Log entries are addressed by database, writer, device, and sequence; blobs by digest. The log.streams route lists a writer’s devices and each contiguous sequence head without rereading every entry.

ExeMem uses Lambda’s 6 MiB request and response ceilings, including the platform envelope, and DynamoDB’s 400 KiB stored-item limit. The reference relay uses the same payload ceiling. File bytes use separate transfer URLs.

Read limits must be between 1 and 90, and starting sequences must be positive. A cursor replaces the starting sequence; conflicting cursor, writer, or device parameters are refused. The reference relay also rejects unknown request fields.

Source: Reference relay

One record change call

The app sends one record change. The node applies it to a personal or owned database, or to a received database when a usable Write lease covers the member. Otherwise it queues a proposal if the member may submit. The reply says applied or pending.

Apps can ask for a change without deciding whether a lease allows it now. A pending reply keeps a suggestion separate from an accepted record.

Use client.select("trip").changeRecord with a schema, key, operation, complete record and condition. A covered writer gets applied. A Submit member gets pending and a submission sequence; the local record changes after publisher acceptance arrives.

This call takes one create, replace, or delete, without a file. Create requires an absent key; direct replace and delete require the read revision. It requires a non-nil lowercase UUID and, on the app socket, a schema write grant on either path. A read-only member gets 403. A failed direct condition gets 409. The proposal submission lock spans the saved-ID check and direct-or-pending choice. Repeating a saved proposal ID and identical body returns the same sequence, even if a lease has since arrived; another body gets 409. The direct path has no ID receipt: repeating an applied create or replace normally fails its condition. After an uncertain reply, inspect the record and proposal status before retrying; reusing the ID alone does not guarantee the same result. A lease that expires during the decision can send the change to the proposal path. Applied confirms this node’s change, not relay delivery or permanent acceptance by every reader.

Member writes and publisher checks

Database write leases

The publisher signs a timed lease for the database. It covers members with Write permission at that signed position. A member keeps the lease on disk and decides locally whether it can sign a direct change, even offline or after restart.

Shared work can continue while the publisher is unavailable. A signed closing point gives every reader the same rule for late arrivals.

Set lastdb share lease <database> --length 24h. The publisher renews around halfway through and when membership changes. A member stops direct writes before expiry, leaving a safety margin of 10% of the length, capped at five minutes.

Leases are opt-in, from 10 seconds to 90 days. Clearing the length stops renewal and does not end issued leases early. The publisher allows another half-length after expiry before a later lease can close it. The closing entry records the member stream positions it saw; later direct entries under the old lease are excluded. Readers decide from signed history, not their clocks. Winners are recomputed. This device resubmits an excluded change as a proposal if it still has Submit or Write access; acceptance is not guaranteed. No usable lease means /v1/write refuses. The record change call instead queues a proposal if this member may submit.

Member changes

A Write member with a usable lease can make a signed direct change. Otherwise, a permitted change becomes a proposal for the publisher’s LastDB to decide.

A direct write needs current Write permission, coverage by the newest held lease, time remaining before the local safety margin, and app schema access. Without these, /v1/write returns 403. Replies report the resulting live revisions. If signing fails, history repair must succeed before falling back to a proposal; failed repair returns an unconfirmed error. The record change call chooses the path. A leased direct write changes the local received store and is signed for other readers.

Proposal approval

The publisher’s LastDB checks each proposal against the current role, schema, and expected record state, then signs its decision.

Create requires no live record. Replace and delete require the expected winning history entry. Hash and hash-range keys carry validated alternate addresses. Files remain unsupported. The shared write lock keeps incorporation separate from an owned write and its signed mirror. An accepted change is saved locally, then signed as data citing the proposal. A refusal is a signed heads entry citing the proposal and carrying current publisher stream tips. Storage or signing failures leave the proposal undecided for retry. If signing fails after a local write, the node attempts to restore the history winner. That repair can also fail and log a warning. These saves are not atomic. The old configurable per-schema settings remain removed.

Before checking a proposal, the publisher restores that record to its accepted history state. It then checks the expected winning entry. Submit members must own records they replace or delete; Write members may change any record.

Signed personal checkpoints

Snapshot capture

LastDB captures a consistent view of records, attachments, and sync progress. Upload uses that view while later writes continue.

Normal capture waits for all local entries to be acknowledged and the file-deletion ledger to clear. It seals record-home commits, then tries up to 64 merge steps before pinning; the current bound can leave merge work pending. The first cut survives restart and is released after publication is recorded; preparing it can fail startup. Initial and ordinary manifests allow 4,096 files. The initial cut caps each file at 5,000,000,000 bytes (5 GB); relay limits also apply. A local record file is limited to 33,554,403 bytes so its sealed snapshot copy fits one native value.

Ordinary capture first seals logged record-home commits without blocking writers, then repeats sealing under the write gate. It tries up to 64 merge steps, forces a full-drive flush, and pins record and file roots with applied stream heads.

Beginning the first-snapshot cut flushes the native store, then the snapshot call seals remaining frames before preserving files. It does not run ordinary capture’s merge-settlement loop or repeat its full-drive flush after that seal. Later opening reuses the saved cut.

Local file references are verified and sealed into a private snapshot file store. Newly staged files use ordered writes and file synchronization; they do not share ordinary capture’s explicit full-drive flush.

Recovery and remaining delivery limits

Personal database restore

Restore rebuilds personal data in a fresh home using the recovery phrase. It installs the newest advertised snapshot, then replays later device changes.

The relay retains one checkpoint; restore has no previous-checkpoint fallback. Failure to install the newest returns an error. A snapshot preserves native personal records, metadata, alternate addresses, deletion state, and included files. Later entries omit arbitrary metadata. Named shares, installed apps, credentials, and never-uploaded data are outside this restore. Invalid replay streams can freeze and be skipped without failing the whole command. Only the relay’s specific nonpayment forbidden response is treated as an unknown database during discovery; payment and other access failures remain errors. The recovery relay URL is not saved. A device behind removed history needs a fresh home; it does not reset itself.

The phrase derives the personal database identity and keys. Replay begins after the positions covered by the snapshot, or from the beginning when no snapshot exists. Restore works in private staging and publishes an unused destination after closing the stores.

Native snapshots include spool records from the source device. Restore clears those inherited records before the new device captures its own writes; external spool files and device-specific sync state are not copied.

Source: Personal database restore

Personal replay checks

Personal replay checks the owner signature, device, predecessor, sequence, and order. It opens the sealed payload, validates its shape, and verifies attachment bytes. A record change and its next stream head commit together.

Frozen streams are stored and skipped, including during restore. Freezing returns success for that stream, so command success does not certify that every advertised entry was recovered. Malformed payloads, absent required file references, and oversized file markers freeze the stream. A fetched attachment that cannot decrypt, does not match its marker, or has a noncanonical marker also freezes its stream. Local file-read and storage failures stop the turn for retry. Transfer failures likewise remain errors; leftover incoming files are removed on the next receive turn. Schema puts and drops follow their own winning stamps; older ones cannot undo newer schema changes. Schema removal is paged and idempotent; its head advances after removal completes. A snapshot supplies a starting point, not automatic repair for a frozen stream or missing later entries. Snapshot installation separately checks the owner signature, advertised entry hash, manifest, native paths, file lengths and digests, and covered stream heads.

Before entry validation, a segment download must match its declared length and digest, device stream, consecutive sequence range, and final hash. A malformed segment returns a read error. Entry signature and payload checks still run after expansion; their frozen-stream behavior is unchanged.
