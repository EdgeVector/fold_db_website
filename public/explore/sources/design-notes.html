Cloud source and future design

Source review: 29 October 2026. Earlier shared-data design: 6 October 2026.

Backup preserves run files. The owner can request a full snapshot or explicitly enable automatic backup. Automatic work requires a saved account connection. Restore combines a snapshot with accepted changes and still needs its release switch. This review does not establish a deployed service or a successful recovery.

Equal canonical fields share one protein

Each canonical field shares independently across schemas. App ownership, key differences, declarations, and the earlier schema-overlap rule do not restrict membership.

A matching name alone does not establish equal identity. An explicit field map resolves its source identity.

Schema load joins existing memberships and molecule references in one native batch. It preserves current tips and author clocks.

Writes establish membership before they select related tips. They need the required key fields for each related molecule.

Older keys do not fill automatically. Backfill still needs exact source keys, shared target-key identities, and valid existing protein membership.

A snapshot adoption plan does not replace data

The owner sends a held snapshot request and candidate metadata through snapshot_plan on /api/sync/logical-v1. Node API version 10 adds this action.

Both snapshots need enabled, certified device coverage. Disabled or unknown coverage fails. The existing local snapshot requirements still apply.

The plan compares at most 33 device positions. Unknown devices, changed original device identities, or different hashes at equal positions fail.

A candidate behind the local state needs its common event hash in retained local metadata. A candidate ahead needs separate proof of that shared history.

A missing device entry does not prove an empty database. The plan names the original local or peer events still needed.

Every result sets replacement_allowed: false. The comparison reads bounded metadata; it replays no event bodies and publishes no replacement.

Replacement still needs a common starting-state proof, complete candidate file checks, and another check of the local state.

It must preserve local identity, update device receipts and control records, replay required original events, and publish one complete state.

The response has a 32 KiB limit. This operation does not enable ordinary cloud restore or prove a production recovery.

Write preparation batches exact field reads

Changed fields share bounded header and tip reads within each database scope. Each fetch holds at most 10,000 exact keys.

The same reader resolves current private changes, generation state, and Delete barriers. A missing exact-scope header retains the existing full-load fallback.

Prepared values leave with the request. This fetch limit is separate from the small-result reuse allowance. Disk still precedes the ack.

Linux memory and account encryption

The Linux allocator disables large memory pages by default. An explicit MIMALLOC_ALLOW_THP value keeps the caller’s choice.

The process reports the actual kernel state or an error. This policy reduces retained memory; it adds no total process cap.

Local file-record encryption uses the account content key directly. The unused alternative keyring and its factory option are removed.

Aggregate, expiry-queue, S3, and telemetry helpers retain their earlier behavior. CI adds bounded diagnostics and operational checks, not new guide parts.

Optional history keeps earlier field values

History is off by default. The owner chooses Off, Keep, or an expiry duration for a canonical field within one database scope.

A changed value or Delete saves the previous visible atom and its original write facts. References keep its atom and required file bytes.

Expiry starts when the value enters history. Later policy changes affect future entries. Expired entries disappear from reads before the worker releases them.

The history worker handles 32 entries per expiry page. Purge and record expiry also remove selected history, including keys without current tips.

History activation advances the logical key marker. Off does not reverse that change; older programs that do not recognize history must refuse the home.

Restore one field is a new conditional write

The owner can list and read history for an exact schema, field, and key through /api/atom-history.

Restore requires an unexpired history entry and either the expected current mutation or an absent-value condition. It creates a fresh normal write.

A concurrent change fails the condition. This operation does not rewind the database or enable cloud restore.

Snapshots record exact device positions

New snapshot metadata uses version 5. It records disabled device capture or a signed map from the exact held disk state.

The map includes the local device and up to 32 trusted peers, within 32 KiB. Restore checks the map against restored native files before publication.

Older version 3 snapshots remain readable with unknown device coverage. Unknown does not mean disabled.

The map grants no device trust, restores no private signer, and removes no device events. Cloud change-backup metadata remains version 4.

A held local snapshot uploads nothing

The owner can prepare, inspect, resume, and release a snapshot through the logical-sync route. Its saved request retains exact files in both homes.

Automatic backup must be off and remote work settled. An unreleased snapshot blocks new cloud work and retains local disk files.

This operation uses the real backup planner. It creates no independent backup or cloud publication.

Query replies can omit unused detail

Full detail remains the default. Values mode retains keys, values, and the record conflict signal while it removes field metadata.

Count mode requires supported live keyed reads without conditions, value ordering, offset, or continuation. An unavailable exact count fails.

Each request reads and checks a shared atom once, then reuses it across selected tips. This adds no cache between requests.

Ordinary record writes no longer rewrite unchanged schema definitions. Actual schema changes still update their definitions and key bindings.

DEV backup cleanup stays within its CI account

The CI recovery workflow registers its exact run and stream before uploads. It resumes saved cleanup identities after uncertain replies.

Cleanup protects the baseline and latest successful recovery. Unknown or unverified uploads remain protected.

The workflow checks recovery of the retained snapshot after cleanup and requires enough space before the next upload.

This source path does not enable automatic deletion for normal production backups or prove a successful production recovery.

Optional signed device changes

A home can opt into capture with LASTDB_LOGICAL_CAPTURE=1. Once enrolled, its saved identity and event position remain required on later opens.

Accepted field values, their signed event, and the device position share the data commit.

This first version accepts personal create and update requests only. It refuses deletes, proteins, mapped fields, shared data, aggregates, and file blobs.

Local requests are limited to 128 mutations and 256 KiB. An event has at most 1,024 field outcomes and less than 1 MiB.

The event backlog has a 64 MiB cap and no cleanup. A full backlog refuses the complete write. Ordinary reads do not replay these events.

The separate device signing key is outside the native backup file list. Missing or inconsistent identity state refuses open.

Device exchange is an explicit owner operation

The owner trusts another device’s initial position, then exports or imports pages through POST /api/sync/logical-v1.

The receiver checks signatures, event order, and installed schema, field, and molecule identities. Gaps and different chains are refused.

Data and the peer position share one disk commit. Matching saved event hashes make repeat delivery safe. Imports do not create new local authored events.

A page holds at most four events and 1 MiB of event data. The home supports 32 trusted devices and 65,536 saved event receipts.

The same limited field rules apply. No automatic delivery worker connects this operation to cloud backup or restore.

Existing records need explicit backfill keys

The owner supplies source keys to POST /api/db/backfill-protein-keys. Schema load does not discover or backfill historical records.

One request accepts 1–64 keys and at most 4,096 source tips. It copies current visible tips between existing personal protein members with shared canonical identities.

Original atoms and author clocks stay intact. Newer target tips and Delete barriers keep priority. Ambiguous target slots are refused.

The operation does not replay historical source Delete barriers. A capture-enabled home refuses this unsupported writer.

New definitions need a verified developer owner

New schemas, expansions, and declared fields require an Exemem developer certificate with publication permission and the registered app owner’s signature.

Local namespace claims use the same rule. A repeat request that only returns an existing public definition can remain a read.

The service resolves that read from saved definitions and follows valid successor links. Broken or ambiguous links fail.

An expansion saves its predecessor marker and successor together before it updates memory. Competing expansions cannot silently replace the same predecessor.

This review checks source behavior. It does not confirm the deployed schema service.

Restore diagnostics keep the exact selected chain

After a log link passes its checks, restore saves its identity, record and file roles, byte totals, and event boundaries.

A resumed check requires the same facts. The CI recovery check keeps its selected backup fixed while later automatic backups can continue.

The complete restore checks and release switch still apply. These changes do not establish a successful production recovery.

Reuse stays inside one write preparation

A private write can remember an exact disk result, including confirmed absence. Later steps reuse that result from the same saved state.

Private changes take precedence. A counter change therefore cannot read an older saved value after the same write updates it.

The allowance is 1 MiB and 10,000 results, with at most 16 KiB per value. It retains no decoded storage blocks.

Results leave memory when preparation ends. Ordinary reads use no such store. Disk publication still precedes the ack.

Each molecule supplies its hash protection key

Each molecule has its own secret key for non-empty hash tokens and a required rule for typed ranges.

There is no plain-hash option. The removed account-level hash key was unused; the account content key still protects disk and backup bytes.

This change does not alter the current disk format or open client cursor identity.

One data model across the layers

Memory serves current logical records. A native write saves a complete disk snapshot before memory publication and the ack.

Cloud backup is a separate operation. A local ack does not confirm a cloud copy.

The layers preserve the same data relationships. Their files and completion times differ.

Interrupted file deletion completes before normal use

A saved request names the exact file removals and both homes’ saved positions. It reaches disk before the related change begins.

If the record change reached disk, startup completes the saved file removal. If the record change did not reach disk, the file stays.

An unexpected position or identity stops recovery. Backup refuses an unfinished request. This local recovery does not enable cloud restore.

Compaction reserves output space

Before each output, compaction checks the disk cap and the free-space reserve. Unfinished writes in both homes share the filesystem allowance.

Insufficient space leaves the previous saved state in force. The worker retries later. Active reads can still retain replaced files.

Backup dependencies do not authorize deletion

The explicit dependency command follows accepted backup links and checks their identities and hashes. It creates no destination and deletes no provider files.

Current uploads omit the new dependency declaration. The command therefore keeps the earlier accepted chain conservatively.

The protocol can distinguish a full snapshot from its required change backups. New declarations await service support; automatic deletion for normal production backups remains unavailable.

The command has a 90-second limit, a 32 MiB metadata limit, and a 32,768-backup limit. It still requires the release switch and recovery credentials.

Different keys keep separate molecules

Shared fields under different lookup keys keep their own molecules. Proteins connect their common atoms.

Only matching key names and types can share a molecule. Conflicting existing molecule mappings cause an error; they do not change silently.

Fault reports keep private details local

External fault reports retain a fixed category, severity, operating system, and permitted version and environment fields.

Crash text, paths, stack details, and previous log lines stay out of those reports. This review does not verify a deployed report.

Two run homes, one logical model

A home is a folder of disk files. LastDB uses disk-run for records and disk-cas for file blobs.

Each home has an encrypted CURRENT file list and ordered run files. A native write saves before memory publication and the ack.

Reads check newer files before the compact base. Small filters can rule out absent keys. A match still needs the actual key check.

One worker combines files in both homes after commits. Startup also resumes needed work. Eight files in a level trigger a merge.

Encoded keys must fit 64 KiB, including the collection prefix. Values must fit below 32 MiB.

CAUTION: Current code opens only format 4 homes: disk format v2 with typed ranges. Earlier text-order homes and backups are refused. The old converters are removed.

Some module and marker names still contain “pack”. They do not enable the old disk format.

New-home setup can resume

A folder lock protects creation. A new home saves its account and key-format checks before the format marker. Normal use verifies those checks.

Before the marker exists, a restart removes only recognized partial creation files and starts again. An unexpected entry prevents removal.

Every supported home uses typed range order. Earlier key-format switches no longer select another home format. Startup never converts an existing home.

Run-file read reports now count file opens, file checks, lookup bytes, and data bytes. These counts describe work, not a speed guarantee.

Search delivery is optional

The daemon sends Search batches only when enabled. It sends them after disk publication to a local inbox for the separate search app.

The live queue defaults to 64 MiB and 4,096 files. A reached limit pauses delivery and marks the inbox for a rebuild.

Existing files remain. That limit does not fail the database write, but disk errors can still fail a request.

CAUTION: The inbox contains plain JSON outside the encrypted run files. For a schema with classifications, only word fields qualify.

Fields marked secret or no_index stay out. A schema without field classifications makes every field eligible.

A file reference retains only its name and media type. File keys, file identities, bytes, and thumbnails do not enter the inbox.

Offline search rebuild uses the node key

With the daemon stopped, the command opens a complete run database with its node key.

It writes batches with the same field rules as live delivery. Results change only after the search app consumes them.

The command refuses incomplete creation. It does not create a database, finish setup, or change the disk format.

The offline command does not enforce live queue limits or clear the rebuild marker. A completed export does not resume live delivery by itself.

Explicit disk cleanup can resume

The owner can request cleanup of both run homes. The node saves the request and resumes an active request after a restart.

Small steps combine files even below normal thresholds. Active readers can retain replaced files, so the job waits for their release.

New writes continue between steps and can delay completion. Status reports progress without another disk walk.

Completion covers the saved local boundary. It does not cover future writes, backup copies, or file blobs that still appear live.

A client timeout does not cancel the saved job. An uncertain disk publication stops cleanup until recovery.

Private write memory ends at publication

A private write reserves memory until disk publication. Warm records then use their normal allowance; they do not retain the private write allowance.

The warm set still defaults to 256 MiB. That limit is not a total process cap.

Warm-set status reports real charges

Status now reports the actual warm-set byte charge instead of zero. The warm-set section also reports its own limit.

The process estimate now uses the configured warm-set limit alone. Removed cache allowances no longer reserve extra space. An estimate is not measured process memory.

Base compaction uses counted bytes

The worker counts older values hidden by new records and physical delete markers. Counts include encoded keys and stored values before block compression.

Newer files trigger base work above both 1 MiB and one sixteenth of record bytes. Obsolete bytes trigger it above both 64 KiB and one eighth.

Each step replaces a small part of the base and saves its progress in CURRENT. The next step uses that saved boundary.

Old readers retain their files. New writes, reader holds, and delayed compaction can use extra space. These thresholds are not a filesystem-size guarantee.

Base file targets range from 256 KiB to 1 GiB. A large record can exceed a target.

The worker waits up to two seconds when reads retain more than one sixteenth of current file bytes, with a 1 MiB minimum.

Long reads can retain files after that wait. No fixed total disk-size guarantee follows from these controls.

The disk-size gate is a CI check

The CI disk-size check runs separately from speed measurements. It requires database files at or below 1.5 times logical data bytes at settled checkpoints.

It uses the larger of file lengths and allocated disk bytes. Its workload disables Search and checks again after deletes.

This is a release check on that workload. It is not an enforced runtime cap or a guarantee about temporary peaks.

Compact records before block encryption

Run homes try shorter forms for repeated field names, IDs, integers, and timestamps. Reads reconstruct the exact original record bytes.

The encoder checks its output before use. Only compact JSON objects or arrays up to 1 MiB qualify.

Other values keep their original bytes plus a format byte. Run values must fit below 32 MiB before compact encoding.

The file block can then use compression before encryption. Earlier run homes with untagged values are refused; no automatic upgrade occurs.

File bytes reach disk before their references

A split commit saves new file blobs, then other record changes, then file blob deletes. Memory publication follows the required disk work.

The two homes do not share one atomic disk commit. A crash or failed file delete can leave unused file bytes.

This order protects required files. Run backup now sends file blob run files to B2 and record run files to R2.

Explicit cleanup in the storage library

The storage library supplies one compaction step below automatic size thresholds. The node cleanup job repeats these steps and saves its request.

The call reuses existing file and input limits. It removes obsolete stored values; atom counters still control logical deletion.

One completed call does not promise zero retained bytes. Reads, backup file links, and failed file removal can retain space.

The V2 backup path in current code

Capture waits for the flush, then briefly stops writes while it retains both run homes at one state.

  1. Retain both CURRENT file lists and every required run file.
  2. Check account keys, atom records, and required file bytes.
  3. Copy the encrypted native bytes and check the service receipts.
  4. Publish the encrypted manifest and save the accepted result.
  5. Release source holds only after a confirmed final result permits it.

Extra local file links retain the exact bytes without another full data copy. Local writes continue after capture.

A resumed job uses that same source. It must not select a newer state. The old standalone backup command is removed. The current stopped-home command below uses native run files.

Manual connection for an existing account

The owner can supply an existing account credential through the local node. The node checks account identity and permission for R2 and B2.

The saved connection binds the credential to this node and account. A manual request or explicit automatic enable command follows separately. The connection alone uploads no database files.

This connection permits owner backup requests without the release switch. Restore still requires that switch and account credentials.

Account credentials use the paused credential file. The DEV restored-account enrollment path stays separate. Legacy cloud configuration files no longer select a cloud mode.

Bounded encrypted reads

The run reader authenticates a complete encrypted frame before it exposes decoded bytes. A second read verifies the bytes and exact end again.

Small frames use buffers sized to their encrypted content, up to the stream allowance. Large uncompressed data uses bounded pieces.

Both homes share a metadata allowance. File lists, record decode work, and compressed data still have limits. A size refusal does not skip verification.

Backup checks can reuse verified blocks

Backup and restore checks retain the next key from each relevant run file. They can also retain an authenticated decoded block.

Later keys and values can reuse that block. Equal keys select the newer file, and the value comes from that exact file.

Keys, blocks, and temporary copies share a 1 MiB allowance. Optional block reuse retains at most 32 file handles.

Insufficient memory or file handles returns to the original path. Restore can repeat the complete check after it releases optional handles.

Changed files and failed integrity checks still cause refusal. The check retains its value-size limits. This reuse does not enter the warm set.

Restore errors name a fixed check stage and cause. Private paths, keys, and record contents stay out of these diagnostics.

Older cloud paths are removed

V2 supports manual snapshots, explicit automatic policy, and checked restore. The retired V1 upload, restore, replay, and automatic workers remain removed.

The retired V1 job reader and completion check are removed. V2 no longer uses old job records to admit a new request.

This removal does not convert old jobs or make older packed backups readable.

An unfinished V2 job still needs its own confirmed result before a new V2 job can start.

The old Cloud Off action is removed. An explicit V2 job has its own Close action.

A checked restore to a fresh destination

  1. Select one accepted state. Save its exact identity and check the chain to its full snapshot before file requests.
  2. Check the encrypted manifest, destinations, lengths, and hashes. Recover the original native run files named by the manifest.
  3. Replay accepted changes in order. Check both run file lists, account keys, atoms, and required file bytes.
  4. Publish the verified destination without cloud activation. Run restore creates fresh local lock files.

Restore refuses an existing destination. A partial record import needs a fresh session; a completed checked import can resume. The walkthrough performs no recovery.

Restored account access is a separate DEV action

The reconnect action checks the completed restore receipt and existing account identity. The restored home must be inactive.

It obtains access to the same account without a new identity or a change to recovered data. It refuses primary and archive homes.

The saved credentials remain paused. Reconnect does not start a backup. The home must pass current run-format checks. A retained receipt cannot make an older packed home usable.

Large files need complete local coverage

An atom can reference a file blob. New file keys depend on the private account key and original file hash.

The protected atom carries the file key. The file address identifies the encrypted bytes. Only the current account-based file encryption format is accepted. Older encryption formats and plaintext fallbacks are removed.

Backup needs exact coverage for each main file, thumbnail, and poster. Bytes inside the saved native files need no separate external copy.

V2 requires those bytes inside the captured native files. Remote-only files refuse; the old external-file transfer path is removed.

V2 byte backup

A snapshot or change job retains one exact saved source. It checks transfer receipts before it publishes an accepted backup.

Run jobs send file blob run files to B2. Record run files, both CURRENT lists, home descriptors, and backup metadata use R2.

V2 currently requires external file dependencies to have coverage inside the native file set. Unsupported dependencies refuse.

Resume keeps the exact saved request and capture. Uncertain remote work retains its file hold until a confirmed result permits release.

Manual online backup uses the existing node. Stopped-home backup uses a separate command. Automatic policy requires a saved connection and a separate explicit enable command.

Two destinations, one accepted backup

New jobs require account access to both Cloudflare R2 and Backblaze B2. The client selects a destination for each object.

R2 uses a create-once upload. B2 grants one temporary upload part; the service owns completion. Receipts bind the destination, hash, and length.

The public client descriptor contains no native layout details. The encrypted root holds the recovery identity. A snapshot names both file lists; a change backup names its base and predecessor.

Large native files split into pieces of at most 64 MiB. Files smaller than 64 KiB can share an object for the same destination.

A small-file bundle holds at most 8 MiB and 512 files. The manifest records byte positions to reconstruct each original file.

Backup status does not promise current coverage

Node status reports V2 work, the automatic schedule, retries, pauses, local change positions, and the accepted cloud boundary.

A historical receipt does not prove that current writes reached the cloud. The health check keeps unmeasured freshness unknown.

An enabled policy does not prove current coverage. An automatic pause appears as blocked work. Unmeasured freshness remains unknown.

Each V2 job keeps its own saved state

V2 uses its own job records and source holds. It does not read or repair the retired V1 job records.

The disk format v1 recovery reader is also removed. Local file reads need local bytes.

An unfinished previous V2 job blocks a new request. It must reach a confirmed final state before its source holds can leave.

Protocol version and disk format describe different things. Neither old path enables packed-home recovery.

Restore preserves the saved state

V2 restore selects an exact accepted snapshot or change backup and refuses an existing destination. Older packed backups are unsupported.

It checks both run file lists, account keys, atoms, required file bytes, and saved range rules before publication. Typed rules must agree with the schemas.

The restored files retain their saved counters. Restore does not recount or repair them. A pending restore marker refuses normal use.

Atom records use encrypted run blocks

Run atoms use plain records inside encrypted blocks. The records have no separate content encryption or molecule key bundle name.

This permits compact record values before block encryption. Reads reconstruct the exact original record bytes.

The node key derives separate keys for records and file blobs. Data blocks, lookup blocks, and CURRENT use encryption.

File blob protection remains separate. Block checks bind bytes to their file identity and position.

File sizes, clear footers, and some layout facts remain visible. This does not hide every storage detail.

The new private-key range implementation remains separate from active storage. Its ordered terms reveal order, equality, length, and other information.

Date values and retention

Date fields require valid YYYY-MM-DD text. DateTime fields require an explicit offset and at most nine fractional digits.

The field value stays as supplied. Date and DateTime can serve as range keys in a typed home. Neither can be a hash key.

Retention backfill can replace an old arrival-time age with the current tips’ original write time. Existing records can then expire.

Expiry holds one key page across all schemas. The default is 16 keys; the configured maximum is 64. Record width can reduce that count.

The worker empties and releases each page before the next schema. Short or filtered pages do not end discovery. Schema metadata uses separate memory.

Range order and next-page checks

A read captures its schema, field types, and stored key format. Its next-page cursor includes a compatibility tag for those facts and query options.

Return the whole cursor unchanged. A missing or mismatched tag refuses continuation and requires a new first page.

Integer ranges put 2 before 10. Text ranges keep text order. Earlier text-order homes are no longer supported.

The tag does not grant access or hold a saved data snapshot across pages.

A typed home saves one range rule per molecule. The query uses that rule for key selection, result order, and cursor checks.

Typed values stay inside encrypted run blocks. Typed homes use no separate order-preserving range encryption. Prefix queries require text ranges.

Range decoding uses the selected molecule format. Plain text stays plain; malformed encoded text refuses the read. Missing molecule keys load in batches.

Current node replies only

The app SDK expects the current query, mutation, version, and notice replies. Older reply formats no longer receive compatibility conversion.

Batch queries require the batch route. The SDK no longer retries them as individual queries when that route is missing.

Registry ownership and stored releases

The S3 backend stores apps, releases, and channels in separate records. It reads saved ownership before a protected change.

Three different delete markers

  • A logical Delete barrier blocks old replay. Its removal requires an explicit saved replay cutoff.
  • A molecule generation marker hides an older generation entry. New deletes omit it when no generation needs it and a lock prevents one from appearing.
  • A run-file marker hides an older physical value. Base compaction removes it when no older value can return.

A delete keeps the marker if an active generation exists or another operation holds the generation lock. Logical Delete barriers remain independent.

Explicit cleanup can remove redundant generation markers in pages of at most 256. An active or prepared generation blocks cleanup. Replay cutoffs stay unchanged.

Automatic backup requires an explicit choice

The policy starts disabled. The owner must first save a checked account connection, then enable automatic backup.

Defaults check new changes every minute and request a full snapshot daily. Each interval can range from one minute to seven days.

One job runs at a time. A retry keeps its request and exact source. Some errors pause the policy for attention.

No new changes means no change upload. The daily snapshot remains due even without new writes.

Disable stops new requests and retries. An active job can finish. Local metadata cleanup does not delete remote backups.

Saved changes connect snapshots

A full snapshot establishes the start of a local mutation log. The enabled log retains original encrypted run files through local file links.

A complete change saves file additions, record updates, then file removals. Sequence and hash checks protect the recorded order.

A change backup captures up to 128 complete entries after the accepted boundary. Its encrypted manifest names the base snapshot and previous accepted change backup.

The log has resource limits. Missing retained work records a gap and requires a new full snapshot. Cloud completion does not delay the local ack.

Restore recovers the base, then replays the accepted chain in order. It saves progress for resume and checks the complete data before publication.

Shared field names keep one meaning

Ordinary schema and field declarations can add a definition after common code checks. The separate field-publisher key and publication route are removed.

The checks use names, descriptions, types, and available meaning comparisons. They preserve different units and key roles.

Supplied field identities must match canonical definitions or permitted declared fields. Imports use the same definition checks.

File pointers and local export use current formats

Counter work can share one disk read

A counter update can check its counter and conditional atom-body presence with one decoded block. It still uses one saved view.

The normal read checks a body when needed. Private changes, limited memory, or streamed blocks use the existing fallback.

This temporary work adds no cache between calls and does not change the warm set.

Future design: a shared database

The design gives authorized members access to shared encrypted data. A copied schema can reference the same molecules and atoms.

Members need the correct keys and access grants. A schema copy alone does not deliver files or grant another device access.

Simultaneous cloud writers need a defined frontier, conflict rules, and retention rules. The guide treats this behavior as future design.

Future design: a guaranteed write

A proposed guaranteed write requires a cloud grant before success. Current local writes confirm disk completion without that grant.

The old mutation cloud-publication option and cloud receipt are removed. The exact cloud acceptance and recovery contract needs implementation and proof. The guide does not present it as an available write mode.

Schema checks keep a separate read-only path

A schema check resolves the proposed fields and keys without saving definitions or changing local schemas. Synchronization can register and load the result.

Both paths now share explicit decision rules. Different keys still require a new schema proposal; the node does not invent a service identity.

Stored file records require binary encryption

The file key protects file contents. Account encryption also protects the complete local file blob record, including its metadata.

Every stored file blob record requires the binary ENB: format, even when its file bytes already have encryption. Run-block encryption surrounds that record.

CAUTION: Older ENC:, ENZ:, and unprotected file blob records cause an error. They are not silently treated as missing.

Optional record compression defaults off. A read can still open compressed ENB: records when that write option is off.

The old reseal and reap-unsealed commands are removed. There is no automatic conversion at this boundary.

Other raw-key helpers still accept ENC: where their callers use it. Atom records inside run blocks need no separate record encryption.

Local encrypted export remains available

An owner request selects records by keys and includes their required local file bytes. LastDB signs and encrypts the result for the supplied recipient.

The response contains the protected package. The caller handles delivery. This route sends no message and uploads no object.

The old slice importer, staged-delivery writer, recipient enrollment, and message sender are removed. Missing local bytes cannot use a cloud fetch fallback.

App compatibility now checks declared formats

JSON app manifests can declare request and notice format versions. The installer checks those versions against the node’s supported range.

The optional LastDB version requirement remains. The TOML path checks that requirement. An absent declaration does not prove compatibility.

The signed registry can select a release by supported formats. It prefers an exact build match; entries without format declarations still need that match.

Nightly packages remain separate from the app registry

The nightly workflow builds a fixed LastDB revision for Apple silicon and Linux x64. It checks required gates and verifies the uploaded release bytes.

It publishes a GitHub prerelease. It does not update installed nodes, Homebrew, or the app registry.

The registry connection remains a proposal. This source review does not confirm a successful nightly release or a deployed registry change.

Local development app installs

The install command accepts --from, --rev, and --dev together. It reads the chosen commit’s manifest and checks declared format versions.

The installer clones the origin URL when available, or the local repository otherwise. The selected commit must exist at that source.

The saved receipt records the exact commit and development status. Uncommitted edits and signed-release status do not come with this path.

Backup after a clean stop

Before an upgrade, the owner can request a full backup of the final cleanly stopped state. The command does not stop the daemon itself.

It checks the exact stopped session and shutdown flush receipt. A saved owner connection is required. Automatic backup must be off, with no unfinished job.

The command locks both native homes and retains their files without a daemon, full database copy, or logical database boot. Archives are refused.

After acceptance, it reads every remote object. It checks lengths and hashes, including the original files reconstructed from cloud pieces.

It checks both CURRENT file lists again. Local job metadata can change; the native data and file lists must remain unchanged.

Success verifies backup bytes. It does not perform a restore or upgrade.

Registry generations preserve app identity

The optional SCHEMA_DEFINITION_NAMESPACE selects a separate set of schema and field definitions, releases, channels, and compatibility records.

App identities, ownership, and quota state remain shared. A new generation copies no app identities or definitions.

An empty generation stays empty. The service does not fall back to older definitions.

The name must start with canonical-. The configuration also requires a matching separate search store for derived schema data.

Without the setting, the existing layout remains. This review does not confirm which configuration is deployed.

Reuse within one write or batch read

A write can reuse its checked schema metadata within its current memory allowance. Changed source state invalidates that reuse.

A run reader can reuse its encryption-key setup. One batch lookup can also reuse a decompression workspace.

Each block still receives its own integrity and size checks. Bounded backup reads keep their separate decoder path.

This work does not add a cache between requests or change the warm-set limit. The guide makes no measured speed claim.
