Source notes and release limits

Source review: 4 November 2026. Merged LastDB revision 4b76c7c9.

Format 11: one local record space. The guide describes 134 parts and 455 connections. This update covers seven commits after 70d01896. Completed reviews cover 847 commits after October 21.

App publishing and installation

Normal app installs read the stable or next channel’s public catalog for the node’s exact API version. Each catalog has a registry signature; each entry also has a publisher signature over the app version, Git commit, and interface declaration. A declared search-notice version must match exactly. The node build label is recorded but does not choose the entry.

The installer checks out the full listed Git commit and records it in an install receipt. This path does not use the old version-range preference or require a separate verifier result. Signatures establish who signed which bytes. They do not establish that an app works or limit its user permissions.

Publishing starts from a clean Git checkout and requires an explicit HTTPS registry address and developer account key. The publisher signing key can come from LastSecrets. The publish command records interface versions; it does not itself run a compatibility check.

The CLI keeps verified catalogs outside the database. A failed download can use a valid saved catalog. Lower sequence numbers, or different bytes with the same sequence, cannot replace it. At seven days old, a catalog produces a notice but remains usable. Installation still needs to fetch the app’s source commit.

Normal managed installs now prepare a separate version from the signed catalog, read its install instructions, and switch stable command links after checks. First installation and changed instructions require consent. Brain, LastSecrets, and Search can switch between explicitly trusted owner and CI publisher keys at the expected PROD catalog and GitHub source. Both old and new installs must have pinned trust. Other publisher changes require owner rotation. Inactive installs still prepare code and links but skip health and post-install commands.

On macOS, a managed install installs a minute-by-minute updater. Stable catalog fetches are limited to once an hour while health checks continue; next is checked each poll. Other hosts can invoke the upgrade command. An alternate app root does not install the background updater.

A rollback requires an eligible, healthy previous version. A rejected source commit stays held across automatic polls until a newer commit or explicit install consent. Rollback switches code and links, not database writes or arbitrary install-command effects. Status reports health without triggering rollback.

The former HostTrack and verifier-log release installer is removed. Local development installs retain separate manifest checks. The schema service’s release storage and verifier queue remain, but they do not drive normal catalog installation. This review does not establish live catalog or verifier state.

Apps declare typed schemas locally

The node builds and loads a direct app declaration without finding or registering it at the schema service. Every field must name a type. Shared schema resolution and publication remain separate service operations.

The File field type and shared-file pointer are removed. A file belongs to the record itself. Every ordinary declared field still needs a type; Any remains temporarily in this source revision.

Existing keys and field meanings remain protected. A declaration does not convert existing record values. Shared field definitions still do not share values between schemas.

Source: Local declaration · Required field types · Field type validation · Separate live resolver

One schema owns its records

A schema names fields, a primary key, and optional named alternate keys. Each schema owns its record values.

Canonical field reuse shares meaning and type. It does not connect records in different schemas.

One stored record holds fields, their write facts, metadata, an optional file marker, and any delete marker. The final encoded record, including the marker, must fit within 64 KiB.

Each record can own one file. Its marker describes name, media type, size, and plaintext hash; the bytes stay in the separate file home. Identical files on two records occupy separate entries.

Schema advice and app publishing

POST /v1/advice/schema is read-only. It compares a draft with the service’s canonical vocabulary and loaded schemas. It can report names, different meanings, missing types, classifications, and similar schemas. Similarity is a suggestion, not proof that two definitions are interchangeable.

App check and publish print optional advice on stderr. A request waits at most five seconds. A network failure skips the remaining schemas; an unusable reply skips that schema. Advice failure never blocks either command.

Publishing has separate mandatory checks before signing: the manifest must explicitly list its schemas and type each field. The command reads the running node and checks that every app-owned schema appears with the same identity. An empty list is allowed for an app with no owned schemas. This verifies the currently declared schema set, not arbitrary future app behavior.

Source: Advice findings · CLI advice limits · Publishing checks

Catalog feed is included; service configuration controls it

The service-controlled feed verifies signed stable and next lists by API version, then fetches public GitHub manifests at their exact listed commits. It shares schema normalization with the node. Each app/commit is read once, with at most 20 new manifest reads per run. Private entries are skipped.

The feed now rejects an entire manifest if any declared field uses Any, meaning any kind of value. It also checks inside arrays, maps, objects, and type choices. This keeps vague types out of newly collected shared definitions. A skipped manifest records the app, commit, and reason and adds none of its schemas.

Already recorded app commits are not automatically read again. This change does not clean earlier saved definitions. A newly listed commit can be read with its corrected types. The rule belongs to feed admission; it does not remove Any from the local field type system.

Definitions and their provenance live in a separate catalog_feed.json image with conditional S3 writes. Removal from a successfully updated list marks a definition unlisted; a missing or failed list keeps its prior verified state. Invalid manifests are recorded as skipped, transient failures can retry, and a rate limit stops manifest reads for that run.

The feed can separately offer new field names to vocabulary admission. Vocabulary writes precede the catalog-image write; they are not one shared transaction. The current advice implementation reads loaded schemas and vocabulary, not the separate feed image.

The Lambda build now includes the feed and its route without a catalog-feed build feature. It still stays off when SCHEMA_CATALOG_FEED is unset. Its internal route also checks for the scheduled event’s catalog-feed-schedule identifier. Running it requires those service settings and a configured trigger; this source review does not establish that a deployment enabled them.

The embedding runtime comes from a Lambda layer

The Lambda embedding build loads ONNX Runtime from a shared library supplied alongside its model files. It no longer links that runtime into the main function package. This reduces the package’s size and allows the catalog feed to be included.

ORT_DYLIB_PATH must name an existing runtime library. Model files come from SCHEMA_FASTEMBED_MODEL_DIR, FASTEMBED_CACHE_DIR, or the default /opt/fastembed_cache location. This path does not download the runtime or model during a request. Missing runtime configuration causes embedding initialization to fail; checking that the file exists does not establish that the library is compatible.

The embedding model remains all-MiniLM-L6-v2. This is a packaging change, not a new similarity rule. Live layer contents and service deployment are outside this source review.

One storage format writer for a home

At startup, one component connects records, schemas, clocks, retry receipts, change notices, and lookup keys to the same home and key context. Ordinary database components receive readers and specific write operations. They no longer hold raw storage writers or open arbitrary storage areas. Physical disk storage and authenticated backup replay keep their own entry points.

Reads and writes check the same record structure: known version, a write stamp for every field, valid file hashes, and no surviving stamp at or below the delete marker. Before accepting a complete request, LastDB checks the final encoded record at every changed key against 64 KiB. Repeated changes to one key may temporarily exceed that cap during preparation. An oversized final record refuses the whole request before queue admission.

The file writer keeps an encrypted file and its marker together as an immutable payload. Only the writer that created it can accept it. It reads the current record marker before deciding to replace or remove the file. An ordinary title update can retain a file without reading or rewriting the file bytes. Writes check origin, marker, size, envelope, and nonce; reads verify the encryption tag, plaintext size, and hash.

The lookup-key writer creates encrypted bundles and their range rules. New key identities are limited to 1,024 bytes, saved metadata and wrap entries to 16 KiB, and the nested bundle and its encrypted form to 4 KiB each. The existing three-key form remains; only its hash-protection key is used. The other two slots do not encrypt fields or ranges.

Schema release, record-file deletion, erase audits, and the stopped-home replay cutoff now use format-owned writers too. The cutoff cannot decrease or advance into the future. History still checks field stamps, a 68 KiB encoded-entry cap, and matching expiry links. These are code boundaries and write checks, not a hostile-code sandbox or an audit of every stored key at startup. Format 11, the 256 MiB warm-set default, encryption algorithms, and save-before-ack remain unchanged.

Only format 11 homes

Every new home uses format 11. This release opens and restores only that format.

Each new run-home folder starts with owner-only permissions (0700). Creation does not repair permissions on an existing home.

Older homes, including format 10, need their matching program. The current program has no older-home reader or in-place conversion.

Format 11 removes the org database catalog, scoped record addresses, and automatic sent or received share copies. One schema and primary key identify a local record. Its optional file has a path derived from that schema and key. The format boundary prevents older bytes being read under these rules.

Retired aggregate and imported-field provenance fields are removed from the mutation contract. The signed mutation content hash now uses its v2 domain. This does not restore device exchange.

The old alternate-key change routes are removed. Changed keys need a separate schema and an explicit record copy.

A repeated schema declaration can add fields with unchanged keys and meanings. Existing records read added fields as absent. Schema reads use the exact schema name; the old superseded-schema redirect store is removed.

Run blocks still use zstd compression when it saves enough space, followed by AES-256-GCM encryption. Removing the value wrapper does not remove block compression or encryption.

Saved data must be readable

Local schema reads now fail on unreadable definitions, invalid keys, mismatched names, or incomplete ordered pages. A schema write does not silently overwrite an unreadable saved definition. Schema listings read bounded pages of 256 entries.

A missing write-retry receipt still uses the normal write path. A corrupt or oversized saved retry list refuses the request instead of being treated as empty. Delete-audit reads likewise report an unreadable entry instead of skipping it.

Saved request-activity reports now write every declared field, including zero measurements. Reading those reports requires the fields and their types; malformed records no longer silently disappear or become zero.

Whole-record memory and reads

Full query replies return one metadata block per record, including its optional file marker. Values-only replies omit it. The marker contains no file key or storage path.

The owner file routes are put-blob, fetch-blob, and delete-blob, all addressed by schema and primary key. API 26 removes the local org catalog and whole-home report routes, along with database selection in the field-history request. Conflict inspection and unused app blob routes remain removed.

Source: Query reply shape · Memory counts · API version · Schema declarations.

A read by key checks memory first. A disk fetch can keep one complete decoded record in the warm set.

Memory status now reports actual warm records and held records. Old counters that always stayed zero are removed.

The default warm limit is 256 MiB. It includes the decoded record and file marker. File bytes stay outside the warm set. Least recently used records leave first; a record held by a call stays.

A write publishes its record to memory only after the flush. Older read views and private writes use their own disk state.

A range page names one hash and fetches bounded key pages. Owner pages across a schema follow protected stored-key order.

A page can stop early after many deleted records. Even an empty page can return a next cursor and report more data. Send that cursor unchanged.

Owner cursors name stored positions. Offset, page size, and one extra record must fit within 8,192. Deleted keys also consume the read allowance.

A hash schema without a declared key field returns a protected hash on an owner page. That hash is not a mutation key.

An ascending owner sample without extra query work can stop early. Its reply reports more data and no exact total.

If the reply includes every found record after its offset, its cursor continues through an owner record page with the same fields and order.

A shorter reply has no cursor, because that cursor could skip found records. Other sample forms fail at the read limit.

Source: Incomplete sample replies · Sample continuation rules

Each batch read uses one memory and disk revision. A later page call can observe later writes. Counts, conditions, and deep offsets can fail at the read limit.

Source: disk_pack/record_warm.rs · core_set/records.rs · record_store/record_walk.rs · records/range.rs

One complete saved change

A native request saves records, alternate entries, file changes, history, and notices. File additions reach the file home first, record changes follow, and file removals come last. The two homes have separate disk commits. Memory publication and the ack wait for completion.

Ready requests can share a flush. There is no flush interval.

Each field keeps its own write order. Local metadata updates replace only supplied keys and preserve omitted keys.

An alternate entry belongs to the primary key it names. A departing record removes it only while that ownership still matches.

Repeated changes to one record must leave a final value within 64 KiB. A failed final size check refuses the request.

The older field-size setting remains in status, but no write path uses it. It does not raise the record cap.

Source: transaction/request.rs · write/record_effects.rs · record_value/meta.rs · alternate_keys/write.rs

Schema removal releases its records

CAUTION: A schema drop removes stored data. It first blocks new writes to the schema.

Schema removal deletes records, saved history, and alternate entries in steps of at most 256 entries. Each removed record’s file path is deleted in the same native request. Next, separate bounded batches clear the schema’s age entries, latest-age links, and observed hashes. Tracking writes refuse blocked or removed schema owners.

The owner can inspect observed expiry hashes with the schema-retention route’s partitions action. Pages contain at most 256 hashes; an empty page may still have a continuation. A cursor belongs to the selected retention anchor. The expiry worker follows every page before using the complete hash list.

The schema disappears after cleanup succeeds. An unreadable record or history entry stops cleanup instead of being skipped. If cleanup stops, the schema stays blocked. Repeat the drop to continue.

There are no org or received-data scopes in this format. Old backups and physical file holds can still retain earlier bytes; schema removal does not erase every copy everywhere.

Source: Drop order and durable block · Bounded record release · Complete expiry cleanup · Hash-list continuation · Tracking owner checks

History, deletion, and files

Field history is off by default. An enabled policy saves the previous field value and write facts as a copy.

A history copy contains an earlier field value and its write facts. It omits record metadata and the record’s file. File replacement and deletion have no field-history recovery.

Delete keeps a marker against older writes. Purge also removes retained field history. A whole-record Purge refuses above 1,024 history entries.

The field history route is now /api/field-history. The older atom-history route is removed.

The owner can first remove field history in pages of at most 32 entries. The delete marker remains after Purge.

There are no shared-file reference counts or one-hour waiting worker. put-blob writes the record marker and file together. delete-blob removes the marker and file while keeping the record. Record deletion removes its covered file too.

Backup and restore derive the file path of each marked record. They require a live entry in the captured authenticated file home and stream its stored bytes through the run reader. This checks file presence and run-block integrity. fetch-blob separately decrypts the file and verifies its plaintext size and hash.

Saved conflict records, their cleanup worker, and their queue are removed. Write stamps still select the current value. Optional field history remains separate from losing-write conflicts.

Reference verification is removed. The remaining offline recount command only raises the replay cutoff; it no longer repairs a retention queue. Shared-file counters and their waiting worker remain removed.

Expiry can continue past an empty page of deleted range keys. It remembers a leading deleted stretch in memory and starts later passes after it.

A live write below that position clears it. Concurrent writes prevent an unsafe advance. Each hash starts from the beginning after 64 passes or restart.

The history worker requests up to 32 due entries at a time. A due-page read makes at most 16 bounded reads through removed keys. Successful cleanup advances its cursor; failure keeps its place. Empty bucket removal checks that no new write changed the bucket. Record file deletion uses no waiting queue.

Source: Expiry pages · Expiry progress · Record file lifetime · History cleanup steps

The offline replay cutoff covers the whole home. It no longer requires the all-scopes option. It must be a positive time at or before now.

Source: Offline replay cutoff.

Compaction and physical file holds remain separate from logical deletion. Older cloud copies do not disappear because a local record is deleted.

Local export remains; local share copies are removed

Format 11 has one local record space. It removes the org database catalog, share rules, sent copies, and received subscriptions. Reads no longer combine local records with received records. Named alternate reads no longer have a received-data restriction.

The owner can still export selected field values by key in a signed, encrypted package for a recipient. Export omits record files and their markers. It uploads nothing and does not install received records.

A simple keyed export reads at most 256 records per page and continues past empty pages. The complete export still accumulates in memory. Extra query work can hit the read allowance.

Shared cloud databases, recipient enrollment, and automatic multi-device delivery remain future work. Device exchange and saved conflict records remain removed.

Storage reports have different limits

The owner schema report counts live records and their encoded bytes. It reads all records in the selected schemas.

The persisted whole-home report, its reconciliation route, and its disk ledger are removed. The schema report does not measure every file in the home. Native run-file diagnostics remain separate and avoid counting backup hard links twice.

The owner inventory reads without a metadata write. Delete audit records name erased records, erased file-bearing records, and history counts. The old file-pointer count is removed.

Keys and encrypted run files

Each schema record key space has its own protected hash lookup. Alternate keys use separate key spaces.

Typed range rules preserve the required order inside encrypted run blocks. The order rule alone is not encryption.

Both run homes keep their native encrypted files during backup. Cloud object sizes do not select a different local storage format.

The account content key and plaintext file hash derive the file key and nonce. No file key is stored in the record marker. The file path instead comes from the schema and record key. An outer account storage envelope precedes run-block encryption. Optional file-entry compression, its settings, and its counters are removed; run-block compression remains separate.

Credentials and owner consent save together

One cloud-credentials.json file holds the service address, account access key, and optional owner connection. Connection setup verifies the account, source home, environment, and endpoint, then atomically replaces this file. Recovery credentials do not copy another home’s consent.

The separate cloud-sync settings, resume marker, and manual-connection file are removed. Credentials alone still start no backup. Automatic backup requires its own saved enablement policy; restore uses saved account access and a recovery phrase without a release switch.

Backup access and schema-service environment selection now share a protected-file reader. It requires a regular owner-only file with one link, a bounded size, and a nonempty account key. Symbolic links are refused.

Enrollment, payment, and recovery commands use the same credential format. Callers that already hold a checked file descriptor parse those checked bytes. Keys are cleared when their in-memory credential holder is dropped.

Invalid saved credentials block the account read. They do not stop daemon startup. The schema service then follows its other settings; explicit environment settings still override a valid saved address.

The account access key authorizes service requests. A recovery phrase supplies the separate encryption keys needed to open a backup.

New backup jobs declare recovery dependencies

A full snapshot explicitly names no earlier backup. A change backup names its base snapshot and previous change backup when different. The service can distinguish publication order from the older backups recovery actually needs.

Saved jobs retain their original begin request on retry. The current protocol requires an explicit dependency list and a nonempty provider list. Requests that omit them are refused. The dependency inspection command follows these links and verifies identities; it performs no cloud deletion. Restore and dependency inspection need no release switch.

PROD recovery passed without the release switch

The accepted-main CI operation creates a separate PROD source with 16 records and an 8 MiB file. Automatic backup publishes a snapshot, followed by changed records, one deletion, and a 64 KiB replacement file.

CI removes its generated source home before restoring. The snapshot and later accepted change chain recover into separate unused destinations. Exact keyed values and full file bytes pass across two clean restarts of each recovered home, with the release switch false.

Snapshot file hashes and native file closure are independently checked. For change recovery, the product verifies the authenticated log routes and chain; the operation checks recovered values and file bytes. This is evidence for these format 11 backups, not every backup or older format.

Verified PROD run and retained result. The run records its exact source and binary hashes. It uses no primary data and leaves existing backup policies unchanged.

Backup and restore remain separate

The owner can request a snapshot or enable an automatic policy after an account connection. Defaults check changes each minute and request a full snapshot daily.

A snapshot captures both run homes. Capture state and hard-linked file holds now live under disk-run/cloud-byte-v2, beside the original files. Node upload jobs remain under data/cloud-byte-backup-v2. Later accepted change backups retain complete ordered changes.

Both paths share one upload planner. Large pieces hold at most 64 MiB. Files below 64 KiB can share bundles of at most 8 MiB and 512 files.

The planner asks for byte ranges of at most 64 KiB. Snapshot and change-backup workers read those ranges and save each planned object. The planner checks file lengths and hashes without opening files or sending requests. A separate HTTPS client transfers the bytes under the node’s control.

Stopped-home backup checks that the daemon and owner socket are stopped, then uses the native run-home locks. The separate maintenance lock is removed. Stopped-home backup can leave automatic backup enabled. An unfinished job blocks it. A verified snapshot advances the enabled policy’s saved backup position.

One local restore module now handles download, file and record checks, and publication of the verified home. Restore requires a fresh destination, exact accepted state, complete change chain, saved account access, and the matching recovery phrase. The offline command and credential reader no longer require the release switch.

This release restores only format 11, through run-backup profile 9 and snapshot metadata version 7. Older profiles and unknown key families are refused. Account, schema, record, history-value, and required file-entry checks remain. Recovery now accepts only unscoped record and history key families. The removed conflict queue is no longer part of recovery. There are no shared-file counters to preserve or recount.

DEV recovery uses separate build and recovery jobs. DEV cleanup uses separate bounded passes. Each job has a ten-minute limit. PROD has a separate accepted-main workflow and dedicated account.

The older snapshot comparison and device identity preparation tools are removed. Local snapshots still support prepare, inspect, resume, and release without a cloud upload.

Status compares the observed positions of both local run homes with the automatic policy’s saved backup positions. Equal positions with no required snapshot give current coverage for that check.

New local writes make the backup behind. More than 300 seconds past the upload due time makes that delay stale. Missing positions leave coverage unknown.

A gap requires a new snapshot. A backup position ahead of the local position is a mismatch. A blocked job takes priority in the status line.

Status uses local saved facts; it does not read cloud objects again. A normal manual backup can leave the automatic position unchanged. The stopped-home command can advance it.

The new source enables ordinary authenticated restore. Installing that source is separate; this guide update does not upgrade any database or change its backup policy.

Stable publication requires a full CI qualification

The release workflow freezes the LastDB revision and app commits. It builds matched CLI and daemon packages for Apple silicon macOS and x86-64 Linux, then checks each native package’s durable operations and recovery.

Qualification installs the exact signed-catalog versions of Brain, LastSecrets, and Search into a fresh CI environment. It checks real save, read, delivery, and search operations. An earlier app-operation step can produce unsigned declarations for missing catalogs. Accepted main runs can then publish permitted entries through the separate CI signer. Qualification subsequently installs the signed catalog versions; it still refuses unsigned bootstrap-only evidence.

A publishing run requires at least 3,600 uninterrupted seconds, at least 121 healthy samples, and health-request latency at or below two seconds for 95% of samples. Writes and reads continue every 30 seconds. Clean restart and crash recovery checks follow. A PR preview runs briefly and cannot qualify.

Publication rechecks source gates, app signatures, retained artifacts, and build provenance. It exposes immutable prerelease assets for normal Homebrew PR checks. Only after that PR merges and its formula matches the qualified bytes does the release become stable.

The app publish command’s --prepare option validates the checkout and declared schemas, then writes an unsigned declaration. It loads no signing key and publishes nothing. This supports CI without handing it a publisher key.

CI signs permitted app compatibility entries

A separate publishing job accepts evidence from the same accepted main revision and CI run. It checks the retained artifact, GitHub provenance, fixed app commits, declared API, and search-notice format. It obtains a short-lived GitHub identity tied to the publication body, and asks a dedicated AWS KMS key to sign it. The private key is not exported.

New automatic publication starts at API 27 and covers Brain, LastSecrets, and Search on stable and next. Earlier catalogs retain their original publisher. Existing matching entries are reused after a separate registry authorization request; incompatible entries stop the publication. This source review does not establish that a live publication succeeded.

App compatibility publication precedes the hour-long stable qualification. A signature does not replace that qualification, the normal Homebrew PR gates, or install consent. PR previews cannot publish.

Unchanged vocabulary needs no new write

The schema service compares checked definitions with durable vocabulary. A vocabulary-only request with no new definitions updates its memory cache and returns without a storage write. New definitions and schemas still use the existing commit path. This avoids repeated writes and contention during startup.
