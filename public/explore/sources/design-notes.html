Source notes and release limits

Source review: 3 November 2026. Merged LastDB revision 84c18e7c.

Record-owned files, schema advice, and publishing checks. The guide describes 131 parts and 423 connections. This update covers 10 commits after the published revision. Completed reviews cover 823 commits after October 21.

App publishing and installation

Normal app installs read the stable or next channel’s public catalog for the node’s exact API version. Each catalog has a registry signature; each entry also has a publisher signature over the app version, Git commit, and interface declaration. A declared search-notice version must match exactly. The node build label is recorded but does not choose the entry.

The installer checks out the full listed Git commit and records it in an install receipt. This path does not use the old version-range preference or require a separate verifier result. Signatures establish who signed which bytes. They do not establish that an app works or limit its user permissions.

Publishing starts from a clean Git checkout and requires an explicit HTTPS registry address and developer account key. The publisher signing key can come from LastSecrets. The publish command records interface versions; it does not itself run a compatibility check.

The CLI keeps verified catalogs outside the database. A failed download can use a valid saved catalog. Lower sequence numbers, or different bytes with the same sequence, cannot replace it. At seven days old, a catalog produces a notice but remains usable. Installation still needs to fetch the app’s source commit.

Normal managed installs now prepare a separate version from the signed catalog, read its install instructions, and switch stable command links after checks. First installation and changed instructions require consent. A changed publisher key requires owner rotation. Inactive installs still prepare code and links but skip health and post-install commands.

On macOS, a managed install installs a minute-by-minute updater. Stable catalog fetches are limited to once an hour while health checks continue; next is checked each poll. Other hosts can invoke the upgrade command. An alternate app root does not install the background updater.

A rollback requires an eligible, healthy previous version. A rejected source commit stays held across automatic polls until a newer commit or explicit install consent. Rollback switches code and links, not database writes or arbitrary install-command effects. Status reports health without triggering rollback.

The former HostTrack and verifier-log release installer is removed. Local development installs retain separate manifest checks. The schema service’s release storage and verifier queue remain, but they do not drive normal catalog installation. This review does not establish live catalog or verifier state.

Apps declare typed schemas locally

The node builds and loads a direct app declaration without finding or registering it at the schema service. Every field must name a type. Shared schema resolution and publication remain separate service operations.

The File field type and shared-file pointer are removed. A file belongs to the record itself. Every ordinary declared field still needs a type; Any remains temporarily in this source revision.

Existing keys and field meanings remain protected. A declaration does not convert existing record values. Shared field definitions still do not share values between schemas.

Source: Local declaration · Required field types · Field type validation · Separate live resolver

One schema owns its records

A schema names fields, a primary key, and optional named alternate keys. Each schema owns its record values.

Canonical field reuse shares meaning and type. It does not connect records in different schemas.

One stored record holds fields, their write facts, metadata, an optional file marker, and any delete marker. The final encoded record, including the marker, must fit within 64 KiB.

Each record can own one file. Its marker describes name, media type, size, and plaintext hash; the bytes stay in the separate file home. Identical files on two records occupy separate entries.

Schema advice and app publishing

POST /v1/advice/schema is read-only. It compares a draft with the service’s canonical vocabulary and loaded schemas. It can report names, different meanings, missing types, classifications, and similar schemas. Similarity is a suggestion, not proof that two definitions are interchangeable.

App check and publish print optional advice on stderr. A request waits at most five seconds. A network failure skips the remaining schemas; an unusable reply skips that schema. Advice failure never blocks either command.

Publishing has separate mandatory checks before signing: the manifest must explicitly list its schemas and type each field. The command reads the running node and checks that every app-owned schema appears with the same identity. An empty list is allowed for an app with no owned schemas. This verifies the currently declared schema set, not arbitrary future app behavior.

Catalog feed is implemented but excluded by default

The optional feed verifies signed stable and next lists by API version, then fetches public GitHub manifests at their exact listed commits. It shares schema normalization with the node. Each app/commit is read once, with at most 20 new manifest reads per run. Private entries are skipped.

Definitions and their provenance live in a separate catalog_feed.json image with conditional S3 writes. Removal from a successfully updated list marks a definition unlisted; a missing or failed list keeps its prior verified state. Invalid manifests are recorded as skipped, transient failures can retry, and a rate limit stops manifest reads for that run.

The feed can separately offer new field names to vocabulary admission. Vocabulary writes precede the catalog-image write; they are not one shared transaction. The current advice implementation reads loaded schemas and vocabulary, not the separate feed image.

The Lambda’s catalog-feed build feature is off by default because the enabled package exceeded its 15 MiB limit. Running it also requires the configured schedule, its sentinel event, and SCHEMA_CATALOG_FEED. This source review does not establish that a deployment enabled those requirements.

Only format 9 homes

Every new home uses format 9. This release opens and restores only that format.

Each new run-home folder starts with owner-only permissions (0700). Creation does not repair permissions on an existing home.

Older homes, including format 8, need their matching program. The current program has no older-home reader or in-place conversion.

Format 9 replaces shared-file pointers and reference counts with a file path derived from the schema, scope, and record key. This format boundary prevents older bytes being read under the new rules.

Aggregate writes and signed imported field writes remain refused.

The old alternate-key change routes are removed. Changed keys need a separate schema and an explicit record copy.

A repeated schema declaration can add fields with unchanged keys and meanings. Existing records read added fields as absent.

Whole-record memory and reads

Full query replies return one metadata block per record, including its optional file marker. Values-only replies omit it. The marker contains no file key or storage path.

API 23 replaces the owner file routes with put-blob, fetch-blob, and delete-blob, all addressed by schema and primary key. It removes file-pointer values, blob-counter status, and the file-liveness route. Reference verification now covers the retention queue.

Source: Record conflict flags · Memory counts · API version · Schema declarations.

A read by key checks memory first. A disk fetch can keep one complete decoded record in the warm set.

Memory status now reports actual warm records and held records. Old counters that always stayed zero are removed.

The default warm limit is 256 MiB. It includes the decoded record and file marker. File bytes stay outside the warm set. Least recently used records leave first; a record held by a call stays.

A write publishes its record to memory only after the flush. Older read views and private writes use their own disk state.

A range page names one hash and fetches bounded key pages. Owner pages across a schema follow protected stored-key order.

A page can stop early after many deleted records. Even an empty page can return a next cursor and report more data. Send that cursor unchanged.

Owner cursors name stored positions. Offset, page size, and one extra record must fit within 8,192. Deleted keys also consume the read allowance.

A hash schema without a declared key field returns a protected hash on an owner page. That hash is not a mutation key.

An ascending owner sample without extra query work can stop early. Its reply reports more data and no exact total.

If the reply includes every found record after its offset, its cursor continues through an owner record page with the same fields, order, and database.

A shorter reply has no cursor, because that cursor could skip found records. Other sample forms fail at the read limit.

Source: Incomplete sample replies · Sample continuation rules

Each batch read uses one memory and disk revision. A later page call can observe later writes. Counts, conditions, and deep offsets can fail at the read limit.

One complete saved change

A native request saves records, alternate entries, file changes, history, and notices. File additions reach the file home first, record changes follow, and file removals come last. The two homes have separate disk commits. Memory publication and the ack wait for completion.

Ready requests can share a flush. There is no flush interval.

Each field keeps its own write order. Local metadata updates replace only supplied keys and preserve omitted keys.

An alternate entry belongs to the primary key it names. A departing record removes it only while that ownership still matches.

Repeated changes to one record must leave a final value within 64 KiB. A failed final size check refuses the request.

The older field-size setting remains in status, but no write path uses it. It does not raise the record cap.

Source: transaction/request.rs · write/record_effects.rs · record_value/meta.rs · alternate_keys/write.rs

Schema removal releases its personal records

CAUTION: A schema drop removes stored data. It first blocks new writes to the schema.

Schema removal deletes personal records, saved history, conflicts, and alternate entries in steps of at most 256 entries. Each removed record’s file path is deleted in the same native request.

The schema disappears after cleanup succeeds. If cleanup stops, the schema stays blocked. Repeat the drop to continue.

Database scopes use separate cleanup with a complete-change size limit. Received share copies stay separate. This is not a promise to erase every copy everywhere.

History, deletion, and files

Field history is off by default. An enabled policy saves the previous field value and write facts as a copy.

A history copy contains an earlier field value and its write facts. It omits record metadata and the record’s file. File replacement and deletion have no field-history recovery.

Delete keeps a marker against older writes. Purge also removes retained history and conflicts. A whole-record Purge refuses above 1,024 history entries.

The field history route is now /api/field-history. The older atom-history route is removed.

The owner can first remove field history in pages of at most 32 entries. The delete marker remains after Purge.

There are no shared-file reference counts or one-hour waiting worker. put-blob writes the record marker and file together. delete-blob removes the marker and file while keeping the record. Record deletion removes its covered file too.

Backup and restore derive the file path of each marked record. They require a live entry in the captured authenticated file home and stream its stored bytes through the run reader. This checks file presence and run-block integrity. fetch-blob separately decrypts the file and verifies its plaintext size and hash.

Atom counters, molecule cleanup, and old conflict caches are removed. Conflict expiry now removes the conflict and its queue entry in one saved batch.

Reference checks and offline recount now concern the retention queue. Blob counting, recount, waiting-queue status, and liveness explanation are removed.

Expiry can continue past an empty page of deleted range keys. It remembers a leading deleted stretch in memory and starts later passes after it.

A live write below that position clears it. Concurrent writes prevent an unsafe advance. Each hash starts from the beginning after 64 passes or restart.

A time-queue page makes at most 16 bounded reads. Conflict cleanup stops after 64 empty pages, retains its position, and pauses. Record file deletion uses no waiting queue.

Source: Expiry pages · Expiry progress · Record file lifetime · Conflict cleanup steps

The offline replay cutoff covers the whole home. It no longer requires the all-scopes option. It must be a positive time at or before now.

Source: Offline replay cutoff.

Compaction and physical file holds remain separate from logical deletion. Older cloud copies do not disappear because a local record is deleted.

Local share copies remain separate

An active share rule copies changed personal field data to each local share scope in the same request. Copies include the delete marker but omit the record’s file. Query exports also omit files and their markers; a caller must arrange any separate file transfer.

A read chooses the live local record first. Otherwise the first active received scope with a live record supplies the whole record.

A simple keyed export reads at most 256 records per page and continues past deleted keys. It still collects the complete export in memory.

Extra conditions, value order, or a query limit keep one read and can hit its read allowance.

Source: Keyed export pages

Active received data blocks alternate reads. Local share support does not enable automatic cloud delivery.

Device event capture and peer exchange are removed. Ordinary writes no longer create signed device events or new peer conflicts.

Existing conflict records remain readable and expire through the time queue. Older device snapshot maps and comparison tools are removed.

Source: records/received.rs · write/record_effects.rs

The old app estimates and their refresh routes are removed. The home report describes disk files separately from the schema record totals.

The owner inventory reads without a metadata write. Delete audit records name erased records, erased file-bearing records, and history counts. The old file-pointer count is removed.

Keys and encrypted run files

Each schema record key space has its own protected hash lookup. Alternate keys use separate key spaces.

Typed range rules preserve the required order inside encrypted run blocks. The order rule alone is not encryption.

Both run homes keep their native encrypted files during backup. Cloud object sizes do not select a different local storage format.

The account content key and plaintext file hash derive the file key and nonce. No file key is stored in the record marker. The file path instead comes from the schema and record key. An outer account storage envelope precedes run-block encryption. Optional file-entry compression, its settings, and its counters are removed; run-block compression remains separate.

Source: src/record_space.rs · field_key_codec/profile.rs · disk_pack/run_node.rs · record_store/record_files.rs

Saved account credentials have one reader

Backup access and schema-service environment selection now share a protected-file reader. It requires a regular owner-only file with one link, a bounded size, and a nonempty account key. Symbolic links are refused.

Enrollment, payment, and recovery commands use the same credential format. Callers that already hold a checked file descriptor parse those checked bytes. Keys are cleared when their in-memory credential holder is dropped.

Invalid saved credentials block the account read. They do not stop daemon startup. The schema service then follows its other settings; explicit environment settings still override a valid saved address.

The account access key authorizes service requests. A recovery phrase supplies the separate encryption keys needed to open a backup.

Source: Credential format and file checks · Schema-service selection · Recovery keys

New backup jobs declare recovery dependencies

A full snapshot explicitly names no earlier backup. A change backup names its base snapshot and previous change backup when different. The service can distinguish publication order from the older backups recovery actually needs.

Saved jobs retain their original begin request on retry. Older requests that omit the dependency list still protect their predecessor chain conservatively. The dependency inspection command follows these links and verifies identities; it performs no cloud deletion. Restore still needs its release switch.

Backup and restore remain separate

The owner can request a snapshot or enable an automatic policy after an account connection. Defaults check changes each minute and request a full snapshot daily.

A snapshot captures both run homes. Later accepted change backups retain complete ordered changes.

Both paths share one upload planner. Large pieces hold at most 64 MiB. Files below 64 KiB can share bundles of at most 8 MiB and 512 files.

The planner asks for byte ranges of at most 64 KiB. Snapshot and change-backup workers read those ranges and save each planned object. The planner checks file lengths and hashes without opening files or sending requests. A separate HTTPS client transfers the bytes under the node’s control.

Stopped-home backup can leave automatic backup enabled. An unfinished job blocks it. A verified snapshot advances the enabled policy’s saved backup position.

One local restore module now handles download, file and record checks, and publication of the verified home. Restore still needs a fresh destination, exact accepted state, complete change chain, account access, and the release switch. Consolidation does not enable it.

This release restores only format 9, through backup profile 7. Older profiles and unknown key families are refused. The saved retention state must pass validation; restore does not repair it. There are no blob counters to preserve or recount.

DEV recovery uses separate build and recovery jobs. DEV cleanup uses separate bounded passes. Each job has a ten-minute limit. None proves PROD recovery.

The older snapshot comparison and device identity preparation tools are removed. Local snapshots still support prepare, inspect, resume, and release without a cloud upload.

Status compares the observed positions of both local run homes with the automatic policy’s saved backup positions. Equal positions with no required snapshot give current coverage for that check.

New local writes make the backup behind. More than 300 seconds past the upload due time makes that delay stale. Missing positions leave coverage unknown.

A gap requires a new snapshot. A backup position ahead of the local position is a mismatch. A blocked job takes priority in the status line.

Status uses local saved facts; it does not read cloud objects again. A normal manual backup can leave the automatic position unchanged. The stopped-home command can advance it.

This review does not enable restore, alter the primary, or change its automatic backup policy.
