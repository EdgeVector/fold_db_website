Cloud source and future design

Source review: 25 October 2026. Earlier shared-data design: 6 October 2026.

Native backup code exists. Its release flag stays off by default.New backup work also needs account readiness. Automatic backup requires separate consent. This review does not establish a deployed service or a successful recovery.

One data model across the layers

Memory serves current logical records. A native write saves a complete disk snapshot before memory publication and the ack.

Cloud backup is a separate operation. A local ack does not confirm a cloud copy.

The layers preserve the same data relationships. Their files and completion times differ.

The native backup path in current code

  1. Capture one exact disk snapshot before any backup file upload. Retain its required files while local writes continue.
  2. Check every required external file. Transfer its protected bytes and obtain verified service receipts.
  3. Publish an encrypted manifest that lists the exact files and receipts. Save the accepted result in the backup job.
  4. Release the source hold only after a confirmed terminal result permits it.

The saved job can resume the same source after a process exit. It must not silently choose a newer disk state.

The native path copies an exact snapshot. It does not add the later mutation log described in the older cloud proposal.

Automatic backup needs explicit consent

This controller uses the original backup path. The new V2 path remains manual.

The release flag, account permission, and saved automatic consent must all permit the work. Manual backup does not require automatic consent.

The controller checks whether a confirmed backup covers the saved data. It can start the first backup without another write.

After confirmed coverage, unchanged data and compaction alone need no new upload.

Compatible unfinished work resumes the same saved job. Temporary failures can retry. Identity, permission, quota, and source problems need attention.

Auto Off blocks future automatic work. It does not close a job already admitted. Close also turns automatic consent off.

A checked restore to a fresh destination

  1. Select one accepted backup. Save its exact identity before file requests.
  2. Check the manifest and each required file’s identity, length, and protected content.
  3. Check the complete snapshot, atoms, file references, and saved-state boundary. Read each atom and its encryption key from that same selected state.
  4. Publish the verified destination. Keep cloud sync and automatic backup off.

Restore refuses an existing destination. The walkthrough in the guide describes source behavior; it does not perform a recovery.

Restored account access is a separate DEV action

The reconnect action checks the completed restore receipt and existing account identity. The restored home must be inactive.

It obtains access to the same account without a new identity or a change to recovered data. It refuses primary and archive homes.

The saved credentials remain paused. Reconnect does not enable cloud sync or automatic backup.

Large files travel separately

An atom can reference a file blob. New file keys depend on the private account key and original file hash.

The protected atom carries the file key. The file address identifies the encrypted bytes. Supported older files keep their original keys.

Backup needs exact coverage for each main file, thumbnail, and poster. Bytes already inside packed files need no second copy.

External bytes need a verified source and a backup-owned copy. A local file reference alone does not establish a complete backup.

Manual V2 byte backup now has a complete path

A manual job retains one exact saved state. It checks transfer receipts before it publishes an accepted backup.

Small files share transfer packs. Large files can use several byte pieces. An encrypted file list records their exact positions.

Native file bytes keep their existing protection. The transfer adds no whole-file encryption. Structural metadata can remain readable.

V2 currently requires external file dependencies to have coverage inside the native file set. Unsupported dependencies refuse.

Resume keeps the exact saved request and capture. Uncertain remote work retains its file hold until a confirmed result permits release.

The V2 release switch stays off by default. Account permission is separate. Automatic backup does not start V2 jobs.

Backup without another node

The standalone command uses existing native files. It creates no second daemon or database writer.

Progress stays in a separate private directory. A durable file hold is the permitted source change.

A separate credentials-only setup can register the same account for an explicit environment. Credentials remain paused; registration alone does not enable backup.

Restore counters before normal use

Both restore paths select an exact accepted backup and refuse an existing destination.

Normal writes and cleanup remain blocked until complete checks match records, references, counters, and files.

An interrupted record restore keeps its marker after restart. Counter checks do not silently repair a mismatch.

Encryption and disk format now have separate checks

Format 6 retains atom content encryption. Only local file blob records receive an extra storage encryption layer.

Tips, counters, and schema definitions can remain readable. A small protected record checks the account key before use.

Startup refuses older formats. A separate inactive transfer target can convert supported format 4 or 5 records.

The converter refuses format 5 with a replay cutoff. It needs a converter that preserves that cutoff.

The new private-key range implementation remains separate from active storage. Its ordered terms reveal order, equality, length, and other information.

An optional larger-key format supports future conversion targets. Existing homes do not select it automatically.

Future design: a shared database

The design gives authorized members access to shared encrypted data. A copied schema can reference the same molecules and atoms.

Members need the correct keys and access grants. A schema copy alone does not deliver files or grant another device access.

Simultaneous cloud writers need a defined frontier, conflict rules, and retention rules. The guide treats this behavior as future design.

Future design: a guaranteed write

A proposed guaranteed write requires a cloud grant before success. Current local writes confirm disk completion without that grant.

The exact cloud acceptance and recovery contract needs implementation and proof. The guide does not present it as an available write mode.

Services around the database

  • The schema service supplies definitive schema definitions.
  • Cloud access authorizes remote delivery.
  • Future design: protected messages carry invitations, key grants, and share notices.
  • Future design: a shared file service holds encrypted file bytes for authorized members.
  • The app registry describes releases and their LastDB compatibility.

Each guide part states whether its explanation describes reviewed source or future design.

Questions that remain in the design

  • How does one atom use keys when it belongs to databases with different encryption keys?
  • Which range, recipient, and file metadata can the cloud see?
  • Which frontier and retention rules permit simultaneous writers?
  • What permits cloud file removal after a member leaves or a device stays offline?
  • What result does a read return when a key is absent locally and the cloud is unavailable?
