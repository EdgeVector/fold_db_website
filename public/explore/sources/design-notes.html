Source notes and release limits

Source review: 6 November 2026. Merged LastDB revision ceb3630a.

API 30: whole-record reads and conditional writes; the unused SDK org locator is removed. API 29 requests remain supported. The guide describes 137 parts and 487 connections. This publication includes 19 commits after f75edbcc. Completed reviews cover 955 commits after October 21.

App publishing and installation

Normal app installs read the stable or next channel’s public catalog for the node’s exact API version. Each catalog has a registry signature; each entry also has a publisher signature over the app version, Git commit, and interface declaration. A declared search-notice version must match exactly. The node build label is recorded but does not choose the entry.

The installer checks out the full listed Git commit and records it in an install receipt. This path does not use the old version-range preference or require a separate verifier result. Signatures establish who signed which bytes. They do not establish that an app works or limit its user permissions.

Publishing starts from a clean Git checkout and requires an explicit HTTPS registry address and developer account key. The CLI reads its developer signing key from a file and rejects LastSecrets locators. Its embedded LastSecrets key handling has been removed; external credential handling is separate. The publish command records interface versions; it does not itself run a compatibility check.

The CLI keeps verified catalogs outside the database. A failed download can use a valid saved catalog. Lower sequence numbers, or different bytes with the same sequence, cannot replace it. At seven days old, a catalog produces a notice but remains usable. Installation still needs to fetch the app’s source commit.

Normal managed installs now prepare a separate version from the signed catalog, read its install instructions, and switch stable command links after checks. First installation and changed instructions require consent. Brain, LastSecrets, and Search can switch between explicitly trusted owner and CI publisher keys at the expected PROD catalog and GitHub source. Both old and new installs must have pinned trust. Other publisher changes require owner rotation. Inactive installs still prepare code and links but skip health and post-install commands.

On macOS, a managed install installs a minute-by-minute updater. Stable catalog fetches are limited to once an hour while health checks continue; next is checked each poll. Other hosts can invoke the upgrade command. An alternate app root does not install the background updater.

A rollback requires an eligible, healthy previous version. A rejected source commit stays held across automatic polls until a newer commit or explicit install consent. Rollback switches code and links, not database writes or arbitrary install-command effects. Status reports health without triggering rollback.

The former HostTrack, verifier-log, and schema-service catalog installers are removed. Signed catalog lookup uses lastdb app list APP; --catalog-entry returns its declaration. The app run, promote, resolve, and info commands are removed. Run installed apps through their command links.

Apps declare typed schemas locally

The node builds and loads a direct app declaration without finding or registering it at the schema service. Every field must name a type. Shared schema resolution and publication remain separate service operations.

The File field type and shared-file pointer are removed. A file belongs to the record itself. Every ordinary declared field still needs a type; Any remains temporarily in this source revision.

Existing keys and field meanings remain protected. A declaration does not convert existing record values. Shared field definitions still do not share values between schemas.

Source: Local declaration · Required field types · Field type validation · Separate live resolver

One schema owns its records

A schema names fields, a primary key, and optional named alternate keys. Each schema owns its record values.

Canonical field reuse shares meaning and type. It does not connect records in different schemas.

One stored record holds its primary key, named alternate addresses, fields, one record stamp, metadata, and an optional file marker. Deletion removes the live value and saves its stamp in a separate applied-delete entry. A file marker also has an immutable version identified by a writer stream and sequence. The encoded record must fit within 64 KiB, including addresses and the file marker. Empty fields do not make a live record absent.

Each record can own one file. Its marker describes name, media type, size, and plaintext hash; the bytes stay in the separate file home. Identical files on two records occupy separate entries.

Schema advice and app publishing

POST /v1/advice/schema is read-only. It compares a draft with the service’s canonical vocabulary and loaded schemas. It can report names, different meanings, missing types, classifications, and similar schemas. Similarity is a suggestion, not proof that two definitions are interchangeable.

App check and publish print optional advice on stderr. A request waits at most five seconds. A network failure skips the remaining schemas; an unusable reply skips that schema. Advice failure never blocks either command.

Publishing has separate mandatory checks before signing: the manifest must explicitly list its schemas and type each field. The command reads the running node and checks that every app-owned schema appears with the same identity. An empty list is allowed for an app with no owned schemas. This verifies the currently declared schema set, not arbitrary future app behavior.

Retired schema-service paths

The catalog feed, its internal route, and its separate S3 image writer are removed. Advice still reads the loaded schemas and vocabulary. The legacy compositional rewrite of incoming schemas is also removed; native component-cover advice remains a separate path. Local typed declarations and pinned replay definitions remain.

The embedding runtime comes from a Lambda layer

The Lambda embedding build loads ONNX Runtime from a shared library supplied alongside its model files. It no longer links that runtime into the main function package. This reduces the function package’s size.

ORT_DYLIB_PATH must name an existing runtime library. Model files come from SCHEMA_FASTEMBED_MODEL_DIR, FASTEMBED_CACHE_DIR, or the default /opt/fastembed_cache location. This path does not download the runtime or model during a request. Missing runtime configuration causes embedding initialization to fail; checking that the file exists does not establish that the library is compatible.

The embedding model remains all-MiniLM-L6-v2. Unused built-in model choices are removed from the vendored library. The service already selected this model, so its similarity model is unchanged. Live layer contents and service deployment are outside this source review.

One storage format writer for a home

At startup, one component connects records, schemas, clocks, change notices, and lookup keys to the same home and key context. Ordinary database components receive readers and specific write operations. They no longer hold raw storage writers or open arbitrary storage areas. Physical disk storage and authenticated backup replay keep their own entry points.

Reads and writes check the version-3 record structure: independently stored addresses, one record stamp, and a consistent file marker and version. Deleted values cannot be encoded as live records. Each complete encoded record must fit within 64 KiB. The API rejects repeated primary keys in one mutation batch.

The file writer keeps each encrypted payload and marker together. A plain replacement preserves the existing attachment without reading or rewriting its bytes. A mutate request can instead supply a file source or explicit file: null. The writer checks origin, marker, size, envelope, and nonce. Portable replay and reads also verify the encryption tag, plaintext size, and hash.

The alternate-entry writer binds each saved location to an explicit alternate address and primary target. Its key includes a digest of the primary address. Several records can share one alternate address without replacing each other’s pointers. Both key spaces keep their own range rules. Reads validate membership against stored addresses; continuation carries a primary-record tie-breaker.

Existing generated-home operations now supply complete conditional records. The file recovery operation performs sequential replacements, carrying the exact marker forward. A lost write reply requires a fresh read; the write path no longer looks up a retry receipt. These source changes are not a new PROD recovery result.

The lookup-key writer creates encrypted bundles and their range rules. New key identities are limited to 1,024 bytes, saved metadata and wrap entries to 16 KiB, and the nested bundle and its encrypted form to 4 KiB each. Each primary key space and named alternate key has one bundle with a single hash-protection key. Payload fields have none. Older bundles can still be read; their unused content and range keys are ignored. Stored records and ranges remain protected by run-block encryption.

Restore validates the primary and alternate bundles against their declared range rules, grouped into batches of at most 128 keys. It requires no payload-field bundles. The new comparison identity also invalidates older page cursors: restart those reads from their first page.

Retention sharing follows explicit alias links and earlier schema versions. Reusing a canonical field definition alone does not connect two schemas for expiry.

Source: Bundle ownership · Single-key encoding · Restore bundle checks · Cursor comparison identity · Retention sharing

Schema release, record-file deletion, erase audits, and the replay cutoff use format-owned writers. Field history and all its policy, queue, read, restore, and purge paths are removed. These boundaries do not audit every key at startup. The 256 MiB warm limit and save-before-ack rule remain.

Only format 14 homes

Every new home uses format 14. This release opens and restores only that format.

Each new run-home folder starts with owner-only permissions (0700). Creation does not repair permissions on an existing home.

Older homes, including formats 12 and 13, need their matching program. The current program has no older-home reader or in-place conversion.

Stable request IDs bind the complete intended mutation and expected revision. Author signatures additionally bind the allocated record clock. This does not restore device exchange or per-field merge.

The old alternate-key change routes are removed. Changed keys need a separate schema and an explicit record copy.

Explicit shared operations and recovery

An enrolled shared database has explicit DEV commands under lastdb admin shared. The writer commands use a stopped non-primary home and saved DEV connection. They install exact schemas, bind a writer, send changes, and receive peer changes. Publication uses the running node’s snapshot command. Member enrollment and automatic delivery remain absent.

A bound shared write saves the complete outgoing mutation with its record, file changes, alternate entries, and writer position. Push freezes the exact next batch before transfer. It uploads and verifies all named file versions and the encrypted log before append. Only an exact accepted receipt advances the local upload position. Uncertain acceptance leaves the saved batch available for reconciliation.

Explicit DEV pull verifies retained peer ranges and saves them in a durable inbox. Missing prefixes wait; overlapping or substituted ranges are rejected. Winning records, exact files, alternate entries, applied progress, and removal of completed inbox ranges commit together. A peer behind the retained cloud prefix needs a newer checkpoint. Pull considers every registered peer, starting after the last applied peer. That choice is saved with the applied range, so rotation survives restart.

The dedicated shared layout separates data before snapshot creation. disk-run holds shared records and definitions; disk-cas holds their files. disk-private holds device-only records and files, local author state, outgoing work, inbox state, and bookkeeping. Creation declares 1–64 shared aliases. Active peers cannot grow that scope; staged restore can add verified tail schemas.

A short write barrier captures accepted writer positions and durable file holds together. The publisher hashes the held original files and uploads them unchanged: record data and file lists to R2, record-file data to B2, and the encrypted manifest to R2. No filtered export is built. Publication saves its exact intent. Retry reopens the same hold; submitted work reconciles its receipt before release.

restore-shared now connects the owner transport and native staged writer. It requires a saved connection, recovery phrase, and a registered device’s separate signing key. The command accepts an explicit DEV or PROD environment, but the verified shared recovery result is DEV only. It checks the selected snapshot and every captured tail, exact schemas, file bytes, and native closure before activating an unused destination. It saves a fresh local stream and does not copy device credentials. Completed activation can resume from its saved workspace.

The inbox allows at most four ranges per peer and applies one complete range at a time. A planning window permits at most 64 ranges and 16 MiB; staged restore applies at most 128 entries or 4 MiB per batch. Shared binding admits 1–64 exact schemas. Protocol views permit at most 1,024 writers. These bounds do not promise end-to-end recovery capacity.

Bound shared schemas refuse existing expiry policies and uncoordinated schema removal. Local file versions remain only while a live record or pending outgoing mutation needs them.

A snapshot command for the running DEV node

lastdb admin shared snapshot sends pending changes, holds and publishes the original encrypted shared files, then sends changes through a saved target. Writes continue during upload. Its receipt reports the snapshot, uploaded position, and R2/B2 file counts.

The snapshot command requires a dedicated shared home, explicit non-primary path, saved DEV connection, enrolled device key, and private absolute workspace. It uses the owner socket. Only one snapshot runs at a time. Retry the same workspace after interruption. Ordinary Backup V2 refuses this dedicated layout; it remains the separate path for ordinary homes.

Completed local logs and obsolete file versions are released

A matching cloud receipt advances the uploaded head and removes completed local mutations through the lesser of uploaded and applied progress. In the same native commit it clears their pending file references. Each exact file version tracks live-record use and its last pending local sequence. Only a version with neither use is removed. A peer replacement cannot discard bytes that an older local mutation still needs to upload.

New homes start with this reference tracking ready. Older homes wait for local uploads to catch up, then rebuild it in saved phases over logs, records, and files. Idle DEV push and pull advance at most 64 steps per invocation, checking a two-second budget between steps. Work resumes from its saved phase. Physical run files still follow compaction and hold rules; cloud objects have their own lifetime.

Object reservation and completion retry the same request on RetryLater or OutcomeUnknown, with six bounded delays from 25 to 800 milliseconds and the operation deadline. The provider byte upload stays outside this retry loop.

Shared disk commits and private recovery

A shared write touching several homes saves an encrypted recovery journal before committing file, record, and private changes. Reopen finishes an incomplete journal before normal reads and writes. Memory publication and success wait for the complete disk change. Read budgets, compaction, and explicit cleanup include the private root. Its encryption key uses a separate derivation label.

Shared delete-marker cleanup now runs during DEV pull

After an applied or idle peer step, explicit DEV pull attempts one cleanup batch. A step that needs a newer checkpoint skips it. The cloud writer directory must match the locally admitted participants. The cutoff is the earliest mutation timestamp at this writer’s confirmed cloud-upload position and each peer’s locally applied position. It uses mutation timestamps, not the time of the network transfer.

A missing upload receipt, peer head, or applied timestamp holds cleanup. A peer position behind its retained cloud prefix or beyond its accepted head also holds it. The cleanup reads at most 32 age entries, rechecks each saved deletion stamp, and removes only matching stamps strictly older than the cutoff. It saves the reclaimed timestamp in the same commit.

Later replay rejects history at or before that saved boundary; newly admitted peers must also start after it. Shared snapshots preserve the boundary for recovery. This is a bounded part of explicit DEV catch-up, not a background cleanup job, a retained-file cleanup, or new PROD recovery evidence.

Whole-record memory and reads

API 30 retains API 29’s whole-record reply: every stored field, the primary key, all alternate addresses and the revision. A full reply also includes metadata. An empty live record still appears. To show just a title, the app selects it from the returned record.

{"schema_name":"PhotoById","filter":{"HashKey":"photo-42"}}

A query rejects the old fields and secondary_concurrency options. Field conditions and sorting work on records already loaded for the chosen keys. Unknown condition and sort fields are refused. The owner’s export can still select fields when it builds a package from those records.

The owner file routes remain put-blob, fetch-blob, and delete-blob. The CLI now exposes file writes through lastdb mutate and reads through lastdb get --hydrate. A request wrapper supplies a complete mutation and either a file source path or file: null. Raw upload metadata precedes the bytes with an explicit length; the server still accepts the earlier header form.

Source: Query reply shape · Field conditions · Export selection · Memory counts · API version · Schema declarations.

A read by key checks memory first. A disk fetch can keep one complete decoded record in the warm set.

Memory status now reports actual warm records and held records. Old counters that always stayed zero are removed.

The default warm limit is 256 MiB. It includes the decoded record and file marker. File bytes stay outside the warm set. Least recently used records leave first; a record held by a call stays.

A write publishes its record to memory only after the flush. Older read views and private writes use their own disk state.

A range page names one hash and fetches bounded key pages. Owner pages across a schema follow protected stored-key order.

A page can stop early after many deleted records. Even an empty page can return a next cursor and report more data. Send that cursor unchanged.

Owner cursors name stored positions. Offset, page size, and one extra record must fit within 8,192. Deleted keys also consume the read allowance.

Owner pages recover the API key from the stored record, even when no payload field contains it. They no longer substitute a protected hash for such a record’s mutation key.

An ascending owner sample without extra query work can stop early. Its reply reports more data and no exact total.

If the reply includes every found record after its offset, its cursor continues through an owner record page in the same order.

A shorter reply has no cursor, because that cursor could skip found records. Other sample forms fail at the read limit.

Each batch read uses one memory and disk revision. A later page call can observe later writes. Counts, conditions, and deep offsets can fail at the read limit.

Explicit addresses and complete writes

Local schemas require record_keys: a primary definition plus up to 16 named alternates. Each definition uses hash or hash_range, with its own range type. Addresses are independent of payload fields. Primary keys cannot be absent; optional alternates can declare allow_absent. Key definitions cannot change in place.

Apps construct compound text ranges themselves. LastDB no longer joins field parts, pads values, or reverses time. Shared alternate coordinates are valid. Return the complete query cursor so every primary record at that address can be visited.

This native JSON creates a record for a schema with a primary hash and a by_album hash-and-range declaration. A replacement uses the full desired record, mutation_type replace, and expected type revision with the actual token from a complete read.

{
  "type": "mutation",
  "mutation_id": "9d8f79c6-b779-4a48-a228-8425cc77e142",
  "schema": "PhotoById",
  "key_value": {"hash": "photo-42"},
  "alternates": {"by_album": {"hash": "coast", "range": "photo-42"}},
  "record": {"title": "Morning light", "album": "coast"},
  "mutation_type": "create",
  "expected": {"type": "absent"}
}

SDK 0.7 requires API 29. The SDK does not read or merge old data before a write. The CLI accepts the same complete mutation through lastdb mutate --request-file. The node assigns the write ID and returns it with the new record revision.

Hash-only retention uses the record’s write time. Dated String ranges use the timestamp in the explicit range. The expiry worker batches reads of revisions and alternate addresses before conditional deletes.

One complete saved change

A native request saves records, alternate entries, file changes and notices. File additions reach the file home first, record changes follow, and file removals come last. The two homes have separate disk commits. Memory publication and the ack wait for completion.

Ready requests can share a flush. There is no flush interval.

One stamp and one opaque 64-hex-character revision identify the entire record. The stamp contains milliseconds, a source-stream UUID, and a sequence. Local writer progress commits with the record; restart cannot reuse an accepted position. Create requires expected absence. Replace, Delete, and Purge require the current record revision. A stale revision returns a conflict and publishes none of the request.

Each mutation supplies every declared alternate name. An explicit null is allowed only for allow_absent declarations. The format writer derives pointer changes from the old and new explicit addresses in the same request. The database does not derive them from payload fields.

A replacement supplies all desired fields, metadata, and alternate addresses. Omitted fields and metadata disappear. An omitted file change keeps the current attachment; explicit file: null removes it. The same primary key cannot occur twice in one API batch. Every record and condition must pass before publication.

The older field-size setting remains in status, but no write path uses it. It does not raise the record cap.

Schema removal releases its records

CAUTION: A schema drop removes stored data. It first blocks new writes to the schema.

Schema removal deletes records, applied-delete entries, and alternate entries in steps of at most 256 entries. Record-owned files are released through their reference tracking. Separate bounded batches clear age entries, latest-age links, and observed hashes. Tracking writes refuse blocked or removed schema owners.

The owner can inspect observed expiry hashes with the schema-retention route’s partitions action. Pages contain at most 256 hashes; an empty page may still have a continuation. A cursor belongs to the selected retention anchor. The expiry worker follows every page before using the complete hash list.

The schema disappears after cleanup succeeds. An unreadable record stops cleanup instead of being skipped. If cleanup stops, the schema stays blocked. Repeat the drop to continue.

There are no org or received-data scopes in this format. Old backups and physical file holds can still retain earlier bytes; schema removal does not erase every copy everywhere.

Deletion and record files

A schema may declare file_required: true. Every live record must then retain a file; deletion can still remove the record. The flag belongs to the schema identity and cannot change in place.

Hydration fetches the exact returned record revision, verifies file size and SHA-256, and publishes to a new output path without overwriting an existing file. A concurrent replacement refuses the fetch instead of returning mismatched bytes.

Source: Exact-revision hydration · Raw file input · Required-file enforcement · Schema identity

Field history is removed. There are no saved field-value copies, field policies, expiry queues, or field-history read and restore commands. Format 14 refuses the retired key families.

Cloud restore remains a whole-home recovery operation into a fresh destination. It is not an old-value query or an in-place field undo.

Delete requires a live matching revision and removes the whole record. Purge also removes the current record and can target a matching saved deletion revision. Both retain a separate applied-delete stamp. A fresh delete of an absent record conflicts. There is no field-history cleanup or history-entry cap.

A plain record replacement preserves its attachment. A mutate request with a file source replaces it; file: null removes it. The full fields, metadata, and alternate addresses must still be supplied. File references retain bytes needed by a live record or pending local mutation. Matching upload receipts release completed mutations and obsolete versions together. Ordinary unshared replacements can release the old version immediately.

Backup and restore derive the file path of each marked record. They require a live entry in the captured authenticated file home and stream its stored bytes through the run reader. This checks file presence and run-block integrity. fetch-blob separately decrypts the file and verifies its plaintext size and hash.

Conflicting requests write nothing; the caller must reread and recompute the complete replacement. Saved losing-write conflicts and field history are removed.

The offline operation is now lastdb admin storage replay-cutoff. It raises the replay cutoff on a cleanly stopped home; it does not repair a file counter or a history queue.

Expiry can continue past an empty page of deleted range keys. It remembers a leading deleted stretch in memory and starts later passes after it.

A live write below that position clears it. Concurrent writes prevent an unsafe advance. Each hash starts from the beginning after 64 passes or restart.

Local export remains; local share copies are removed

The current format retains one local record space. It has no org database catalog, share rules, sent copies, or received subscriptions. Reads no longer combine local records with received records. Named alternate reads no longer have a received-data restriction.

The owner can still export selected field values by key in a signed, encrypted package for a recipient. Export omits record files and their markers. It uploads nothing and does not install received records.

A simple keyed export reads at most 256 records per page and continues past empty pages. The complete export still accumulates in memory. Extra query work can hit the read allowance.

Explicit shared-writer operations now work with an already enrolled DEV database. Recipient enrollment and automatic multi-device delivery remain separate unfinished work. Device exchange and saved conflict records remain removed.

Keys and encrypted run files

Each schema record key space has its own protected hash lookup. Alternate keys use separate key spaces.

Typed range rules preserve the required order inside encrypted run blocks. The order rule alone is not encryption.

Both run homes keep their native encrypted files during backup. Cloud object sizes do not select a different local storage format.

The account content key and plaintext file hash derive the file key and nonce. No file key is stored in the record marker. The file path comes from the schema and record key plus the immutable file version. An outer account storage envelope precedes run-block encryption. Optional file-entry compression, its settings, and its counters are removed; run-block compression remains separate.

Credentials and owner consent save together

One cloud-credentials.json file holds the service address, account access key, and optional owner connection. Connection setup verifies the account, source home, environment, and endpoint, then atomically replaces this file. Recovery credentials do not copy another home’s consent.

The separate cloud-sync settings, resume marker, and manual-connection file are removed. Credentials alone still start no backup. Automatic backup requires its own saved enablement policy; restore uses saved account access and a recovery phrase without a release switch.

Backup access and schema-service environment selection now share a protected-file reader. It requires a regular owner-only file with one link, a bounded size, and a nonempty account key. Symbolic links are refused.

Enrollment, payment, and recovery commands use the same credential format. Callers that already hold a checked file descriptor parse those checked bytes. Keys are cleared when their in-memory credential holder is dropped.

Backup and restore remain separate

The owner can request a snapshot or enable an automatic policy after an account connection. Defaults check changes each minute and request a full snapshot daily.

A snapshot captures both run homes. Capture state and hard-linked file holds now live under disk-run/cloud-byte-v2, beside the original files. Node upload jobs remain under data/cloud-byte-backup-v2. Later accepted change backups retain complete ordered changes.

Both paths share one upload planner. Large pieces hold at most 64 MiB. Files below 64 KiB can share bundles of at most 8 MiB and 512 files.

The planner asks for byte ranges of at most 64 KiB. Snapshot and change-backup workers read those ranges and save each planned object. The planner checks file lengths and hashes without opening files or sending requests. A separate HTTPS client transfers the bytes under the node’s control.

Stable publication requires a full CI qualification

The release workflow freezes the LastDB revision and app commits. It builds matched CLI and daemon packages for Apple silicon macOS and x86-64 Linux, then checks each native package’s durable operations and recovery.

Qualification installs the exact signed-catalog versions of Brain, LastSecrets, and Search into a fresh CI environment. It checks real save, read, delivery, and search operations. An earlier app-operation step can produce unsigned declarations for missing catalogs. Accepted main runs can then publish permitted entries through the separate CI signer. Qualification subsequently installs the signed catalog versions; it still refuses unsigned bootstrap-only evidence.

A publishing run requires at least 3,600 uninterrupted seconds, at least 121 healthy samples, and health-request latency at or below two seconds for 95% of samples. Writes and reads continue every 30 seconds. Clean restart and crash recovery checks follow. A PR preview runs briefly and cannot qualify.

Publication rechecks source gates, app signatures, retained artifacts, and build provenance. It exposes immutable prerelease assets for normal Homebrew PR checks. Only after that PR merges and its formula matches the qualified bytes does the release become stable.

The app publish command’s --prepare option validates the checkout and declared schemas, then writes an unsigned declaration. It loads no signing key and publishes nothing. This supports CI without handing it a publisher key.
