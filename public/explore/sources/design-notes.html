Cloud source and future design

Source review: 23 October 2026. Earlier shared-data design: 6 October 2026.

Native backup code exists. Its release flag stays off by default.New backup work also needs account readiness. This review does not establish a deployed backup service or a successful recovery.

One data model across the layers

Memory serves current logical records. A native write saves a complete disk snapshot before memory publication and the ack.

Cloud backup is a separate operation. A local ack does not confirm a cloud copy.

The layers preserve the same data relationships. Their files and completion times differ.

The native backup path in current code

  1. Capture one exact disk snapshot before any backup file upload. Retain its required files while local writes continue.
  2. Check every required external file. Transfer its protected bytes and obtain verified service receipts.
  3. Publish an encrypted manifest that lists the exact files and receipts. Save the accepted result in the backup job.
  4. Release the source hold only after a confirmed terminal result permits it.

The saved job can resume the same source after a process exit. It must not silently choose a newer disk state.

The native path copies an exact snapshot. It does not add the later mutation log described in the older cloud proposal.

A checked restore to a fresh destination

  1. Select one accepted backup. Save its exact identity before file requests.
  2. Check the manifest and each required file’s identity, length, and protected content.
  3. Check the complete snapshot, atoms, file references, and saved-state boundary.
  4. Publish the verified destination. Keep cloud sync off.

Restore refuses an existing destination. The walkthrough in the guide describes source behavior; it does not perform a recovery.

Large files travel separately

An atom can reference a file blob. The file content uses its own encryption key.

The atom carries the file reference and the protected key material. A small field read does not require the large file bytes.

Backup needs exact coverage for each main file, thumbnail, and poster. Bytes already inside packed files need no second copy.

External bytes need a verified source and a backup-owned copy. A local file reference alone does not establish a complete backup.

Future design: a shared database

The design gives authorized members access to shared encrypted data. A copied schema can reference the same molecules and atoms.

Members need the correct keys and access grants. A schema copy alone does not deliver files or grant another device access.

Simultaneous cloud writers need a defined frontier, conflict rules, and retention rules. The guide treats this behavior as future design.

Future design: a guaranteed write

A proposed guaranteed write requires a cloud grant before success. Current local writes confirm disk completion without that grant.

The exact cloud acceptance and recovery contract needs implementation and proof. The guide does not present it as an available write mode.

Services around the database

  • The schema service supplies definitive schema definitions.
  • Cloud access authorizes remote delivery.
  • Future design: protected messages carry invitations, key grants, and share notices.
  • Future design: a shared file service holds encrypted file bytes for authorized members.
  • The app registry describes releases and their LastDB compatibility.

Each guide part states whether its explanation describes reviewed source or future design.

Questions that remain in the design

  • How does one atom use keys when it belongs to databases with different encryption keys?
  • Which range, recipient, and file metadata can the cloud see?
  • Which frontier and retention rules permit simultaneous writers?
  • What permits cloud file removal after a member leaves or a device stays offline?
  • What result does a read return when a key is absent locally and the cloud is unavailable?
