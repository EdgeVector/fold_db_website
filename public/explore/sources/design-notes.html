Source notes and release limits

Source review: 1 November 2026. Merged LastDB revision 7053eb5a.

Whole records are the current model. The guide describes 124 parts and 405 connections. This review covers 20 new commits, and 632 commits after October 21.

One schema owns its records

A schema names fields, a primary key, and optional named alternate keys. Each schema owns its record values.

Canonical field reuse shares meaning and type. It does not connect records in different schemas.

One stored record holds fields, their write facts, record metadata, and any delete marker. The final encoded record must fit within 64 KiB.

Large files stay in a separate file home. A record holds their small references.

Source: src/record_value.rs · src/alternate_keys.rs · atom_store/record_cap.rs

Only format 7 homes

Every new home uses format 7. This release opens and restores only that format.

Formats 4 to 6 require the older program to read their records into a fresh home. The current program has no older-home reader or in-place conversion.

Field atom and molecule read and write paths are removed. Aggregate writes and signed imported field writes are refused.

The old alternate-key change routes are removed. Changed keys need a separate schema and an explicit record copy.

A repeated schema declaration can add fields with unchanged keys and meanings. Existing records read added fields as absent.

Source: disk_pack/run_admission.rs · run_node/creation.rs · byte_backup/run_codec.rs · write/records.rs · schema_declare/owned.rs

Whole-record memory and reads

A read by key checks memory first. A disk fetch can keep one complete decoded record in the warm set.

The default warm limit is 256 MiB. Least recently used records leave first; a record that a call holds stays.

A write publishes its record to memory only after the flush. Older read views and private writes use their own disk state.

A range page names one hash and fetches bounded key pages. Owner pages across a schema follow protected stored-key order.

An owner cursor continues from the previous stored key. Offset plus requested records is limited to 8,192. Conditions and counts can require broader reads.

Source: disk_pack/record_warm.rs · core_set/records.rs · atom_store/record_walk.rs · records/received_range.rs

One complete saved change

A native request saves its records, alternate entries, file counts, history, and notices together. Memory publication and the ack follow disk completion.

Ready requests can share a flush. There is no flush interval.

Each field keeps its own write order. Local metadata updates replace only supplied keys and preserve omitted keys.

An alternate entry belongs to the primary key it names. A departing record removes it only while that ownership still matches.

Repeated changes to one record must leave a final value within 64 KiB. A failed final size check refuses the request.

Source: transaction/request.rs · write/record_effects.rs · record_value/meta.rs · alternate_keys/write.rs

History, deletion, and files

Field history is off by default. An enabled policy saves the previous field value and write facts as a copy.

A history copy omits record metadata. Its file references still keep the required file bytes available.

Delete keeps a marker against older writes. Purge also removes retained history and conflicts. A whole-record Purge refuses above 1,024 history entries.

The owner can first remove field history in pages of at most 32 entries. The delete marker remains after Purge.

File counts cover current record references and saved history. A zero count starts a one-hour wait by default; a new reference cancels removal.

Backup checks file pointers in records and history. Metadata-only file references use file counts and the full native file copy.

Compaction and physical file holds remain separate from logical deletion. Older cloud copies do not disappear because a local record is deleted.

Source: atom_history/records.rs · write/record_effects.rs · blob_counter/deltas.rs · proof/records.rs

Local share copies and explicit peer exchange

An active share rule copies a changed personal record to each local share scope in the same request. Copies include the delete marker and file counts.

A read chooses the live local record first. Otherwise the first active received scope with a live record supplies the whole record.

Active received data blocks alternate reads. Local share support does not enable automatic cloud delivery.

Explicit owner peer exchange uses signed version 2 record events. Each field keeps the newer write. A losing different value can remain as a conflict.

If a merged peer record exceeds 64 KiB, the stored record stays unchanged. The receipt names the skipped record; other records can save.

Peer exchange refuses file blobs and shared data. It sends Purge as Delete, so the receiver keeps its own history. Automatic network delivery remains unavailable.

Source: records/received.rs · write/record_effects.rs · records/cap.rs · records/admission.rs

Keys and encrypted run files

Each schema record key space has its own protected hash lookup. Alternate keys use separate key spaces.

Typed range rules preserve the required order inside encrypted run blocks. The order rule alone is not encryption.

Both run homes keep their native encrypted files during backup. Cloud object sizes do not select a different local storage format.

File blobs retain separate encryption and file keys. Peer metadata excludes local file-reference keys.

Source: src/record_space.rs · molecule_key_codec/profile.rs · disk_pack/run_node.rs · sharing/file_blob_seal.rs

Backup and restore remain separate

The owner can request a snapshot or enable an automatic policy after an account connection. Defaults check changes each minute and request a full snapshot daily.

A snapshot captures both run homes. Later accepted change backups retain complete ordered changes.

Restore needs a fresh destination, exact accepted state, complete change chain, account access, and the release switch.

This release restores only format 7. Earlier backup profiles are refused. Restore preserves saved counts and does not repair them.

The DEV recovery workflow adds a guarded manual baseline operation. That change is not proof of PROD recovery or older-backup compatibility.

This review does not enable restore, alter the primary, or change automatic backup policy. Inactive snapshot preparation still grants no replacement authority.

Source: automatic/policy.rs · byte_cloud_backup/mod.rs · logs/plan.rs · byte_backup/run_codec.rs · workflows/cloud-backup-recovery.yml

No vendored LastStore source changed in this interval. Schema-service error helpers preserve their response rules.
