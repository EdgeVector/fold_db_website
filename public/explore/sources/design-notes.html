Source review: 19 November 2026. Merged LastDB revision b5542a7555b12ec4fca20c2226f86b8378d0bbb1.

The guide describes 131 parts and 509 connections. This update reviews 2 more commits after 3216b293. The reviewed history contains 212 commits after the October 21 baseline c70e6fd. People’s current sharing implementation was also checked against the earlier source, when the app was called Social. Changed code and surrounding callers were examined across the model, memory, disk, flush and ack, deletion, encryption, cloud activation, backup, recovery, and services, including vendored LastStore. Records and keys

A schema owns its records. Canonical field reuse shares definitions, not values. One record carries complete fields and one revision. Primary and named alternate addresses are supplied separately. Replacement supplies the complete new payload; conditional writes protect against overwriting a newer version. Records remain capped at 64 KiB, with large files stored separately.

Ordinary record reads use keys or a range under one hash. The app API can also list a schema’s primary keys with keys_only: true and no key or range. This returns keys, not unfiltered records. Pages default to 100 keys and cap at 1,000. Arbitrary field filters are not available.

App requests and access

The SDK provides read, write, and changes. Reads accept at most 64 items, execute four at a time, and retain request order with per-item errors. A write list commits within one owned database. Creates require absence; replacements and deletes require the read revision. Refusals can name the mutation index and the reason exists, absent, or revision. Reads now serve ready received databases, checking a durable signed-log prefix before and after the read. Received direct writes require fresh active Submit access and a durable store. The changes extension still refuses received databases; proposals remain separate.

An installed app with a signed access declaration starts on apps.sock. Activation registers its ID, read and write access, extensions, and data folder on the owner socket. An explicit reinstall or upgrade of the active version registers that grant again. An automatic poll of an unchanged release skips registration. An identical grant succeeds without rewriting the grant file. Launching supplies the saved ID and socket path without calling the node; the app can start while the node is stopped, although database calls still need it. The SDK sends X-LastDB-App, not a session token. One grant per app is saved in app-grants.json beside the sockets, outside the database. It survives restart and has no expiry. Replacement updates later requests from running apps. The node permits 256 apps, 256 names per list, and a 1 MiB grant file. Missing or unreadable grants admit no apps. A read or write grant can use "*" for all current and future schemas. Extensions remain explicit.

The declaration needs no separate owner approval. The launcher and install steps do not sandbox programs. Both sockets check the operating-system user, but a same-user program can still use the owner socket. The app ID is not a secret credential. The selected-database session mechanism is removed. Saved app permissions remain. The app socket has four workers, 256 queued connections, and an 8 MiB body limit. A full queue returns 503 with a structured busy error and Retry-After: 1. Status reports app_socket separately from uds.

File input names a local regular file outside the LastDB home. The app API does not carry file bytes. A file read can return an existing reference path; the path check detects absence or changed size, not a same-size edit. Reading file bytes performs the separate hash check. Each file reply reports local, a path or null, without writing a new file. On the app socket, file: true can copy bytes LastDB holds into the registered app data folder at files/<content hash>. The folder uses 0700 permissions and the copy uses 0600. Without that folder the path remains null. A same-size existing copy is reused. On the owner socket, file: true can instead name file_dir: an existing absolute directory owned by the user, not group or world writable, and not a symlink at its leaf. Held bytes are written there under their content hash with mode 0600. Apps cannot set this folder. This does not fetch a cloud-only file.

App database actions

SDK 0.19 adds client.databases on POST /v1/x/databases. An app must declare the databases extension. Its eleven actions list or create databases, accept invitations or read links, issue read links, list or declare schemas, read or change sharing settings, invite a receiver, submit a proposal, and check a proposal’s status. The node reuses the existing database handlers and their checks. The databases extension alone permits schema placement. It does not consult the record read or write lists. Optional app_id names the schema namespace; omission uses the registered app ID. The schema name must match that namespace. Record reads and writes still require their respective grants.

Supply the database selector in the action body. An omitted selector defaults to the personal database, even if the SDK client selected another database. The extension accepts successful 200 and 202 replies; failures use the app API’s error shape. A 202 submission is queued, not accepted. Database-session tokens are removed. Raw owner administration routes remain unavailable on the app socket.

submitProposal uses the extension when the launcher sets LASTDB_APP. Owner clients retain the owner submissions route. Other owner helpers do not automatically switch: on the app socket, check status with client.databases({action: "submission_status", database: "trip", mutationId}), rather than getShareSubmissionStatus.

Changed keys and memory

The optional changes extension returns locally stamped record keys and deletions. Entries commit with their records. It retains 250,000 entries and examines at most 500 per page. Save through, even when schema filtering returns no entries. Rebuild the app’s view when id changes or gap is true. This is not record history or the cloud mutation log, and it does not promise to report every remote replay.

The decoded-record warm set defaults to 256 MiB. It includes record keys, metadata, and file markers. Held records can keep it above that target. Schema definitions have a separate cache. File bytes remain outside the warm set. The least recently used unheld records leave first.

Each run home now keeps at most 32 open readers between calls. A reader holds a file handle, cipher, footer, and decoded top block; it retains no data blocks or records. Least recently used readers leave first. Compaction removes retired runs from the pool, while active reads may still hold them. Separately, one read can reuse up to 64 checked lookup blocks, bounded by the smaller of 256 KiB or one-sixteenth of its byte allowance. That block cache ends with the call. These are separate limits, not a total process-memory cap.

Disk, flush, encryption, and deletion

Format 15 remains current. A request privately prepares its changes. The bounded write queue combines requests already waiting, without a collection timer. File additions commit before record changes; removals follow the durable record change. Run completion and CURRENT staging can overlap, but publication waits for both. The disk root and clean memory state publish before the write succeeds.

Run files authenticate encrypted blocks. Content-key derivation and file encryption remain in place. Ordinary reads authenticate a complete block, with a 64 MiB decompressed-output cap. Native snapshot transfer streams files separately. A local file reference leaves the original external file in place; removing the reference does not delete that file.

Deletions remove live records and alternate addresses while retaining the ordering facts needed to reject older replay. Record replacement retires old stored file bytes after the record is durable, except for the confirmed attachment temporarily held behind a pending local edit. Settlement and schema deletion release unused holds. Inline attachments use a separate bounded saved row. Obsolete file-reference metadata bookkeeping and the unused replay-cutoff check are removed. Local deletion does not immediately erase cloud copies. Personal cloud cleanup has its own tracked objects and snapshot coverage; shared uploads remain outside that cleanup path.

Cloud activation and accepted changes

One signed-log worker handles personal, owned named, and registered received databases. Owned uploads require saved account access and a matching live creation response for the database and environment. Local writes finish independently of cloud availability. ExeMem checks eligibility and routes cloud bytes; LastDB decides recovery and retention correctness.

The local accepted-change stream records committed work before upload. Its confirmed upload position and the downloaded cloud position are different sequences. Saved identity bindings and exact retry bytes prevent a retry from silently naming different work. Personal devices reconcile under the same owner key. In proposal mode, whole-database members use the separate proposal inbox. Direct mode lets active writers append to the published log.

The first personal snapshot establishes a durable baseline. Explicit native snapshots capture both run homes and their checked file inventory. Covered personal snapshots can queue bounded log cleanup and retryable provider cleanup. A separate ledger tracks confirmed personal file uploads for snapshot-covered deletion. No periodic full-snapshot schedule or general shared-object cleanup is established. The old backup index-log-history command is removed.

Sharing waits for cloud enrollment

Sharing configuration reads and writes, member changes, invitations, and read-link creation check the same enrollment state as the sync worker. A live create reply must confirm this database and environment. The confirmation is kept in the running process and resets at restart.

  • No verified account connection: return immediately with owner status 409 no_cloud_account. The app API uses 409 conflict and the message “this node has no cloud account”. Connect the account before retrying.
  • Account connected, database not enrolled: wake sync and wait up to 30 seconds. Continue when enrollment succeeds. Otherwise return owner status 503 database_enrolling, or app status 503 busy, with Retry-After: 2.
  • Already enrolled, service answer unconfirmed: keep 503 share_configuration_unconfirmed on the owner route and 503 busy on the app API. The message is “share configuration is not confirmed”. This is a service or verification failure, not another enrollment wait. Specific service refusals retain their own status and details.
  • Payment required: preserve owner status 402 and app status 403 permission_denied. A known payment hold is not reported as enrollment in progress.

The owner CLI preserves the error message and code for member changes and read-link creation. The app reply preserves the retry header. These changes do not alter local durability, record conflict rules, invitation contents, or the separation between the mutation and proposal logs.

Recovery and its limits

Fresh owner restore selects a database and fixes a cloud head. It installs an available native file snapshot, then replays a continuous retained log through that head. It checks access, manifest binding, allowed paths, lengths, hashes, encrypted entries, and required files. The fresh destination is published only after successful shutdown. Without a native base, recovery needs the retained log from its start.

The archived JSON-entry snapshot chain and its install journal are removed. An expired private named cursor still stops. Received databases now stage and install the publisher’s native snapshot, then resume after its position. Initial acceptance also installs that snapshot before opening the store; with no snapshot it starts at zero. Personal automatic recovery can stage an exact native snapshot and later entries, after first publishing pending local edits. It refuses changed source boundaries, external references, unconfirmed writes, or pending deletion. The daemon shuts down before exchanging data directories, retaining the old data in staging.

Native snapshot download requests a service hold where supported. Logical attachment replay still assembles each requested file in memory; response bounds alone are not a total recovery-memory cap. This source review does not establish a new recovery pass or PROD qualification.

Share: proposals and publication

A whole-database share keeps a mutation log and a separate proposal log under one database ID, with independent positions. Only the publisher reads and settles proposals. The publisher’s LastDB confirms membership and the signed memberWrites map, checks the installed schema and record version, commits accepted changes, and uploads them before settlement.

Each schema can be owner_only, own_records, or shared. A missing name defaults to owner_only. own_records permits creating records and replacing or deleting records whose live created_by matches the member. Edits and deletes require the submitted base. The former fixed social/Comment exception and per-member writeSchemas check are removed. Direct writes bypass this approval.

The first active proposal in a page confirms the map with the service. Later proposals reuse it. If confirmation fails, proposals stay pending. Invalid or denied proposals are discarded. Use client.select(id).submitProposal with the databases extension, or the owner submissions route. The 96 KiB limit and single create, replace, or delete remain. HTTP 202 means submitted, not accepted. Private status reports submitted, published, discarded, or unknown.

Social, Medical, and Finance illustrate uses for separate shared databases. Medical and finance app rules are not supplied here. Approval happens automatically on the publisher’s machine; receivers do not have another review inbox.

Source: Approval · Record rules · Settlement

Received writes waiting for publication

The database list and invitation-accept reply include publish on each received database. Owned databases omit it. Apps get the same report through the databases extension. pending is the local accepted-write queue head minus its confirmed prefix. It counts queued direct writes, not proposals awaiting publisher approval. A receiver store that cannot be opened reports zero, so zero alone is not proof that every write reached the service.

lastAttempt records a time, outcome, and status. confirmed means the service accepted an append or recognized a duplicate beyond the uploaded writer sequence. refused means an authorization refusal before any chunk of this upload was accepted; the node then restores the prior record and removes the queued item when that restoration succeeds. unconfirmed keeps the write queued, including payment refusal. A partially accepted upload is not retracted on a later refusal. The report describes the last append attempt, not the completion of every queued write.

Status is an HTTP code when the service replied. It can instead name a stop: access_unknown, no_credentials, snapshot_required, gap, spool_position_mismatch, or empty_page. Other named failures cover reading, preparing, restoring, or confirming queued writes. When usable credentials exist but no response or named failure was recorded, status can be null. A note already recorded during that turn wins, so a confirmed service response can remain visible even if later local confirmation fails. The last attempt lives in memory and is null again after restart. Logs retain only a limited outcome/status category and suppress repeated identical categories; they do not log the database ID or record contents through this report.

Source: Publication report · Append and queue confirmation · Database replies · SDK report · Private logging

A member’s first direct upload

A new received-database writer may be refused access to the publisher’s writer-tip endpoint. When the member has no saved upload position, that specific authorization refusal now starts its position at zero so it can send sequence 1. The append still goes through service authorization. Other writer-tip errors stop publication. Later attempts use the saved position for that database, device, writer, environment, and cloud scope. A mismatch with the next queued page stops publication instead of skipping past it.

Queue gaps, required recovery, an unexpectedly empty page, and position mismatches now record an unconfirmed publication status. Named errors also cover queue reads, preparation, worker stops, and local confirmation. An existing service response is not overwritten by a later local error. The report remains a recent attempt, not proof that every queued write has reached the cloud.

Source: Upload positions and queue stops · Stop categories · Retraction reporting

A refused proposal is not a retryable upload

A proposal append refused by the service for authorization returns HTTP 403 and “this member cannot submit this shared mutation”, with no retry header. The app API calls this permission_denied. Do not retry it. This is the append decision, before any later publisher approval. A successful 202 still means submitted only.

An append that cannot be confirmed returns HTTP 503 and “shared mutation was not confirmed”, with Retry-After: 2. The app API calls this busy. An unpaid account on this append stays in that category; it is not treated as a final authorization refusal. Retry the same proposal after the delay using its original idempotency key. The later proposal-status call still reports submitted, published, discarded, or unknown.

Schemas, installation, and releases

Manifests can declare each field once as a typed object, or use the older list and field maps. Mixing both forms is refused. An app’s activation resolves named schemas at their signed definition IDs before the app probe runs. If either access side is "*", it also places manifest schemas that neither side names, using the signed source commit. The node accepts compatible definitions and refuses incompatible changes. It first checks definitions already on the node, then the schema service, then a matching manifest entry. Every named definition must hash to its signed ID. An unresolved definition refuses activation and restores the prior version. Existing exact definitions keep their retention; a manifest fallback keeps its declared retention. Declarations may name schemas from another app’s namespace; identical definitions succeed and incompatible definitions fail.

After a public app is listed, the publish command pushes the running node’s wire-form definitions. Missing schemas are skipped with a warning; an ID mismatch refuses the push. A failed push warns but leaves the app listed. Private apps and prepare mode do not push. The schema service accepts signed pushes for already listed app commits. It checks the listing, publisher, commit, and signature. Up to 256 definitions fit within a 1 MiB push. It computes each definition’s ID and stores an immutable object before updating the catalog. GET /v1/schemas/<definition ID> returns that object without credentials. The old scheduled catalog feed and public-manifest fetch are removed. Advice uses pushed definitions and built-in vocabulary. Examples require matching normalized names, compatible supplied types, and compatible descriptions. Vocabulary advice still works when the catalog is unavailable.

The owner can also place an app schema in an owned named database through POST /api/databases/{id}/apps/declare-schema. Dispatch selects that database’s record store before running the existing declaration checks. It does not also install the schema in the personal database. Later record requests name the database ID. Received shares refuse placement. Apps use the databases extension without needing a record write grant; the raw owner route remains unavailable on the app socket.

Source: Owned database dispatch · Current SDK scoping

App installation searches signed catalogs by app API version (current and minimum 1), separately from socket API 42 with minimum 38, and chooses each app’s highest supported entry. Absent levels are skipped; other retrieval failures stop selection unless a verified cached catalog is available. Separate DEV and PROD profiles supply pinned registry keys. Managed installs retain version folders and rollback; a rollback switches code, not database changes.

CI proves app operations across supported interfaces but no longer signs or republishes app listings. Existing signed entries remain valid. Stable qualification still requires its full one-hour run and normal source, security, exact-source snapshot, provenance, and publication gates. The snapshot release check now completes after a successful import, without waiting for account cleanup. DEV account retirement still runs separately; a failure there fails the workflow. This guide review is not a release, deployment, or primary upgrade.

Retired search delivery and current commands

The Search app integration, its local inbox, field-selection pipeline, status counters, and --enable-search daemon option are removed. Writes no longer create search batches. Personal recovery no longer checks a search-delivery switch. Search indexing belongs to an app using supported reads and changes; this is not a built-in search service. The separate LastSeek CI job only builds and records its version; it no longer proves inbox ingestion. Stable app qualification covers Brain and LastSecrets.

All lastdb get and get-keys calls now use /v1/read, including received databases. lastdb mutate uses /v1/write for conditional create, replace, and delete in personal or owned databases. Received writes require direct mode and active Submit access. The old query, list, mutation, changes, generic schema-declaration, and blob routes are removed without aliases. The SDK removes their convenience methods. Reads return fields, primary key, revision, and basic blob information, without full metadata, alternate addresses, or inline markers.

lastdb get --hydrate DIR names an existing directory, not an output filename. Held bytes go there under their hash; an existing file reference returns its original path. A mutate wrapper can name file: {"source":"photo.jpg"}, relative to the request file. The API uses file: {"path":"/photos/photo.jpg"}. Omission preserves a replacement’s blob; null clears it. Existing inline files remain unchanged. The engine still stores and replays inline files, but the public API has no inline-file operation. --hydrate-inline, file placement flags, --mutation-id, and alternate-key listing are removed. Keyed alternate reads remain available. Purge remains internal; public writes accept delete.

The database-session route, tokens, header checks, and SDK session methods are removed. Name the database on each read, write, or changes item. SDK select still scopes schema and proposal helpers, but does not fill the database field in read or write items.

Implemented paths and current limits

The status audit covers every part and connection. Expiry already removes records through revision-checked erasure. New-home creation already creates the record store before normal use. Both connections are shown as implemented. Local file references also work through the app API, not only owner routes.

Last writer wins selects one complete record when private devices synchronize. The ordering uses the earlier of author time and cloud acceptance time, then writer key, device, and sequence. It does not merge fields or maintain a separate collection of losing versions. Ordinary app writes still require an absent record or a matching revision. External and inline attachments now use the same last-writer-wins order. Ordinary attachment conflicts no longer pause sync. Pending local edits keep one complete confirmed state until settlement. A later caption-only write inherits the confirmed photo, even if a different local photo is still visible. Missing or damaged required bytes, incompatible schemas, and unrecoverable older pending state still stop replay.

Cloud-coordinated guaranteed writes and durable conflict preservation are retired designs, as clarified on 17 November 2026. They are not future work in this guide. Local writes still reach disk before success. Opt-in and manual labels describe implemented features that need configuration or an explicit request.

Request statistics

lastdb ops and owner-only GET /api/ops report completed calls and schema activity. The command sorts by total elapsed time; --by-count sorts calls by request count and schemas by item count. --json returns the structured response. The route first appeared in API 40; current socket source is API 42 with minimum 38.

Both in-memory tables hold at most 256 rows, reserving one for overflow. Request bodies contribute up to eight distinct schema names; further names share an overflow label. Caller labels are clipped to 64 bytes. Owner calls can carry a client label; app calls use the supplied app ID, including refused requests. These labels do not establish identity. Schema rows do not distinguish databases. No request payload is retained in the counters. Restart clears all statistics.

Timing starts after worker and body-budget admission. Normal calls include reply writing; deferred owner calls are recorded before the reply returns to a worker. These are elapsed request times, not CPU use or complete client latency. Each schema receives the whole request time, so schema totals must not be added as independent work. Refusal counts use the HTTP response status; errors inside a successful batch response are not separate refusals. Connections rejected before request recording are absent. The app socket and selected-database sessions cannot read this report.

Two logs and local sharing identity

A reader receives every entry served from the shared mutation log. There is no publisher-only writer filter, stored direct-write mark, or separate writer-signature frame. The service controls admission. The publisher still owns snapshots and proposal settlement.

Shared replay follows service delivery order. It restores a pending local preimage before an earlier served change and recognizes a local echo. Create requires absence; replace and delete require a record. Failed preconditions and alternate-key collisions are warned and skipped. Bad entry/scope bodies are skipped; storage and required-file failures still stop progress. Private databases retain their separate stamp-based last-writer-wins path.

Publisher mutation identities and proposal receipts stay beside the sync journal, outside record storage. Intake retries use a receipt or deterministic mutation ID to recognize a completed write. Record identity markers are saved after commit, not atomically with it. Authorship stays inside the record. These source findings do not establish a new live recovery result.

Database-set record authorship

Live records now carry created_by and updated_by, set by LastDB from the authenticated writer’s node key. A replacement retains the creator and updates the latest writer. Local apps share the node’s identity. Accepted proposals retain the member’s identity even though the publisher uploads the accepted change. Replay preserves authorship; deleted markers have none. Older records may omit either value. A later replacement does not invent a missing creator.

Reads and the SDK expose known authorship as strings and omit unknown values. These keys are reserved entries in the stored metadata map, exposed separately in read replies. Caller metadata cannot replace them. Saved replay baselines keep them, including the creator when an own-device edit settles. They count toward the record and warm-set byte limits. Comment ownership now reads created_by from the live record. The old creator sidecars, injected author_id, and share_author fallback are removed. Legacy proposal source filenames and metadata are ignored; an accepted replacement still preserves the publisher’s existing metadata.

Snapshots include referenced local attachments

Initial and later native snapshots now read each referenced file, check its size and hash, seal the bytes with the database content key, and add them to a private snapshot file home. Stored file runs are reused. The live reference and original file stay unchanged. Restore therefore needs the saved bytes, not the source machine’s original path. Capture needs temporary disk space and fails on missing, changed, unreadable, or oversized references. The existing 512 MiB read-and-seal limit applies per referenced file.

The initial checkpoint records its original database frontier separately from the added snapshot file entries. Later capture holds the write and reference-catalog boundaries while preparing the snapshot. Its private staging directory is removed on release. This snapshot change does not remove the external-reference guard from automatic replacement of a lagging device’s local home, and does not establish a new PROD recovery pass.

Sharing settings, direct writes, and open read links

The node now reads, signs, and sends settings for read: members|anyone, write: proposals|direct, and memberWrites. No statement means members, proposals, and an empty map. The map holds at most 256 schema names of at most 128 bytes. Settings have their own signed sequence. They are sent before member updates, so the two changes are not atomic. Failed settings do not send member changes; failed member changes can follow successful settings.

Direct mode lets an active Submit member commit through /v1/write to a durable received store. Fresh selfAccess and local app grants are required. The encrypted upload uses the member’s identity. A local ack does not prove cloud acceptance. A refused, uncommitted upload restores the prior record and drops the queued item. Unknown access keeps the queue; confirmed closure retracts it. Direct writes skip publisher approval and the memberWrites map.

Open read links are opaque tokens containing the database read key, not browser URLs. The publisher can issue one through the CLI or share_link action. Acceptance registers it locally without membership and downloads the publisher’s snapshot. The service must permit read: anyone; issuing a link does not change that setting. Link readers cannot append. Returning to members cannot recall keys or bytes already shared.

Decided but not implemented: the later per-member read/propose/write capability design replaces the database-wide write switch. The reviewed code still uses the switch and Read/Submit roles. These are source findings, not evidence of production service rollout.

App removal and registry versions

lastdb app remove drops the app grant and removes installed code, receipts, and owned command links. Schemas and records remain. The separate app data folder stays unless --delete-data is used. Removing the current receipt prevents automatic upgrade polling from reinstalling it. Apps with active post_install steps are refused because no uninstall procedure is declared. A stopped node can leave a grant for a later retry; other node errors stop before file deletion.

Catalog lookup, publication, and rollback use app_api_version, not the owner socket version. Wildcard permissions are valid at every app API version. A running older node without the new field is refused by registry commands; no socket-version fallback is invented. This review does not qualify old installed apps or a new release.
