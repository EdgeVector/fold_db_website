Local storage and authorship

Record

A record holds one schema’s fields, primary key, named alternate addresses, one revision, and database-set authorship. Replacement supplies the complete desired state. Omitted fields disappear.

The complete encoded record has a 64 KiB limit, including keys, alternates, one write stamp, authorship, metadata, and file markers. Its single attachment can be a blob or inline file; those bytes stay separate. A live record can have no payload fields.

Source: Record

Record authorship

Local writes set created_by at creation and updated_by on each change. Shared materialization keeps the earliest accepted creator and the winning writer separately.

Personal replacements retain created_by. An attachment-only replay keeps the winning fields’ writer and time. Shared creation means the earliest accepted write to that key, not arrival order. Per-change signed entries omit arbitrary remote metadata; native personal snapshots preserve stored metadata.

Warm set

A read by key checks the warm set first. A disk fetch can keep the complete decoded record for a later call.

The default warm limit is 256 MiB. It covers decoded records, their keys, metadata, and file markers. Schema definitions and file bytes stay outside this charge. The least recently used unheld records leave first. Older read views and private writes use disk. A range page can admit its selected records without fetching them a second time.

Flush and acknowledgement

A native write saves its complete change before publishing memory and returning success. Normal record commits use one encrypted log frame and one ordered flush.

Normal logged commits append one frame and perform one ordered file flush. Large commits can seal pending work and write directly to a run. macOS uses F_BARRIERFSYNC, with F_FULLFSYNC as a fallback; Linux uses fdatasync. An explicit native flush receipt forces the drive cache to storage. Spool uploads also require a full flush, but reuse its coverage for later pages until new entries arrive. Local success does not confirm a cloud copy.

The write queue can group prepared requests into one native commit. Commit-log flush counts measure those native commits, not individual API requests.

Captured entries commit atomically with their records; encrypted files are written first. An ID repeated within a batch or among queued writes, a signing failure, or a full spool can refuse a write. Personal /v1/write wakes the upload worker after the commit.

Owned shareable /v1/write still mirrors into signed history after the local commit. That later step can fail. Read the record before deciding whether to retry.

Ordinary snapshot capture seals pending commits, waits for the file-deletion ledger to clear, and forces a full-drive flush before pinning. The first-snapshot path flushes before its snapshot call seals any remaining log frames; newly sealed files and staged local-reference copies do not share that earlier full-drive flush.

Run block encryption

Separate derived keys protect each record and record-file home. Owned named databases derive their content keys from the node signing seed and database UUID. Received Share publications use their supplied content key.

Block compression skips inputs below 256 bytes. It is kept only if it saves at least 64 bytes and 10%, including its length header. Encryption still applies when compression is skipped. File sizes, clear footers, and some layout facts remain visible. Personal payloads and shared data and schema bodies are sealed before signing. That log encryption is separate from local run encryption. The run reader loads and authenticates a complete block before exposing decoded bytes. Decompressed output is capped at 64 MiB; the former two-pass bounded reader is removed. Personal snapshots transfer native encrypted files unchanged. Their clear manifest exposes file paths, lengths, and digests, not record content.

The record commit log encrypts each frame with the record home key, a fresh identifier, and its commit counter. Replay authenticates frames before restoring logged values. Log file sizes and framing remain visible.

AArch64 Apple and Linux builds enable hardware AES and polynomial multiplication when the CPU supports them, with a software fallback. The cipher and encrypted format stay AES-256-GCM.

Prepared writes

LastDB prepares a complete change privately and checks that it fits. The write succeeds only after disk completion and memory publication.

Prepared data stays private. Each primary key appears at most once per API batch. A failed condition or oversized record refuses the request. Saved records enter memory after flush; large prepared sets can wait for a later fetch.

Preparation uses the format writer for records and their related changes. Before accepting the request, LastDB checks the final encoded record at each changed key.

Memory limits

The warm set and prepared writes have separate byte limits.

The warm set defaults to 256 MiB; held records can keep it above that target. Pending native writes have a 512 MiB allowance, including staged signed entries and encrypted attachment copies. Those bytes also count in the disk-space reservation. Read and backup work have their own bounds. These are not a total process-memory cap. The former process governor and allocator tuning are removed. Each run home can also retain 32 reader handles and their small lookup headers. Personal sync requests up to 90 stored relay items per page. One segment item expands to many entries, and its full blob is buffered during decoding; 90 is not a decoded-entry or memory cap. Its file sealing and opening still buffer whole files. Shared histories remain in memory. Snapshot hashing and HTTP transfer stream native files. Copying a local file reference into the snapshot still buffers that complete file. Whole-memory blob reads have a 64 MiB cap. Segment reads have a 16 MiB cap per blob and fetch up to eight concurrently. Streamed file downloads do not use that whole-memory cap.

The warm set estimates complete decoded records, including their keys, authorship, metadata, and file markers. Prepared native writes use a separate byte allowance.

The record home also retains unsealed commit-log records in its memory layer. It is separate from the warm set and pending-write allowance. The 256 MiB seal threshold counts encoded log-frame bytes before the next append, not total resident memory.

Write queue

Prepared requests wait privately in order. Requests already ahead of the disk worker can share one complete commit. Later arrivals wait for the next commit.

Each request passes its own checks and waits for disk. Captured work is checked for IDs repeated among queued writes in memory, spool capacity, and memory limits before it enters the queue. A group stops growing at 1,024 requests or 1,024 captured entries. A group that reaches a limit flushes before another request can join. An API mutation batch remains one complete request; grouped requests keep separate acceptance conditions.

Snapshot commit

A normal record-home commit appends and flushes a log frame before publishing logged memory. A later seal writes those records to a run and publishes CURRENT.

Record and file homes keep separate commits. File additions precede the record commit; file deletions follow it. The commit log covers record-home commits only. Spool entries are part of the record commit, so there is no separate staged-entry recovery step. Run home

A home is a folder of disk files. LastDB uses one run home for records and one for record files. The record home appends commits to a log before later seals create runs.

Only format 15 homes are accepted. New homes use it automatically. Older homes need their matching program; in-place conversion is unavailable. Record commit log

The record home normally appends each complete commit as one encrypted frame and flushes it in order. LastDB returns success after publishing the matching memory state.

A frame holds a complete home commit. The log uses numbered files; new files start when the active file reaches its 16 MiB target. A commit larger than half the maximum decompressed frame bypasses the log after a seal. Replay requires consecutive frontiers. A torn final frame is ignored; an unreadable interior frame or missing frontier refuses open. A clean stop seals commits and removes the log.

Each log file is created with private permissions and its directory entry is synced. Appends use the platform’s ordered file flush.

An orderly stop seals every logged commit and removes the commit-log directory. A crash leaves frames for replay.

The current non-logged RunHome opener replays and seals a leftover log before it continues with run commits.

Logged memory layer

The record home keeps flushed commits in sorted memory segments until a seal writes them into a run. Point and range reads check this layer before older runs.

This is separate from the warm set and prepared-write allowance. Its byte count is encoded commit-log frame bytes, not resident memory. A seal freezes active segments while later commits continue. A commit first seals when those frame bytes already exceed 256 MiB; that threshold is checked before append, not a hard memory cap. Background sealing also starts when active log bytes reach a limit between 64 KiB and 8 MiB, or active tombstones hide enough logical data.

The memory layer tracks commit count and encoded frame bytes. CURRENT advances only when a seal publishes a run; read roots report the combined sealed and logged frontier.

Replay rebuilds segments from complete frames above CURRENT. Replay does not estimate the old run bytes hidden by tombstones.

Commit-log seal

A seal freezes logged memory, writes its newest value for each key to a run, publishes CURRENT, then prunes covered log files.

Background work starts when active log bytes reach the calculated threshold, a frozen seal needs completion, or active tombstones hide more than both 64 KiB and one eighth of the logical bytes in existing runs. Large commits and commits made when encoded log-frame bytes already exceed 256 MiB seal before writing directly to a run. Snapshot capture seals, then tries at most 64 merge steps; it can continue with merge work remaining. A clean stop seals and removes the log.

Sealing uses a spare log file so commits can continue while a frozen layer is written. Publication failure poisons the home; restart replays the durable log against CURRENT.

Ordinary snapshot capture seals once before it waits for the write gate and again under the gate. It then runs up to 64 merge steps, forces a full-drive flush, and pins the resulting roots.

The first-snapshot path calls the explicit native flush, then the snapshot call seals remaining frames into runs. It does not run ordinary capture’s merge-settlement loop or repeat its full-drive flush after sealing.

A delete carries the old value’s length when it was already read. Other tombstones use the mean logical bytes per live run key. These are cleanup hints, not measured disk savings. They are not stored in the log or reconstructed on replay. A later base merge removes obsolete run bytes; sealing alone does not free them.

Log segments

Personal sync puts consecutive signed entries from one device stream into a blob. The relay stores one small item that names the blob at the segment’s last sequence number.

Personal send batches target 2 MiB across signed entries and encrypted files; the first entry can exceed that target. A segment contains only signed entry JSON, one entry per line. When reading, the node rejects a segment blob over 16 MiB. The relay blob limit is separate. Shared databases and older senders use inline entries.

Relay protocol: docs/designs/relay-protocol.md, Log segments. ExeMem stores the item as kind segment at entry#{node}#{device}#{last_seq:020}; the item itself is not charged. The committed blob is charged once.

The reference relay stores the descriptor at {last_seq}.json. A segment counts as one item toward the read limit. A read from within its sequence range starts with that segment, and the cursor advances to last_seq + 1.

The relay does not parse or verify signatures or the chain of entries inside the blob. The caller performs the ordinary entry signature and chain checks after the segment content checks.

The sender assembles segment bytes in memory and streams them in 64 KiB body chunks. A temporary segment file is not flushed to the drive; the worker can rebuild it from signed spool entries. It is not a separate recovery copy.

A read page fetches up to eight segment blobs concurrently, each at most 16 MiB. It checks their digest, length, framing, stream, sequence range, and final hash before ordinary entry checks. Full segment contents remain in memory while the page is assembled.

Personal write spool

The personal store commits each signed entry in the same store transaction as its record or schema change. Encrypted attachment bytes stay in separate spool files until the relay confirms them.

The plaintext body is capped at 1 MiB. A captured request and grouped commit each hold at most 1,024 entries. Signed entries and encrypted files share a 1 GiB cap. Repeated IDs within a batch or among queued writes are refused. Stored IDs are not read to check a new write. Missing entries, wrong sequence numbers, or missing files block progress. The old accepted-v1 folder is refused; it is not converted automatically.

Spool entries, recent mutation IDs, and upload progress are records in disk-run. Confirmation commits the upload position, acknowledgement, and entry removals together. File removal follows that commit; startup removes leftover files outside the pending range.

A configured relay, an existing spool, or a signed restore enables capture. Once enabled, capture remains enabled across restarts. Fresh offline homes capture nothing. Named sibling and received stores do not create unused spools. Existing personal data needs a first snapshot before later entries upload.

ID cleanup retains at least the newest 10,000 acknowledged entries by sequence and every unacknowledged ID. Trimming is bounded and runs on acknowledgement, including the first after reopening. These records no longer reject a later write by ID.

Snapshots include the spool records in their native run files, but exclude accepted-files. Restore clears inherited spool records before the new device starts its own stream.

Before upload, the worker captures the spool head and fully flushes the drive if that head is newer than the last successful flush. Pages through that head reuse the flush. Later writes wait for a new flush. This coverage is kept in memory and cleared on reopen or spool reset.

The node gives record writes fresh IDs. Schema changes use their increasing author time. The sender reads finished spool entries to upload them; write preparation does not read them back for checks.

Worker, connection, and status

Background relay worker

The background worker exchanges personal and shared changes, handles leases and proposals, and runs due cloud cleanup. Snapshot uploads run separately.

LASTDB_RELAY_URL overrides the ExeMem address in saved credentials. Without either, the worker idles. The daemon signals the worker in memory to shorten a clean pause. Commands in another process use a wake file. Neither wake path forces a drive flush. Personal send and receive are both attempted, except while a required first snapshot blocks that personal turn. Per-database errors remain visible while other work continues. Shared members known to lack deposit permission wait locally; an unexpected relay 403 waits up to 30 seconds or until grants or leases change.

Each turn uploads shared logs, pulls owned shares, renews configured leases, and decides member proposals. Personal sync receives before sending, then runs any due cloud sweep. A second shared upload sends publisher decisions before received-share work. Ordinary snapshot uploads run in a separate background task.

The worker checks an external wake file every 50 milliseconds while paused. A lost wake only delays work until the next turn. A failed turn keeps its normal backoff; a wake does not turn errors into a busy loop.

If a write reaches the spool after a turn observed an empty page, the worker wakes another turn to send it. A requested snapshot can then get the quiet point it needs.

Relay client

The relay client signs each cloud request with the node’s identity and retries temporary refusals within a fixed limit.

Control requests allow 10 seconds to connect and 30 seconds per attempt. Responses cap at 8 MiB, and redirects are refused. Retries cover gateway 502–504, 500 unavailable, and selected 429 rate_limited provider or read failures. Configuration, quota, payment eligibility, and other refusals are not retried here. A non-timeout connection, request, or body error that returns within five seconds can also retry. Timeouts return without that retry. Connections are not kept in an idle pool. Total retry waiting is at most 1.75 seconds, in addition to request time. The worker uses one relay URL; LASTDB_RELAY_URL overrides saved credentials. A stored append does not prove complete recovery or delivery to every device.

Signed operations include log append, read, stream listing, trim, and blob requests. The signature binds the method, path, protocol version, database, body hash, time, and nonce. A temporary refusal can trigger up to three retries, each with a fresh signature.

Blob transfers

Attachment and checkpoint file transfers stream bytes and verify a download before making the file available. Personal log segments use the same blob service, but the log reader loads each whole segment into memory.

Connections allow 10 seconds. Downloads have a 30-second read limit. Uploads allow 30 seconds without progress while body bytes remain, then up to 64 extra seconds for buffered bytes and an answer. There is no total upload deadline. Progress counts transport bytes, not confirmed storage. Upload bodies stream in 64 KiB chunks; file uploads use positional reads. Retries resend the whole file; multipart and resume are absent. A stored digest needs no second upload. ExeMem permits a blob up to 5,000,000,000 bytes (5 GB); a near-limit upload is not proved. Record attachments have the smaller 33,554,403-byte limit. Native snapshot run files have separate bounds. Whole-memory blob reads have a 64 MiB client cap. Segments and snapshot manifests have a tighter 16 MiB cap. Streamed file downloads do not use that whole-memory cap.

The client obtains a temporary transfer address. Attachment and checkpoint downloads use a private temporary file and publish the final path only after length and SHA-256 match. Transport failures and HTTP 408, 429, 500, 502, 503, or 504 can be retried for up to three attempts.

File bytes travel separately from signed JSON requests. The relay’s 6 MiB payload ceiling does not cap a streamed file. A segment is a blob too, but the relay response contains only its small descriptor; the node fetches and holds the full segment bytes in memory while it checks framing, digest, length, stream identity, sequence range, and final entry hash.

Transfer URLs reject credentials and fragments. They require HTTPS and reject localhost and non-public IP literals, except at the exact origin of a configured loopback relay. Redirects are refused. This check does not resolve hostnames to validate their IP addresses.

Relay-supplied headers cannot override host, framing, proxy, cookie, or cloud metadata-service headers. File uploads supply their own content length. Segment bytes are assembled in memory before the segment blob upload.

Request history

The daemon saves request counts and timings once a minute and on clean shutdown. The history command reads these local files without contacting the daemon.
