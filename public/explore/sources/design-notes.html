Local storage and authorship

Record

A record holds one schema’s fields, primary key, named alternate addresses, one revision, and database-set authorship. Replacement supplies the complete desired state. Omitted fields disappear.

The complete encoded record has a 64 KiB limit, including keys, alternates, one write stamp, authorship, metadata, and file markers. Blob and inline file bytes stay separate. A live record can have no payload fields.

Source: Record

Record authorship

Local writes set created_by at creation and updated_by on each change. Personal sync uses native replay. Shared-history materialization sets both fields to the winner, or to the proposing member for an incorporation. Shared history separately remembers the earliest creator.

Ordinary local and native personal replacements retain original created_by. The shared materializer copies the winner into both author fields. Shared proposal ownership uses the earliest accepted record position, not arrival order or stored created_by. Per-change signed entries omit arbitrary remote metadata; native personal snapshots preserve stored metadata.

Source: Record authorship

Warm set

A read by key checks the warm set first. A disk fetch can keep the complete decoded record for a later call.

The default warm limit is 256 MiB. It covers decoded records, their keys, metadata, and file markers. Schema definitions and file bytes stay outside this charge. The least recently used unheld records leave first. Older read views and private writes use disk. A range page can admit its selected records without fetching them a second time.

Source: Warm set

Flush

A flush sends prepared changes through the native disk queue. Requests can share one complete disk commit before each receives success.

With capture enabled, accepted bodies reach the spool before memory publication and the ack. Missing entries or a full spool refuse progress. Personal /v1/write then wakes sync; it does not sign synchronously. Owned shareable /v1/write still mirrors after the local commit and can fail that later API step. Local success never confirms a cloud copy.

Source: Flush

Run block encryption

Separate derived keys protect each record and record-file home. Owned named databases derive their content keys from the node signing seed and database UUID. Received Share publications use their supplied content key.

Block compression skips inputs below 256 bytes. It is kept only if it saves at least 64 bytes and 10%, including its length header. Encryption still applies when compression is skipped. File sizes, clear footers, and some layout facts remain visible. Personal relay entries use a separate sealed payload. Shared entries still serialize clear fields. Neither transport rule changes local run encryption. The run reader loads and authenticates a complete block before exposing decoded bytes. Decompressed output is capped at 64 MiB; the former two-pass bounded reader is removed. Personal snapshots transfer native encrypted files unchanged. Their clear manifest exposes file paths, lengths, and digests, not record content.

Source: Run block encryption

Personal sync and shared logs

Personal database identity

The owner’s identity seed deterministically derives the personal database ID, birth material, and read key. Every owner device uses the same signing key and database, with its own device ID.

This identity rule applies to the main personal database. Named sibling databases remain separate. An older registry with a different personal ID fails to open; the code supplies no automatic conversion. Possession of the phrase grants the owner identity and read key. The one-off old-home adoption script and admin identity command were removed. Adding a first snapshot to a compatible home does not convert an incompatible identity or disk format.

Source: Personal database identity

Personal write spool

The personal store captures an encrypted body beside each record or schema commit when a relay is configured. An existing spool or signed restore also enables capture. The background worker signs and sends these saved changes.

Each body is capped at 1 MiB. A captured record request is limited to 1,024 mutations. Bodies and copied files share a 1 GiB spool cap; signed retry files are separate. Gaps block progress. Once capture starts it stays enabled across restarts, even without a relay. Fresh offline homes capture nothing. An existing home’s first snapshot must reach the relay before later entries upload. Named sibling and received stores do not create unused spools. Retry-ID cleanup keeps the latest 10,000 records by modification time plus all unacknowledged IDs. Cleanup runs on open and every 2,500 acknowledgements; an older, forgotten ID can become a new write.

Source: Personal write spool

Personal device sync

The worker reads other owner devices before signing its local spool, so attachment decisions use the latest received baseline. It saves the exact signed batch and uploads blobs before entries. Native replay saves winners and progress together.

An outbound page has at most 90 entries and a 2 MiB target counting bodies and attachment bytes. The first item can exceed that target. Relay append chunks also target about 3 MiB of JSON. Incoming pages hold at most 90 entries per device. Only the main personal database uses this path. A first snapshot can cover earlier uncaptured data. The relay needs stream-list, snapshot, and blob routes. Per-change bodies omit arbitrary record metadata; a native snapshot preserves metadata already in its files.

Source: Personal device sync

Personal sync progress

One native metadata row holds each device stream’s applied sequence, hash, order, and frozen flag. A remote record or schema put commits with its next head. The outgoing signed batch is saved separately for exact retry.

Schema removal finishes its paged, idempotent deletion before advancing the head. Invalid streams can freeze and remain skipped. Outgoing JSON has a 64 MiB read/write cap; sealed retry blobs occupy additional disk space. A relay receipt allows confirmed spool entries to retire. Shared databases still use separate history files. A read at a removed history position reports that the device is behind. Download errors appear in cloud status; a clean receive clears that download error.

Source: Personal sync progress

Sealed personal payloads

Before signing, personal sync encrypts each accepted body and external file with AES-256-GCM and a fresh nonce. The database ID, owner key, device ID, and sequence are authenticated with the ciphertext.

Entry headers, stream identity, order, lengths, and sealed blob digests remain visible. Personal file encryption still buffers complete bytes. Shared record payloads use clear signatures and do not use this sealer.

Source: Sealed personal payloads

Whole-record last-writer-wins

A signed entry’s order value uses the write time in milliseconds, raised above its predecessor and cited entries. The greatest order, node key, and device ID wins. Native personal replay also uses the entry sequence as a final tie-breaker. Deletions carry an order too.

The order comes from clocks, not a trusted global time. Values at or beyond 1 January 2100 are rejected. Personal records and their alternate addresses share a record winner. External and inline attachments each track their last explicit set or clear; a replacement that keeps a file does not claim that slot. Create, delete, and purge reset both slots. Pending local edits stay visible until settlement. Shared direct changes count only under the lease rules. Local writes still check absence or revision. Losing values have no separate conflict archive.

Source: Whole-record last-writer-wins

Owned write mirroring

After an owned shareable /v1/write commits, the node prepares birth, schema, and record entries as needed and saves the signed batch to its authored log in one operation. The shared write lock spans the local commit and this mirror.

The selector can be the owned database name or ID and must resolve to saved birth material. Personal writes use the spool instead. Other shared write routes are not connected by this mirror. Hash and hash-range records include canonical alternate addresses. Files and ranged hashes containing U+001F are refused before commit. Arbitrary record metadata is omitted; fields are signed in clear. A signing failure attempts history repair before returning 503. A failed signed batch leaves no newly signed prefix. Repair can fail, and the native record batch and signed log are still separate saves.

Source: Owned write mirroring

Shared logs and upload cursor

Each shared database saves locally signed entries in authored.json and accepted entries from other streams in received.json. uploaded.json counts confirmed authored entries. Restart loads births first, then combines both logs by deterministic signed position. Personal sync instead uses its native spool and stream heads.

Files live under log-sync/<database-id>/. Each log has a 16 MiB limit. Authored entries rewrite their log on append; received entries rewrite theirs when the accepted count changes. A failed received save leaves entries in memory and retries on a later pull. Missing files mean empty logs or cursor zero; invalid or unreadable files error. A cursor beyond its log is refused. Only a full relay stored count advances it. Pending entries and receive page cursors are not saved. This is separate from the native record transaction.

Source: Shared logs and upload cursor

Signed history

A database history contains signed entries from node and device streams. Each stream starts at sequence 1 and links each later entry to its predecessor. Cross-stream references name entries the writer has seen.

Personal databases use the native write spool and saved stream heads. Their snapshots use a separate seed-derived stream shared by the owner’s devices. Shared databases save authored and received logs and rebuild history with births first and then deterministic signed positions; dependencies and repair markers remain in memory. Personal snapshots now permit removal of covered log entries. Shared snapshots and automatic lagging-device reset remain unavailable.

Source: Signed history

Worker, connection, and status

Background relay worker

Each turn uploads shared logs, pulls owned shares, renews configured leases, and decides member proposals. Personal sync receives before sending. A second shared upload sends publisher decisions before received-share work. Ordinary snapshot uploads run in a separate background task.

LASTDB_RELAY_URL overrides the ExeMem address in saved credentials. Without either, the worker idles. A wake marker shortens a clean pause; completed work wakes another turn without repeatedly waking an idle worker. Personal send and receive are both attempted, except while a required first snapshot blocks that personal turn. Per-database errors remain visible while other work continues. Shared members known to lack deposit permission wait locally; an unexpected relay 403 waits up to 30 seconds or until grants or leases change.

Source: Background relay worker

Relay client

The node signs log append, read, stream-list, trim, and blob requests with its identity. The signature binds the method, path, protocol version, database, body hash, time, and nonce. A temporary refusal can trigger up to three retries, each with a fresh signature.

Control requests allow 10 seconds to connect and 30 seconds per attempt. Retries cover gateway 502–504, 500 unavailable, and selected 429 rate_limited provider or read failures. Configuration, quota, payment eligibility, and other refusals are not retried here. A non-timeout connection, request, or body error that returns within five seconds can also retry. Timeouts return without that retry. Connections are not kept in an idle pool. Total retry waiting is at most 1.75 seconds, in addition to request time. The worker uses one relay URL; LASTDB_RELAY_URL overrides saved credentials. A stored append does not prove complete recovery or delivery to every device.

Source: Relay client

Saved cloud credentials

One protected file holds the service address, account access key, and optional checked connection. Account commands, schema-service selection, and the relay worker use its reader.

The reader requires an ordinary private file owned by the current user. It rejects links, oversized files, and empty keys. The saved service address is now the default relay URL; LASTDB_RELAY_URL can override it. Personal entries come from the native spool; shared signed logs remain separate. Their presence is not proof of relay access or backup coverage.

Source: Saved cloud credentials

Cloud readiness

The current database_cloud_state helper reports Enrolled when saved cloud credentials can be read, and NoAccount when they are absent. Grant and link actions use this check.

The previous signed database-create exchange, 30-second enrollment wait, and per-database live confirmation cache are removed. wait_for_enrollment now returns immediately. Enrolled does not establish remote database readiness.

Source: Cloud readiness

Node status

Status reports the running build, socket workers, cloud errors, and upload progress. It also reports the last personal snapshot this node published or installed, using a saved local record without querying the relay.

The old detailed backup policy and progress routes remain removed. Received listings have a separate process-local publish report. A clean upload does not clear payment_hold or prove receive completeness. Unreadable state can report fallback counts alongside an error. No error or zero pending entries is not proof of complete backup. Snapshot status is this node’s knowledge, not a live claim about the relay’s newest snapshot. Personal receive failures, including a required history position that was removed, now appear as download errors. Per-database relay usage reports this device’s confirmed uploads and released log bytes, separately from billing and other devices.

Source: Node status

Finding signed streams

Shared writer discovery

For a shared database, the worker pulls known publisher devices and also discovers additional publisher streams. Current and historical Submit or Write grants identify member writer keys. It materializes records after pulling the publisher and member dependencies.

Writer-wide fallback is used only when stream discovery is unsupported (404, 405, or 501). Accepted received entries are saved; pending dependencies and page cursors are not. Alternate addresses are reconstructed, but shared files, arbitrary metadata, and bundle loading remain incomplete.

Source: Shared writer discovery

Reference relay

The reference relay keeps log entries by database, writer, device, and sequence. A signed birth and publisher grants supply its access index. It also stores blobs by digest. The log.streams route lists a writer’s devices and each contiguous sequence head without rereading all entries.

The relay checks request signatures and grants; it does not run complete AcceptEntry validation. Appends and reads cap a batch at 90. A read without device_id pages one writer’s devices. Public any-read still requires a signed caller. Revoked members can read a single publisher stream to learn their revocation; writer-wide reads remain refused. Stream discovery uses the writer-wide grant check, and its head map is rebuilt from entries and saved removal positions at startup. An identical repeated append also repairs a head missing after a cancelled request. Signed append requests cap at 64 MiB; other signed JSON requests cap at 64 KiB. Blob uploads stream separately and require the returned checksum header, matching bytes, and matching length. There is no blob-size cap unless --max-blob-bytes sets one. ExeMem DEV recovery has separate CI evidence; reference-relay source alone does not establish a deployment. Blob ownership is scoped to the database even when bytes share a digest. Transfer signatures bind the method, database, resource, and a 15-minute expiry. Repeated commits are idempotent. Append prevalidation detects conflicting duplicates before saving the batch, but it is not a crash-atomic file transaction.

Source: Reference relay

Member writes and publisher checks

Database write leases

The publisher signs a timed lease for the database. It covers members with Write permission at that signed position. A member keeps the lease on disk and decides locally whether it can sign a direct change, even offline or after restart.

Shared work can continue while the publisher is unavailable. A signed closing point gives every reader the same rule for late arrivals.

Set lastdb share lease <database> --length 24h. The publisher renews around halfway through and when membership changes. A member stops direct writes before expiry, leaving a safety margin of 10% of the length, capped at five minutes.

Leases are opt-in, from 10 seconds to 90 days. Clearing the length stops renewal and does not end issued leases early. The publisher allows another half-length after expiry before a later lease can close it. The closing entry records the member stream positions it saw; later direct entries under the old lease are excluded. Readers decide from signed history, not their clocks. Winners are recomputed. This device resubmits an excluded change as a proposal if it still has Submit or Write access; acceptance is not guaranteed. No usable lease means /v1/write refuses, so apps must choose the proposal route.

Source: Database write leases

Member changes

A Write member with a usable database lease can change its local received store through /v1/write. The node signs the direct change for other readers. Submit members and writers without a usable lease can send proposals for the publisher to decide.

A direct write needs current Write permission, coverage by the newest held lease, time remaining before the local safety margin, and app schema access. Without these, /v1/write returns 403; it does not automatically turn that request into a proposal. Files are refused for shared writes. Proposals leave local records unchanged until publisher acceptance arrives. Member bundles are not applied by nodes even when the relay stores them. Lease closing can exclude a direct write; this device then proposes it again if it may still submit.

Source: Member changes

Publisher incorporation

After pulling member streams, the publisher checks each unresolved proposal against its current role, schema, and expected history entry. Submit members must own a record they replace or delete; Write members may change any record. It signs an acceptance or a not-accepted decision.

Create requires no live record. Replace and delete require the expected winning history entry. Hash and hash-range keys carry validated alternate addresses. Files remain unsupported. The shared write lock keeps incorporation separate from an owned write and its signed mirror. An accepted change is saved locally, then signed as data citing the proposal. A refusal is a signed heads entry citing the proposal and carrying current publisher stream tips. Storage or signing failures leave the proposal undecided for retry. If signing fails after a local write, the node attempts to restore the history winner. That repair can also fail and log a warning. These saves are not atomic. The old configurable per-schema settings remain removed.

Source: Publisher incorporation

Proposal submission and status

The submissions route accepts a UUID idempotency key and saves a signed proposal. Status is submitted, published, not_accepted, or unknown, derived from the local ledger and history. A publisher data citation means accepted; a publisher heads citation means not accepted.

The envelope carries mutation_type, expected, and optional record fields and alternate addresses, up to 64 KiB. Hash and hash-range keys work; ranged hashes cannot contain U+001F. Non-null files are refused. Submit and Write members may propose; the publisher checks their current role and record conditions. HTTP 202 and relay storage do not mean published. Published and not_accepted are final decisions for that proposal. Submitted can mean the decision has not arrived yet. The idempotency ledger is saved separately from the signed log. Its 4 MiB limit is checked before signing. Repeating a UUID with the same body reuses its proposal; a different body is refused.

Source: Proposal submission and status

Local entry validation

AcceptEntry verifies the signature, database binding, predecessor, observed dependencies, order value, and writer authority before accepting an entry. Missing dependencies wait. A conflicting signed entry at the same writer sequence freezes that stream.

Signature and chain validation are separate from deciding which entries count. Excluded direct entries remain in the stream so later entries can arrive. New lease or grant information can recompute affected winners and creators. Ordinary record conflicts use whole-record last-writer-wins. A fork at the same signed sequence is a different error. Rejection and fork evidence remain in memory; accepted received entries are saved.

Source: Local entry validation

Signed membership grants

The publisher signs database roles. Read permits fetching. Submit permits proposals that create records or change records the member created. Write permits proposals against any record and direct writes under a covering lease.

Roles apply to the whole database. The publisher checks the current role when deciding a proposal. Reducing access does not undo publisher-incorporated records or end an issued lease early. A member stops signing directly when it learns of a reduction. Public any-read cannot be revoked through this node API, although low-level history and relay validation understand its revocation. Grant replies confirm local authoring, not relay delivery. Only the publisher can change grants.

Source: Signed membership grants

Received records and schema definitions

Received database registration

Accepting an open token saves the database, content key, publisher device ID, and optional local name. It marks an empty receiver store ready to open and wakes the relay worker.

The limit is 32 registrations. An older registration without a publisher device ID can use writer-wide discovery. List state becomes ready when held history has the signed birth; this does not prove every record was applied. Accepted received history is saved and replayed after restart; pending dependencies are fetched again. Read access no longer waits for the removed prefix.json marker.

Source: Received database registration

Signed schema definitions

The publisher signs schema definitions before the record entries that need them. Each sync turn also signs every new or changed definition in an open owned shareable store, including schemas with no records. Shared receivers load these definitions before applying records. Personal replay carries schema definitions in its sealed entries.

Only the publisher can sign schema entries. The background pass needs an open store, saved birth material, and an accepted birth. It does not bootstrap existing records. History keeps the definition with the highest signed position per namespace; loading checks its name and local compatibility. A schema entry does not supply alternate addresses, file bytes, or record metadata.

Source: Signed schema definitions

Received record access

The read API selects a registered received database and reads the records already in its local store by key. The obsolete durable-prefix file check has been removed.

A readable store or ready list row does not prove complete synchronization. Ready means the held history has a birth entry, even if later materialization fails. Before data arrives, reads can find no record or no schema. Alternate addresses are reconstructed. Shared files and arbitrary remote metadata remain unsupported. A Write member with a usable lease can write directly; other permitted changes use proposals.

Source: Received record access

Record materialization

The daemon loads signed schemas and writes winning records and alternate addresses at canonical hash or hash-range keys. Both stored author fields follow the winning writer. Repair restores history winners when local signing fails or a lease closing excludes a direct change.

A live winner needs a declared schema. An undeclared tombstone is skipped. Ranged keys use the schema’s range encoding; ranged hashes cannot contain U+001F. File bytes and arbitrary remote metadata remain absent. A record is skipped only when fields, alternate addresses, and both authors match. Writes still use checked local revisions. Accepted received history is saved. Retry markers remain in memory. Repair uses the same record shape and can fail; failures are logged.

Source: Record materialization

Member upload status

A received database listing reports publish.pending and publish.lastAttempt. Pending is the last observed count of log entries after the upload cursor. The last attempt records a time, outcome, and relay status when available.

The report lives in memory and resets on restart. Pending is null until observed; the list itself does not open a store. A failed attempt does not refresh the pending count. An upload refusal keeps the proposal queued and changes no record. Confirmed means relay storage of the observed log, not publisher acceptance or delivery to every reader. Owned database listings omit this report. A Read or revoked member with queued entries reports the hold without asking the relay. Pulls and other databases continue. An unexpected 403 holds uploads for 30 seconds or until the grant or lease changes.

Source: Member upload status

Signed personal checkpoints

Snapshot capture

LastDB holds the write gate to pin the record and file stores with their applied stream heads. The upload reads that saved view while later writes can continue. Local file references are verified and sealed into a private snapshot file store.

Normal capture waits for all local entries to be acknowledged and pending replay and file deletion work to settle. The first cut survives restart and is released after publication is recorded; preparing it can fail startup. Initial and ordinary manifests allow 4,096 files. The initial cut caps each file at 5,000,000,000 bytes (5 GB); relay limits also apply. A local record file is limited to 33,554,403 bytes so its sealed snapshot copy fits one native value.

Source: Snapshot capture

Personal snapshot

The worker freezes a consistent native checkpoint, then one background task per home hashes and uploads its files and manifest. It signs the snapshot entry with the device positions those files cover. Ordinary entry sync continues during the upload.

Personal database only. Manual capture waits for settled sync; --wait stops waiting after 30 minutes. There is one upload task per home and no snapshot queue. A new manual request during upload waits for a fresh cut afterward. The required first snapshot still blocks later personal uploads. A new checkpoint must cover every position in the previous one. Saved upload reuse is bound to the relay origin. Entries cover at most 1,024 device positions; manifests cap at 16 MiB. Native encrypted files travel unchanged; paths, sizes, hashes, and positions are visible. One file is one blob without resumed transfer. A size refusal blocks that snapshot. Publication triggers covered-log cleanup, retaining two checkpoints and all cloud files.

Source: Personal snapshot

Snapshot status

The node saves what it last published or installed: the snapshot time, files, bytes, relay origin, sequence, and covered progress. Status reads that local record, including after restart.

This is local knowledge, not a fresh relay inventory. A size refusal suppresses automatic retries for ten minutes in this process; restart clears that hold. A required first snapshot still waits through the hold. Failed status-file persistence is logged after publication, so an old status alone does not establish relay loss. The active upload reports files and bytes sent. Manual requests can override the ten-minute size-refusal hold. Saved checkpoint reuse is checked against the selected relay origin.

Source: Snapshot status

Local file reference

LastDB hashes a regular file outside the node home and stores its marker on the record. Each home keeps its own path catalog and lock.

The API links an existing file; it does not accept uploaded bytes or inline placement. Registration refuses files over 33,554,403 bytes (32 MiB minus 29 bytes), before hashing. Deletion leaves the original alone. Keep it available and unchanged. Snapshot capture verifies each reference, then seals a copy into a private file store. Restore owns those bytes and does not need the original path. The same size limit ensures the copied file fits a native value.

Recovery and remaining delivery limits

Personal database restore

The recovery phrase derives the personal database identity and keys. Restore installs the newest advertised signed snapshot when one exists, tries the immediately previous checkpoint if installing the newest fails, then replays each device after the positions it covers. Without a snapshot it replays from the beginning. It works in private staging and closes the stores before publishing an unused destination.

A snapshot preserves the native personal records, metadata, alternate addresses, deletion state, and included files. Later per-change entries still omit arbitrary record metadata. Named shares, installed apps, credentials, and never-uploaded data are outside this restore. Invalid replay streams can be frozen and skipped without failing the whole command. Failure to install the newest checkpoint triggers one attempt at the immediately previous sequence. That checkpoint must pass the same checks. If both fail, restore returns the original error; it does not search all older checkpoints. The chosen relay is not saved in the new home. A device whose required history was removed must restore into a fresh home; it does not reset itself.

Source: Personal database restore

Personal replay checks

Personal replay checks the owner signature, device, predecessor, sequence, and order. It opens the sealed payload, validates its shape, and verifies attachment bytes. A record change and its next stream head commit together.

Frozen streams are stored and skipped, including during restore. Freezing returns success for that stream, so command success does not certify that every advertised entry was recovered. Malformed payloads, absent required file references, and oversized file markers freeze the stream. Transfer failures stop the turn for retry. Schema puts and drops follow their own winning stamps; older ones cannot undo newer schema changes. Schema removal is paged and idempotent; its head advances after removal completes. A snapshot supplies a starting point, not automatic repair for a frozen stream or missing later entries. Snapshot installation separately checks the owner signature, advertised entry hash, manifest, native paths, file lengths and digests, and covered stream heads.

Source: Personal replay checks

Recovery identity and connection

The recovery phrase supplies the owner signing seed, deterministic personal database ID, and read key. Restore creates a new device ID. Its relay URL is used for reconstruction and is not saved in the new home.

No account context check or saved credentials are required when the relay URL is supplied. An optional --data-dir supplies only a saved relay address. Later sync still needs a relay override or connection for the new home. Restore enables capture, so later writes can remain queued while no relay is configured.

Source: Recovery identity and connection

Sealed personal attachments

Personal sync reads the file held by an accepted write, encrypts it for that signed entry, and uploads the sealed blob before the entry. A receiving device verifies the download, decrypts it, and stores it under local encryption before applying the record.

Sealing and opening buffer the complete file. A record file may hold at most 33,554,403 bytes; an incoming marker above that limit freezes its stream. Missing or invalid bytes prevent application. Replay can skip downloading an entry whose record and every attachment slot have already lost, when no local write is pending. Inline bytes can travel in the sealed body. Shared attachments and bundle loading remain unconnected. Covered-log cleanup leaves all cloud files and manifests. Native snapshots transfer their encrypted files without the per-entry sealer.

Source: Sealed personal attachments

Covered log cleanup

After publishing a new personal snapshot, the node asks the relay to remove entries covered by the previous checkpoint. The relay checks that signed checkpoint and its stream hashes. It keeps the two newest checkpoint entries and the history needed after the older one.

A fresh restore can start from a checkpoint. Keeping every earlier change in the relay log is no longer necessary.

After checkpoint 3 is published, cleanup uses checkpoint 2. Checkpoint 1’s log entry can leave, while its manifest and all snapshot files remain stored. A device asking for removed history receives 410 and must restore into a fresh home.

Only the owner can request cleanup. Shared histories are excluded. The database birth, stream heads, and last removed sequence and hash remain. Repeated old entries count as duplicates without returning to the log. ExeMem removes at most 1,000 entries per call and subtracts their stored entry bytes once; blob bytes remain stored and billed. The node makes at most 64 calls after a new snapshot. Failure leaves the published snapshot valid; further cleanup waits for a later new snapshot. No automatic device reset or cloud-file deletion is supplied.

The relay derives removal positions from the stored checkpoint, not from caller-supplied positions. It checks the owner signature, checkpoint identity, and covered stream hashes. Blob transfers

The client obtains a temporary address and streams the file. Uploads and downloads can retry transport failures and HTTP 500, 502, 503, or 504, for up to three attempts. Downloads publish their final path only after length and SHA-256 match.

A lost connection or short download retries from the start. Retry waits have 0.5- and 1-second ceilings with jitter. A bad checksum or nonretryable HTTP answer ends the call. Errors omit signed URL queries and fragments.

Connections allow 10 seconds. Downloads have a 30-second read limit. Uploads allow 30 seconds without progress while body bytes remain, then up to 64 extra seconds for buffered bytes and an answer. There is no total upload deadline. Progress counts transport bytes, not confirmed storage. Each upload reads from its own file position. Retries resend the whole file; multipart and resume are absent. A stored digest needs no second upload. ExeMem permits a blob up to 5,000,000,000 bytes (5 GB); a near-limit upload is not proved. Record attachments have the smaller 33,554,403-byte limit. Native snapshot run files have separate bounds.
