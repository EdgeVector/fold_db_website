Cloud source and future design

Source review: 26 October 2026. Earlier shared-data design: 6 October 2026.

Native backup code exists. Its release flag stays off by default. New V2 backup work also needs account readiness. Older cloud clients and automatic backup are removed. This review does not establish a deployed service or a successful recovery.

One data model across the layers

Memory serves current logical records. A native write saves a complete disk snapshot before memory publication and the ack.

Cloud backup is a separate operation. A local ack does not confirm a cloud copy.

The layers preserve the same data relationships. Their files and completion times differ.

Latest source review

The review covers 139 commits after October 21, through 99b57248. This pass examined eight commits and the changed LastStore code.

The new explanations cover compact record values, atom protection in each disk format, checked conversion, merge thresholds, and restart behavior.

Two disk formats, one logical model

Packed storage remains the default. An absent or empty home can explicitly select disk format v2 through LASTDB_DISK_FORMAT=2.

With the node key, this option also converts a supported packed home. Both formats save before memory publication and the ack.

The run layout separates records in disk-run from file blobs in disk-cas. Each home has its own encrypted CURRENT list and ordered files.

Reads check newer files first. Small filters can rule out absent keys. A match still needs a check of the actual key.

One worker combines files in both homes after commits. Startup also resumes needed merges. Eight files in a level trigger a merge.

A separate compact base holds the oldest current values in non-overlapping key ranges. Base compaction removes obsolete values and physical delete markers.

Run keys must fit 64 KiB, including the collection prefix. The separate packed larger-key option does not apply.

Current native backup, restore, and packed maintenance require packed storage. Disk format v2 and V2 cloud backup name different features.

Base compaction uses counted bytes

The worker counts older values hidden by new records and physical delete markers. Counts include encoded keys and stored values before block compression.

Base work starts when newer files exceed one sixteenth of record bytes, or obsolete bytes exceed one eighth. Each trigger also exceeds 1 MiB.

Each step replaces a small part of the base and saves its progress in CURRENT. The next step uses that saved boundary.

Old readers retain their files. New writes, reader holds, and delayed compaction can use extra space. These thresholds are not a filesystem-size guarantee.

Base file targets range from 256 KiB to 1 GiB. A large record can exceed a target.

The worker waits up to two seconds when reads retain more than one sixteenth of current file bytes, with a 1 MiB minimum.

Long reads can retain files after that wait. No fixed total disk-size guarantee follows from these controls.

Compact records before block encryption

Run homes try shorter forms for repeated field names, IDs, integers, and timestamps. Reads reconstruct the exact original record bytes.

The encoder checks its output before use. Only compact JSON objects or arrays up to 1 MiB qualify.

Other values keep their original bytes plus a format byte. Run values must fit below 32 MiB before compact encoding.

The file block can then use compression before encryption. Earlier run homes with untagged values are refused; no automatic upgrade occurs.

File bytes reach disk before their references

A split commit saves new file blobs, then other record changes, then file blob deletes. Memory publication follows the required disk work.

The two homes do not share one atomic disk commit. A crash or failed file delete can leave unused file bytes.

This order protects required files. The separate layout prepares for different cloud stores, but current backup code does not transfer run homes.

Explicit packed-to-run conversion

Conversion locks a supported packed home with key format 4, 5, or 6. It transforms each record for the run format.

It opens atom content, preserves a valid replay cutoff, and writes both run homes. It reopens them and compares every transformed record.

An unfinished switch rolls back on the next keyed open. Conversion needs extra space and one volume for the source and retained files.

Only a successful check permits the switch. The original packed files stay beside the source. Hidden records from older formats refuse conversion.

Incomplete recovery state and an existing retained-files folder refuse conversion. A stopped partial copy is removed on a later packed open.

The V2 backup path in current code

This path captures packed files. It does not support a run home.

  1. Capture one exact disk snapshot before any backup file upload. Retain its required files while local writes continue.
  2. Check every required file inside the captured packed state. Separate stored records into byte pieces and obtain verified service receipts.
  3. Publish an encrypted manifest that describes the record pieces, their order, and receipts. Save the accepted result in the backup job.
  4. Release the source hold only after a confirmed terminal result permits it.

The saved job can resume the same source after a process exit. It must not silently choose a newer disk state.

The new path preserves the records from one snapshot. Restore rebuilds physical files. Older V2 file-copy backups retain their existing reader.

Older cloud paths are removed

V2 is the current manual backup and restore path. The older upload, restore, replay, and automatic backup workers are removed.

V2 first checks retained V1 job and capture records. Incomplete work or unreleased source bytes refuse a new backup.

The check only reads those old records. It cannot resume, close, or repair the retired job.

Startup also refuses saved state from an interrupted retired cloud repair. It leaves recovery as a separate explicit action.

The old Cloud Off action pauses a credential file. It does not cancel an explicit V2 job; that job has its own Close action.

A checked restore to a fresh destination

  1. Select one accepted backup. Save its exact identity before file requests.
  2. Check the encrypted manifest, piece destinations, lengths, hashes, and reconstruction order. Rebuild fresh packed files and compare the complete record digest.
  3. Check the complete snapshot, atoms, file references, and saved-state boundary. Read each atom and its encryption key from that same selected state.
  4. Publish the verified destination without cloud activation.

Restore refuses an existing destination. A partial record import needs a fresh session; a completed checked import can resume. The walkthrough performs no recovery.

Restored account access is a separate DEV action

The reconnect action checks the completed restore receipt and existing account identity. The restored home must be inactive.

It obtains access to the same account without a new identity or a change to recovered data. It refuses primary and archive homes.

The saved credentials remain paused. Reconnect does not start a backup. It can recognize a retained V1 receipt or a current V2 receipt.

Large files need complete local coverage

An atom can reference a file blob. New file keys depend on the private account key and original file hash.

The protected atom carries the file key. The file address identifies the encrypted bytes. Supported older files keep their original keys.

Backup needs exact coverage for each main file, thumbnail, and poster. Bytes already inside packed files need no second copy.

V2 requires those bytes inside the captured native files. Remote-only files refuse; the old external-file transfer path is removed.

Manual V2 byte backup

A manual job retains one exact saved state. It checks transfer receipts before it publishes an accepted backup.

New jobs separate record metadata, other record bytes, file blob bytes, and their reconstruction order. File blob bodies use B2; the other pieces use R2.

Metadata and reconstruction order receive encryption. Stored record bytes keep their existing protection; some control values can remain readable.

V2 currently requires external file dependencies to have coverage inside the native file set. Unsupported dependencies refuse.

Resume keeps the exact saved request and capture. Uncertain remote work retains its file hold until a confirmed result permits release.

The V2 release switch stays off by default. Account permission is separate. No automatic backup scheduler remains.

Two destinations, one accepted backup

New jobs require account access to both Cloudflare R2 and Backblaze B2. The client selects a destination for each object.

R2 uses a create-once upload. B2 grants one temporary upload part; the service owns completion. Receipts bind the destination, hash, and length.

The public client descriptor contains no native layout details. The encrypted root holds the recovery identity and record format.

Record byte pieces hold at most 64 MiB. Metadata pieces hold at most 1 MiB before encryption. Larger keys reduce parallel work when necessary.

Supported larger-key checkpoints now pass the client check. Unsupported feature bits still refuse. This review does not verify deployed cloud services.

Backup status does not promise current coverage

Node status reports manual V2 work, a blocked job, and whether an accepted backup is recorded.

A historical receipt does not prove that current writes reached the cloud. The health check keeps unmeasured freshness unknown.

No local receipt does not prove that an external backup command did no work. Check that command separately.

The old backup-age and recovery-window claims are removed. No automatic scheduler starts.

Backup without another node

The standalone command uses existing native files. It creates no second daemon or database writer.

Progress stays in a separate private directory. A durable file hold is the permitted source change.

A separate credentials-only setup can register the same account for an explicit environment. Credentials remain paused; registration alone does not enable backup.

Restore counters before normal use

V2 restore selects an exact accepted backup and refuses an existing destination.

Normal writes and cleanup remain blocked until complete checks match records, references, counters, and files.

An interrupted record restore keeps its marker after restart. Counter checks do not silently repair a mismatch.

Encryption and disk format now have separate checks

Packed format 6 retains atom content encryption. Only local file blob records receive an extra storage encryption layer.

Tips, counters, and schema definitions can remain readable. A small protected record checks the account key before use.

Packed startup refuses older formats. A separate inactive transfer target can convert supported format 4 or 5 records.

That packed-to-packed converter refuses format 5 with a replay cutoff. The separate packed-to-run converter preserves a valid cutoff.

The new private-key range implementation remains separate from active storage. Its ordered terms reveal order, equality, length, and other information.

An optional packed larger-key format supports future conversion targets. Existing homes do not select it automatically.

Run atoms use plain records without separate content encryption or a molecule key bundle name. Their file blocks protect them on disk.

Run homes derive separate keys for records and file blobs. Data blocks, lookup blocks, and CURRENT use encryption. File blob protection remains separate.

Block checks bind bytes to their file identity and position. File sizes, clear footers, and some layout facts remain visible.

Date values and retention

Date fields require valid YYYY-MM-DD text. DateTime fields require an explicit offset and at most nine fractional digits.

The value stays as supplied. Neither type can serve as a hash or range key yet. Ordinary string keys keep their existing rules.

Retention backfill can replace an old arrival-time age with the current tips’ original write time. Existing records can then expire.

Dated range discovery uses pages of at most 256 keys. It continues past undated keys and short pages until an empty page.

Range order and next-page checks

A read captures its schema, field types, and stored key format. Its next-page cursor includes a compatibility tag for those facts and query options.

Return the whole cursor unchanged. A tag mismatch refuses continuation and requires a new first page.

Current keys retain text order, where 10 comes before 2. Older untagged cursors remain accepted for that order.

The tag does not grant access or hold a saved data snapshot across pages.

Separate code defines typed order and plans conversion of a supplied key set. It refuses collisions such as integer keys 02 and 2.

A separate inspection now checks complete source keys from one stopped home. Neither the plan nor inspection publishes a conversion. Date keys remain refused.

Range conversion inspection keeps the source unchanged

An explicit command inspects a stopped development home, in packed or run format. It holds one saved state and checks the account key.

It checks schema declarations, current tips, Delete barriers, history references, and retained keys. It reports collisions and missing or incompatible definitions.

The default bounds are one million metadata records, 128 MiB of metadata, and 64 KiB per key. Exceeding a bound refuses inspection.

Primary and archive homes are refused. The report states that database conversion and activation remain incomplete. It creates no writer or new disk format.

Three different delete markers

  • A logical Delete barrier blocks old replay. Its removal requires an explicit saved replay cutoff.
  • A molecule generation marker hides an older generation entry. Explicit cleanup can remove it when no active or prepared generation needs it.
  • A run-file marker hides an older physical value. Base compaction removes it when no older value can return.

Molecule marker cleanup reviews one named molecule in pages of at most 256 markers. Execution is explicit and does not change the replay cutoff.

Future design: a shared database

The design gives authorized members access to shared encrypted data. A copied schema can reference the same molecules and atoms.

Members need the correct keys and access grants. A schema copy alone does not deliver files or grant another device access.

Simultaneous cloud writers need a defined frontier, conflict rules, and retention rules. The guide treats this behavior as future design.

Future design: a guaranteed write

A proposed guaranteed write requires a cloud grant before success. Current local writes confirm disk completion without that grant.

The exact cloud acceptance and recovery contract needs implementation and proof. The guide does not present it as an available write mode.

Services around the database

  • The schema service supplies definitive schema definitions.
  • Cloud access authorizes explicit V2 backup work.
  • Future design: protected messages carry invitations, key grants, and share notices.
  • Future design: a shared file service holds encrypted file bytes for authorized members.
  • The app registry describes releases and their LastDB compatibility.

Local encrypted export remains available

An owner request selects records by keys and includes their required local file bytes. LastDB signs and encrypts the result for the supplied recipient.

The response contains the protected package. The caller handles delivery. This route sends no message and uploads no object.

Recipient enrollment, new delivery staging, and the old message sender are removed. Missing local bytes cannot use a cloud fetch fallback.

App compatibility now checks declared formats

JSON app manifests can declare request and notice format versions. The installer checks those versions against the node’s supported range.

The optional LastDB version requirement remains. The TOML path checks that requirement. An absent declaration does not prove compatibility.

The signed registry can select a release by supported formats. It prefers an exact build match; entries without format declarations still need that match.

Local development app installs

The install command accepts --from, --rev, and --dev together. It reads the chosen commit’s manifest and checks declared format versions.

The installer clones the origin URL when available, or the local repository otherwise. The selected commit must exist at that source.

The saved receipt records the exact commit and development status. Uncommitted edits and signed-release status do not come with this path.

Questions that remain in the design

  • How does one atom use keys when it belongs to databases with different encryption keys?
  • Which range, recipient, and file metadata can the cloud see?
  • Which frontier and retention rules permit simultaneous writers?
  • What permits cloud file removal after a member leaves or a device stays offline?
  • What result does a read return when a key is absent locally and the cloud is unavailable?
