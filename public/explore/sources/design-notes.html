Local storage and authorship

Record

A record holds one schema’s fields, primary key, named alternate addresses, one revision, and database-set authorship. Replacement supplies the complete desired state. Omitted fields disappear.

The complete encoded record has a 64 KiB limit, including keys, alternates, one write stamp, authorship, metadata, and file markers. Blob and inline file bytes stay separate. A live record can have no payload fields.

Source: Record

Record authorship

Local writes set created_by at creation and updated_by on each change. Personal sync uses native replay. Shared-history materialization sets both fields to the winner, or to the proposing member for an incorporation. Shared history separately remembers the earliest creator.

Ordinary local and native personal replacements retain original created_by. The shared materializer copies the winner into both author fields. Shared proposal ownership uses the earliest accepted record position, not arrival order or stored created_by. Arbitrary remote metadata is omitted.

Source: Record authorship

Warm set

A read by key checks the warm set first. A disk fetch can keep the complete decoded record for a later call.

The default warm limit is 256 MiB. It covers decoded records, their keys, metadata, and file markers. Schema definitions and file bytes stay outside this charge. The least recently used unheld records leave first. Older read views and private writes use disk. A range page can admit its selected records without fetching them a second time.

Source: Warm set

Flush

A flush sends prepared changes through the native disk queue. Requests can share one complete disk commit before each receives success.

With capture enabled, accepted bodies reach the spool before memory publication and the ack. Missing entries or a full spool refuse progress. Personal /v1/write then wakes sync; it does not sign synchronously. Owned shareable /v1/write still mirrors after the local commit and can fail that later API step. Local success never confirms a cloud copy.

Source: Flush

Run block encryption

Separate derived keys protect each record and record-file home. Owned named databases derive their content keys from the node signing seed and database UUID. Received Share publications use their supplied content key.

Block compression skips inputs below 256 bytes. It is kept only if it saves at least 64 bytes and 10%, including its length header. Encryption still applies when compression is skipped. File sizes, clear footers, and some layout facts remain visible. Personal relay entries use a separate sealed payload. Shared entries still serialize clear fields. Neither transport rule changes local run encryption. The run reader loads and authenticates a complete block before exposing decoded bytes. Decompressed output is capped at 64 MiB; the former two-pass bounded reader is removed.

Source: Run block encryption

Personal sync and shared logs

Personal database identity

The owner’s identity seed deterministically derives the personal database ID, birth material, and read key. Every owner device uses the same signing key and database, with its own device ID.

This identity rule applies to the main personal database. Named sibling databases remain separate. An older registry with a different personal ID fails to open; the code supplies no automatic conversion. Possession of the phrase grants the owner identity and read key.

Source: Personal database identity

Personal write spool

The personal store captures an encrypted body beside each record or schema commit when a relay is configured. An existing spool or signed restore also enables capture. The background worker signs and sends these saved changes.

Each body is capped at 1 MiB. A captured record request is limited to 1,024 mutations. Bodies and copied files share a 1 GiB spool cap; signed retry files are separate. Gaps block progress. Once capture starts it stays enabled across restarts, even without a relay. Fresh offline homes capture nothing. Named sibling and received stores no longer create unused spools. Enabling sync does not take an initial snapshot of older data.

Source: Personal write spool

Personal device sync

The worker signs sealed entries from accepted local writes, saves the exact batch, and uploads its blobs before its entries. It lists the owner’s device streams and reads only entries after each saved head. Native replay chooses and writes record winners.

One outbound page has at most 90 entries and a roughly 8 MiB payload target. Incoming pages hold at most 90 per device. Only the main personal database uses this path. Earlier uncaptured data has no initial snapshot. A relay needs log.streams and blob routes; ExeMem support is not established by this review. Arbitrary record metadata is omitted.

Source: Personal device sync

Personal sync progress

One native metadata row holds each device stream’s applied sequence, hash, order, and frozen flag. A remote record or schema put commits with its next head. The outgoing signed batch is saved separately for exact retry.

Schema removal finishes its paged, idempotent deletion before advancing the head. Invalid streams can freeze and remain skipped. Outgoing JSON has a 64 MiB read/write cap; sealed retry blobs occupy additional disk space. A relay receipt allows confirmed spool entries to retire. Shared databases still use separate history files.

Source: Personal sync progress

Sealed personal payloads

Before signing, personal sync encrypts each accepted body and external file with AES-256-GCM and a fresh nonce. The database ID, owner key, device ID, and sequence are authenticated with the ciphertext.

Entry headers, stream identity, order, lengths, and sealed blob digests remain visible. Personal file encryption still buffers complete bytes. Shared record payloads use clear signatures and do not use this sealer.

Source: Sealed personal payloads

Whole-record last-writer-wins

A signed entry’s order value uses the write time in milliseconds, raised above its predecessor and cited entries. The greatest order, node key, and device ID wins. Native personal replay also uses the entry sequence as a final tie-breaker. Deletions carry an order too.

The order comes from clocks, not a trusted global time. Values at or beyond 1 January 2100 are rejected. Personal replay uses the captured commit time and includes alternate addresses and attachments in the winning record change. Pending local edits keep their visible state until settlement. Shared records still use the limited materializer. Local writes require absence or a matching revision; shared members propose for publisher approval. Losing values have no separate durable conflict archive.

Source: Whole-record last-writer-wins

Owned write mirroring

After an owned shareable /v1/write commits, the node signs each mutation. It first signs the schema definition when that namespace is new or changed in its history. It appends the signed entries to the authored log, then wakes the relay worker.

The selector can be the owned database name or ID and must resolve to saved birth material. Personal writes use the spool instead. Other shared write routes are not connected by this mirror. Hash and hash-range keys work, except a ranged hash containing the unit separator is skipped by planning. Alternate addresses, arbitrary metadata, and files are omitted; fields are signed in clear. A signing failure attempts history repair before returning 503. Previously signed entries remain effective. Repair can fail. The record batch and signed entries are separate saves.

Source: Owned write mirroring

Shared logs and upload cursor

Each shared database saves locally signed entries in authored.json and accepted entries from other streams in received.json. uploaded.json counts confirmed authored entries. Restart combines both logs by order value. Personal sync instead uses its native spool and stream heads.

Files live under log-sync/<database-id>/. Each log has a 16 MiB limit. Authored entries rewrite their log on append; received entries rewrite theirs when the accepted count changes. A failed received save leaves entries in memory and retries on a later pull. Missing files mean empty logs or cursor zero; invalid or unreadable files error. A cursor beyond its log is refused. Only a full relay stored count advances it. Pending entries and receive page cursors are not saved. This is separate from the native record transaction.

Source: Shared logs and upload cursor

Signed history

A database history contains signed entries from node and device streams. Each stream starts at sequence 1 and links each later entry to its predecessor. Cross-stream references name entries the writer has seen.

Personal databases use the native write spool and saved stream heads, without retaining a full in-memory history. Shared databases save authored and received logs and rebuild history in order-value order. Their missing dependencies, rejection evidence, and repair retry markers remain in memory. Snapshots, log-prefix cleanup, and automatic lagging-device reset remain removed.

Source: Signed history

Worker, connection, and status

Background relay worker

Each turn uploads shared logs, pulls owned shares, and decides member proposals. It then sends the personal spool and reads the owner’s other device streams. A second shared upload sends publisher decisions before received-share work.

LASTDB_RELAY_URL overrides the ExeMem address in saved credentials. Without either, the worker idles. A wake marker ends a clean pause within the next 50 ms poll; errors keep the two-second backoff. Personal send and receive are both attempted. Shared databases retain their own mirroring, discovery, and attachment limits. A relay must implement the routes this worker uses.

Source: Background relay worker

Relay client

The node signs log append, read, stream-list, and blob requests with its identity. The signature binds the method, path, protocol version, database, body hash, time, and nonce.

The worker uses one relay URL: LASTDB_RELAY_URL overrides saved credentials. Personal content is encrypted before this client sends it; shared record payloads are still clear. File transfers stream from and to disk. A successful append confirms stored entries, not delivery to every device or complete recovery.

Source: Relay client

Saved cloud credentials

One protected file holds the service address, account access key, and optional checked connection. Account commands, schema-service selection, and the relay worker use its reader.

The reader requires an ordinary private file owned by the current user. It rejects links, oversized files, and empty keys. The saved service address is now the default relay URL; LASTDB_RELAY_URL can override it. Personal entries come from the native spool; shared signed logs remain separate. Their presence is not proof of relay access or backup coverage.

Source: Saved cloud credentials

Cloud readiness

The current database_cloud_state helper reports Enrolled when saved cloud credentials can be read, and NoAccount when they are absent. Grant and link actions use this check.

The previous signed database-create exchange, 30-second enrollment wait, and per-database live confirmation cache are removed. wait_for_enrollment now returns immediately. Enrolled does not establish remote database readiness.

Source: Cloud readiness

Node status

Status reports the running build, uptime, socket workers, and cloud state. Upload turns now record each owned database’s log length, confirmed position, and error. A clean upload clears its upload error; a clean whole turn clears the top-level last_error.

The old detailed backup policy and progress routes remain removed. Received listings have a separate process-local publish report. A clean upload does not clear payment_hold or prove receive completeness. Unreadable state can report fallback counts alongside an error. No error or zero pending entries is not proof of complete backup.

Source: Node status

Finding signed streams

Shared writer discovery

For a shared database, the worker reads known publisher devices after their last accepted entry. If none is known, it asks for all devices under the publisher key. Current and historical Submit or Write grants identify member writer keys.

Writer-wide discovery still reads from sequence 1. Once some publisher devices are known, this shared path does not independently discover every other publisher device. Accepted received entries are saved; pending dependencies and page cursors are not. Alternate addresses, arbitrary metadata, files, and bundles remain incomplete here. Personal sync uses the new stream-list route instead.

Source: Shared writer discovery

Reference relay

The reference relay keeps log entries by database, writer, device, and sequence. A signed birth and publisher grants supply its access index. It also stores blobs by digest. The log.streams route lists a writer’s devices and each contiguous sequence head without rereading all entries.

The relay checks request signatures and grants; it does not run the complete AcceptEntry algorithm. Appends and reads cap a batch at 90. A read without device_id pages all devices under one writer key. Public any-read still requires a signed caller. A revoked member may request a single publisher device stream to learn its signed revocation; writer-wide reads remain refused. This source does not establish an ExeMem deployment or provider placement. Stream discovery uses the same grant check as writer-wide reads. The reference relay rebuilds its head map on startup. Signed JSON requests have a 64 MiB limit; file transfers stream separately and check their declared size and digest. The checked CI workflow skips log.streams against ExeMem until that route is supported.

Source: Reference relay

Member writes and publisher checks

Member changes

Every member changes a received database through a signed proposal. The member’s local records stay unchanged until it pulls a publisher acceptance. The ordinary /v1/write route refuses received databases for every role.

Current Submit or Write permission and the app’s schema access are required to submit. Read members cannot propose. A matching expected record state is still required. Direct member entries and member bundles are refused by local validation and the reference relay. The former direct-write path and permission-cutoff undo are removed.

Source: Member changes

Publisher incorporation

After pulling member streams, the publisher checks each unresolved proposal against its current role, schema, and expected history entry. Submit members must own a record they replace or delete; Write members may change any record. It signs an acceptance or a not-accepted decision.

Create requires no live record. Replace and delete require the expected winning history entry. Hash and hash-range keys work without alternate addresses or files. An accepted change is saved locally, then signed as data citing the proposal. A refusal is a signed heads entry citing the proposal and carrying current publisher stream tips. Storage or signing failures leave the proposal undecided for retry. If signing fails after a local write, the node attempts to restore the history winner. That repair can also fail and log a warning. These saves are not atomic. The old configurable per-schema settings remain removed.

Source: Publisher incorporation

Proposal submission and status

The submissions route accepts a UUID idempotency key and saves a signed proposal. Status is submitted, published, not_accepted, or unknown, derived from the local ledger and history. A publisher data citation means accepted; a publisher heads citation means not accepted.

The envelope carries mutation_type, expected, and optional record fields, up to 64 KiB. Hash and hash-range keys work; ranged hashes cannot contain U+001F. Non-null files are refused. Submit and Write members may propose; the publisher checks their current role and record conditions. HTTP 202 and relay storage do not mean published. Published and not_accepted are final decisions for that proposal. Submitted can mean the decision has not arrived yet. The idempotency ledger is saved separately from the signed log.

Source: Proposal submission and status

Local entry validation

AcceptEntry verifies the signature, database binding, predecessor, observed dependencies, order value, and writer authority before accepting an entry. Missing dependencies wait. A conflicting signed entry at the same writer sequence freezes that stream.

Protocol validation is implemented. The publisher separately checks proposal permissions and record conditions. Ordinary accepted record changes use whole-record last-writer-wins; a forked signed chain is a different error. Rejection and fork evidence remain in memory. Accepted received entries are saved. Permission reductions no longer recompute record winners; members do not author direct record changes.

Source: Local entry validation

Signed membership grants

The publisher signs database roles. Read permits fetching. Submit permits proposals that create records or change records the member created. Write permits proposals against any record. Only the publisher’s signed acceptance changes shared records.

Roles apply to the whole database. The publisher checks the current role when deciding a proposal. Reducing or revoking access does not undo already incorporated records. The wire format still carries cutoffs, but the current code does not use them. Public any-read cannot be revoked through this API. Grant replies confirm local authoring, not relay delivery. Only the publisher can change grants.

Source: Signed membership grants

Received records and schema definitions

Received database registration

Accepting an open token saves the database, content key, publisher device ID, and optional local name. It marks an empty receiver store ready to open and wakes the relay worker.

The limit is 32 registrations. An older registration without a publisher device ID can use writer-wide discovery. List state becomes ready when held history has the signed birth; this does not prove every record was applied. Accepted received history is saved and replayed after restart; pending dependencies are fetched again. Read access no longer waits for the removed prefix.json marker.

Source: Received database registration

Signed schema definitions

The publisher signs schema definitions before the record entries that need them. Each sync turn also signs every new or changed definition in an open owned shareable store, including schemas with no records. Shared receivers load these definitions before applying records. Personal replay carries schema definitions in its sealed entries.

Only the publisher can sign schema entries. The background pass needs an open store, saved birth material, and an accepted birth. It does not bootstrap existing records. History keeps the last accepted definition per namespace; loading checks its name and local compatibility. A schema entry does not supply alternate addresses, file bytes, or record metadata.

Source: Signed schema definitions

Received record access

The read API selects a registered received database and reads the records already in its local store by key. The obsolete durable-prefix file check has been removed.

A readable store or ready list row does not prove complete synchronization. Ready means the held history has a birth entry, even if later materialization fails. Before data arrives, reads can find no record or no schema. Publisher device discovery, alternate reconstruction, and files remain incomplete. Every member uses proposals to change this database; /v1/write is read-only here even with a Write role.

Source: Received record access

Record materialization

The daemon loads signed schemas and writes winning JSON records at hash or hash-range keys. Both stored author fields follow the winning writer. A separate repair path restores history winners at keys whose local write could not be signed, deleting a key with no history record.

A live winner needs a declared schema. An undeclared tombstone is skipped. Ranged keys join hash and range with U+001F; the schema tells the adapter how to split them. Alternate addresses, file bytes, and arbitrary remote metadata remain absent. A record is skipped only when fields and both authors match. Writes still use checked local revisions. Accepted received history is saved. Retry markers remain in memory. Repair after a signing failure uses this same limited record shape; repair failure is logged.

Source: Record materialization

Member upload status

A received database listing reports publish.pending and publish.lastAttempt. Pending is the last observed count of log entries after the upload cursor. The last attempt records a time, outcome, and relay status when available.

The report lives in memory and resets on restart. Pending is null until observed; the list itself does not open a store. A failed attempt does not refresh the pending count. An upload refusal keeps the proposal queued and changes no record. Confirmed means relay storage of the observed log, not publisher acceptance or delivery to every reader. Owned database listings omit this report.

Source: Member upload status

People controls and consent

People app

People is the separate command-line app for verified contacts, shared album setup, circles, consent codes, and access requests. It asks LastDB for signed grants and reads chain views.

People uses the databases extension and its separate @lastdb/people-client wrapper. It has no browser interface. Shared databases use whole_database mode. The old share_config, set_share_config, and seal_invitation calls are removed. Grant actions on LastDB currently require owner context. App-socket compatibility and automatic received data delivery are not established by this source review.

Source: People app

Shared album setup

People’s shared-albums v1 setup prepares Album, AlbumItem, Photo, and Comment in a whole-database share. It reserves a 64-hex database ID and verifies exact schema definitions.

This is the one supplied setup. Stored schema names still use social/. The database-wide memberWrites file and its setup confirmation step were removed. Setup does not grant roles or establish content sync. A preselected database ID currently has no automatically minted birth material in LastDB, so schema setup alone is not proof of a usable grant chain.

Source: Shared album setup

Reusable circles

A circle keeps verified people and links them to whole-database shares. People previews changes and asks LastDB to author signed grant or revoke entries.

Read presets map to read; nonempty schema presets and all map to submit. A direct person grant can choose write. A schema-named preset is not a per-schema grant. People retains a 98-entry roster-plan cap and up to 50 circles. Changed previews need review again; outside grants need an explicit choice. Updates across people and databases are not one atomic transaction.

Source: Reusable circles

App sharing requests

An app saves a proposed circle link or person grant through People. The owner lists waiting proposals, previews the affected access, then approves or declines with the People command. People saves the outcome and tracks unfinished updates per database.

Requests use an existing owned whole-database share and a stable UUID. Database IDs are now 64-hex values. The same request UUID cannot name different content. Changed previews need review again. The list reads up to 64 indexed pending requests per page. These requests approve changes to access; they do not approve record proposals. Grant receipts describe locally authored signed entries, not completed relay delivery.

Source: App sharing requests

People consent codes

People wraps a locally minted LastDB open token with the database ID, publisher key, and grant receipt. The recipient supplies an independently verified publisher key before accepting it.

The wrapper is unsigned and not encrypted. It carries an open token containing the database content key, so it is sensitive. It is not the old sealed invitation and has no old 24-hour expiry contract. Accepting a new token enables publisher-stream pulling, but does not establish complete received data or readable records.

Source: People consent codes

Recovery and remaining delivery limits

Personal database restore

The recovery phrase derives the personal database ID, signing identity, and read key. Restore discovers the owner’s device streams, decrypts entries, and applies them through native replay in a private staging home. It closes the stores before publishing an unused destination.

Restore covers the personal database’s captured schemas, records, alternate addresses, deletions, and attachments. Arbitrary record metadata is not carried. It does not restore named shared databases or data never uploaded. Invalid streams can be frozen and skipped without failing the whole command; inspect the recovery checks. The chosen relay is not saved in the new home. Old --database, --stream, and --device-id options are removed.

Source: Personal database restore

Personal replay checks

Personal replay checks the owner signature, device, predecessor, sequence, and order. It opens the sealed payload, validates its shape, and verifies attachment bytes. A record change and its next stream head commit together.

Frozen streams are stored and skipped, including during restore. Freezing returns success for that stream, so command success does not certify that every advertised entry was recovered. Parsing or file-transfer errors instead stop the turn for retry. Schema removal is paged and idempotent; its head advances after removal completes. No snapshot fills gaps.

Source: Personal replay checks

Recovery identity and connection

The recovery phrase supplies the owner signing seed, deterministic personal database ID, and read key. Restore creates a new device ID. Its relay URL is used for reconstruction and is not saved in the new home.

No account context check or saved credentials are required when the relay URL is supplied. An optional --data-dir supplies only a saved relay address. Later sync still needs a relay override or connection for the new home. Restore enables capture, so later writes can remain queued while no relay is configured.

Source: Recovery identity and connection

Sealed personal attachments

Personal sync reads the file held by an accepted write, encrypts it for that signed entry, and uploads the sealed blob before the entry. A receiving device verifies the download, decrypts it, and stores it under local encryption before applying the record.

HTTP transfers use chunks and private temporary files. Sealing and opening still buffer the complete file; the personal parser caps it at 512 MiB. A missing or invalid blob prevents that entry from applying. Inline bytes can travel inside the sealed body. Shared attachments and bundle loading remain unconnected. Old snapshot-covered blob cleanup remains removed.

Source: Sealed personal attachments
