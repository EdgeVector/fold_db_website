Reviewed 21 November 2026 · LastDB 20559c69ccef32c4129070a37a97e6ec20fc9cc4

The signed-history protocol and grants exist. Received shares can now pull their named publisher stream. Owned shareable writes now mirror hash keys and fields. Fresh receiver reads, attachment transport, and automatic proposal incorporation remain unfinished.

Local storage remains the local contract

One schema owns each complete record and its explicit keys. Ordinary conditional writes still require absence or a matching revision. Format 15 stores records and record files in separate run homes. File additions precede the record commit; removals follow it. The complete disk state and memory publication precede the ack.

The record cap remains 64 KiB. The warm set defaults to 256 MiB and holds decoded records, not file bytes. A held record can keep it above that target. LastStore still retains at most 32 run readers per home. These are not total process-memory limits.

Local encryption, keyed reads, alternate addresses, TTL cleanup, schema deletion, and compaction remain. Snapshot-capture helpers were removed; an ordinary disk commit is still sometimes called a snapshot in storage code. That local commit is not a cloud backup.

Signed history and local validation

A database history contains signed entries from node and device streams. Each stream starts at sequence 1 and links each later entry to its predecessor. Cross-stream references name entries the writer has seen.

AcceptEntry verifies the signature, database binding, predecessor, observed dependencies, logical clock, and writer authority before accepting an entry. Missing dependencies wait. A conflicting signed entry at the same writer sequence freezes that stream.

This protocol validator is implemented. It is not the removed per-schema proposal approval loop. Ordinary record conflicts use whole-record last-writer-wins; a forked signed chain is a different error. Rejection and fork evidence are held in memory, not a durable archive of losing record values.

A database ID is now a 32-byte Ed25519 verifying key encoded as 64 hex characters. Birth proves the publisher’s binding. Device IDs are also 32 bytes. A signed chain fork is not an ordinary record conflict. Whole-record LWW uses logical clock, node key, and device ID; wall time is display information.

Owned writes and the relay worker

After an owned shareable /v1/write commits, the node authors a signed direct entry for each mutation. It saves the entries in its local history and outbox, then wakes the relay worker. A publisher’s app writes need a path from local storage to the signed stream that receivers can pull.

The request must name the database ID and that ID must have saved birth material. A name is not resolved here; no ID or no birth material skips the mirror. Other write routes are not connected by this change. It omits range coordinates, alternate addresses, metadata, and files; it does not reproduce those record shapes. Payload fields are signed, not encrypted. A mirror failure returns 503 after the local commit; it does not roll that commit back. The record batch and its signed entries are not one atomic save.

A daemon worker uploads registered personal and shareable outboxes before any stream pull. Uploads do not require an open record store. It then pulls open owned shareable stores and registered publisher streams. Personal databases keep their upload pass but are not pulled.

A failed upload or owned pull is recorded and other databases still get a turn. One received-share error still stops later received shares. Hitting 64 batches reports an error and retries later; it does not block the pull phase. Owned shareable reads restart at sequence 1; received reads advance from an in-memory head. Neither saves a receive cursor or discovers other devices. A successful turn clears its previous top-level error. That does not prove complete delivery. No relay URL leaves the worker idle.

The owned write mirror authors directly after /v1/write commits. It can create the birth entry on first use, then saves each direct entry in authored.json and outbox.json. Deletes carry an empty value. Grant and proposal actions also author entries. The older author_and_accept_data and bootstrap helpers are not the connection used here.

Locally authored entries and the outbox are saved as authored.json and outbox.json under log-sync/<database-id>. Reloading a history now also reloads its pending outbox entries. A later save therefore retains valid unconfirmed birth, grant, and record entries. Requeueing is idempotent by entry hash. This also applies when rebuilding history after an authored-log append failure. The readers have a 16 MiB limit; missing files load as empty, and unreadable or invalid files produce warnings without stopping history reload. The change does not repair lost or corrupt files. The daemon does not yet save a receive cursor or fetch other device streams. Signed heads are a comparison aid, not proof that all data has arrived.

The current database_cloud_state helper reports Enrolled when saved cloud credentials can be read, and NoAccount when they are absent. Grant and link actions use this check.

The previous signed database-create exchange, 30-second enrollment wait, and per-database live confirmation cache are removed. wait_for_enrollment now returns immediately. Enrolled does not establish remote database readiness.

Sync status after a turn

The worker skips personal-database pulls to avoid expected grant refusals from those reads. Their queued uploads still run. Shareable and received-database failures remain errors. A successful turn clears the tracker’s top-level last_error, but it does not clear payment_hold or stored per-database errors; status can still surface those errors. A clean turn does not establish complete synchronization.

Relay access and confidentiality

The reference relay keeps log entries by database, writer, device, and sequence. A signed birth and publisher grants supply its access index. It also stores blobs by digest.

The relay checks request signatures and grants; it does not run the complete AcceptEntry algorithm. Appends and reads cap a batch at 90. Public any-read still requires a signed caller. This source does not establish an ExeMem deployment or provider placement.

The node proposal and owned-write paths construct raw record payloads and sign them. SignedEntry serializes that payload directly into relay JSON. The old encrypted envelope module was deleted. The guide therefore makes no end-to-end confidentiality claim for the replacement data transport. Local run encryption remains implemented.

The client has a 10-second connection timeout and 30-second request timeout. Failed queued uploads re-wake the loop. The reference relay caps append/read pages at 90 entries. The worker attempts at most 64 batches of 32 per owned database before pulls. A short stored count keeps the batch queued. Identical duplicates count as stored in the reference relay. Upload and owned-pull errors do not prevent attempts for other databases.

Sharing roles and proposal approval

The publisher authors signed grant entries. Read permits fetching. Submit permits record proposals. Write permits direct record entries. Revoke and role reductions record device cutoffs. Revoked members remain in the folded grants view with role revoked. role_of still returns no active grant for them.

Grants apply to the database, not individual schemas. Public any may receive read only and cannot be revoked through the current API. Unlisted devices have cutoff zero after a reduction. Grant APIs return a local entry hash and writer sequence, not relay confirmation. Node ownership is required for these actions.

A signed Data entry is direct or proposal within its writer’s device stream. Direct entries affect the record view. A proposal becomes content only when a publisher entry incorporates it.

The old automatic approval against owner_only, own_records, and shared schema rules was deleted. No caller in the current daemon authors an incorporated entry. The previous guide’s claim that local settings automatically approve record proposals no longer applies to this revision.

The submissions route accepts a UUID idempotency key and authors a signed proposal into the local history and outbox. Status is submitted, published, or unknown according to held history.

The payload is a JSON object at a hash key. Range keys and non-null files are refused; the value limit is 64 KiB. The old 96 KiB proposal contract and discarded status are gone. A held submit or write grant is required. Complete received-history loading and publisher incorporation are incomplete, so this route alone does not provide an end-to-end submission flow.

This is implemented in the history library and relay gate. Owned shareable /v1/write now has a signed mirror. Received member writes still lack that connection. Its retained received-store helper currently returns true for the direct-write check, while durable-prefix and app checks remain. Do not describe that helper as enforcement of the signed write role.

Received databases and materialization

Open tokens now include a required publisher device ID. Older tokens without it fail decoding; older registrations without it are skipped. A receiver starts at sequence 1, then requests the next batch after its accepted in-memory head. Restart loses received history and causes it to be fetched again. Missing dependencies can hold that head back.

Accepting an open token saves the database, content key, publisher device ID, and optional local name. It marks an empty receiver store ready to open and wakes the relay worker.

The limit is 32 registrations. Older registrations without a publisher device ID are skipped. The store-open marker does not satisfy the separate durable-prefix check used by reads. Schemas must already exist, and the new path neither replays them nor writes that prefix marker.

The materializer reads each history winner as a JSON field object at a schema and hash key. The daemon calls it after accepting entries for owned or received stores. It creates, replaces, or deletes records using a checked revision.

The schema must already exist. The adapter supplies no alternate addresses, range key, file bytes, or record metadata. It is not full schema or attachment replay. A fresh receiver has no replayed schema catalog. Materialization also does not write the durable-prefix marker needed for received reads.

People controls and consent codes

People is the separate command-line app for verified contacts, shared album setup, circles, consent codes, and access requests. It asks LastDB for signed grants and reads chain views.

People uses the databases extension and its separate @lastdb/people-client wrapper. It has no browser interface. Shared databases use whole_database mode. The old share_config, set_share_config, and seal_invitation calls are removed. Grant actions on LastDB currently require owner context. App-socket compatibility and automatic received data delivery are not established by this source review.

People’s shared-albums v1 setup prepares Album, AlbumItem, Photo, and Comment in a whole-database share. It reserves a 64-hex database ID and verifies exact schema definitions.

This is the one supplied setup. Stored schema names still use social/. The database-wide memberWrites file and its setup confirmation step were removed. Setup does not grant roles or establish content sync. A preselected database ID currently has no automatically minted birth material in LastDB, so schema setup alone is not proof of a usable grant chain.

Read presets map to read; nonempty schema presets and all map to submit. A direct person grant can choose write. A schema-named preset is not a per-schema grant. People retains a 98-entry roster-plan cap and up to 50 circles. Changed previews need review again; outside grants need an explicit choice. Updates across people and databases are not one atomic transaction.

People wraps a locally minted LastDB open token with the database ID, publisher key, and grant receipt. The recipient supplies an independently verified publisher key before accepting it.

The wrapper is unsigned and not encrypted. It carries an open token containing the database content key, so it is sensitive. It is not the old sealed invitation and has no old 24-hour expiry contract. Accepting a new token enables publisher-stream pulling, but does not establish complete received data or readable records.

The grant receipt is a local entry hash and writer sequence. People’s confirmed wording must not be read as relay delivery.

Restore, bundles, and retired backup paths

The restore command reads explicitly named owner device streams from sequence 1. It verifies entries locally, materializes winning records into staging, shuts down the stores, and publishes an unused destination.

The current adapter creates a one-field Hash schema with v: String for each namespace. It is not a general schema, alternate-key, or attachment restore. Bundles remain pending because this path does not fetch and verify their blobs. Missing dependencies or rejected entries refuse completion. No snapshot fallback or fixed global delivery head remains.

The caller names the streams. There is no automatic complete-device discovery. Earlier snapshot evidence does not qualify this path.

The reference relay supports staged blob upload, size and digest verification, and signed download requests. Signed bundle entries can refer to a blob holding many record changes.

The caller must verify and decode bundle bytes. The daemon and restore reader do not connect that step yet. The former encrypted attachment uploader and snapshot-covered object cleanup are gone. Do not infer working attachment backup from the blob API.

Native cloud snapshots, the initial hard-link baseline, covered-log cleanup, personal blob cleanup, and automatic lagging-device replacement were deleted. The backup snapshot and reclaim commands and the snapshot-roundtrip-dev workflow are gone. Older DEV and PROD results refer to those former implementations and do not qualify the replacement.
