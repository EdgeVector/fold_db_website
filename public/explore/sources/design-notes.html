Source notes and release limits

Source review: 12 November 2026. Merged LastDB revision 2784fae718c5d146d3f0ae0cd8f6ffa4a9f38e7f.

The guide describes 127 parts and 480 connections. This review covers one commit after 59ae901. Completed reviews cover 1177 commits after October 21. The review follows changed code and surrounding callers across the data model, memory, disk, deletion, encryption, cloud, and services. This interval reorganizes backup capture, transfer, restore, and cloud commands. Vendored LastStore code is unchanged.

Retired multiwriter paths and the remaining Shares

The old dedicated shared homes, portable journals, peer replay, writer rejoin, shared snapshot commands, and v1 shared-storage client are removed. Registered Share publication, invitations, verified recipient copies, and contributor submissions remain. Legacy publications use separate personal-format homes and the V2 path. Signed named Shares now use separate receiver stores and the named-sync worker described below. They are not replacements for opening an old dedicated shared home.

Replacement writes now supply the full record. Naming an older schema definition no longer preserves omitted fields. Contributor grants still check the exact declaration and allowed action before the publisher performs a normal conditional write.

Opening a home refuses old dedicated shared markers, a disk-private directory, or known portable-journal and delete-age keys. The briefly added automatic cleanup was reverted before this review completed. Startup neither replays nor removes those entries. There is no automatic migration. This review did not open or change a primary home.

Earlier reviews covered the consolidation of record, schema, storage, query, app registry, and socket code. Source links follow those moves. LastStore counts allocated metadata capacity against its read bounds. Ordinary block decryption now uses the Rust AES-GCM implementation; the frame format, authentication, and compression thresholds stay the same. The diagram retains its four-step Disk view and six service groups.

Source: Retired-home admission · Personal-home admission · Contributor validation · Registered Share copies · Manifest decoding

Smaller service surface

The saved app-change feed, its socket route, and the SDK changes() method are removed. Native writes still save their records before acknowledgment. Optional Search delivery remains a separate action after disk publication; it is not a saved app-change feed.

The stopped-home search-rebuild command is removed. Search delivery still stops when its queue reaches the byte or file limit, or when a rebuild marker is present. Existing batches remain. This source no longer provides that built-in command to repair the search index.

Storage inventory now reports live record counts and bytes by schema. The full physical inventory route and descriptive-name claim retirement are removed. Explicit disk cleanup, the deletion ledger, schema expiry, and backfill remain. Request workers retain their bounds and deferred write replies; their queue-wait timing hook is removed.

The record model still uses schema-owned values, a 64 KiB record cap, and a 256 MiB decoded-record warm-set target. Conditional writes, typed key order, and save-before-ack remain. The guide links to the current source locations and keeps six service groups, with 31 parts.

Source: Socket routes · SDK · Native commit · Search delivery and pause marker · Owner commands · Schema names

Format 15: derived lookup keys and two encryption layers

New homes use format 15. Only that format opens or restores. Personal backup profile 14 identifies it. The old shared marker and profile 15 are refused. A format 14 home needs its matching program; changing its marker is not a conversion.

Each primary or alternate key space derives its hash-protection key from the home content key and key-space identity using HKDF-SHA256. The schema supplies typed range order. Stored field-key bundles, their wrapping key path, and the extra ENB: wrapper around file entries are removed. Files still have content encryption and local run-block encryption. The old device-private shared home and its cross-home journal are removed.

Source: Format and profiles · Lookup-key derivation · File encryption · Run keys and layout

Records, memory, and keyed reads

A schema owns complete records with independent primary and alternate addresses. Replacement requires the current revision and the complete new payload. Canonical field reuse shares definitions, not record values. The 64 KiB record cap and ordinary flush-before-ack contract remain.

The warm set retains decoded records and their keys, metadata, and file markers. Its default target is 256 MiB; held records can keep it above that target. Schema definitions use a separate cache. Prepared native writes retain their 512 MiB allowance. The process-memory governor, deferred-memory accounting, allocator tuning, and extra typed-definition warm cache are removed. These remaining limits are not a process-wide memory cap.

Queries now require exact keys, batches of keys, or a range under one hash. Whole-schema record pages, samples, WHERE-style field conditions, field sorting, and range-only selectors are removed. Ascending keyed cursors remain; descending keyed reads use offsets. Owner key listing and internal maintenance enumeration remain separate from query results.

Source: Whole records · Warm-set accounting · Resource bounds · Keyed query rules · Owner key listing

Disk, flush, and deletion

One native request privately prepares its complete change. A bounded queue can combine arriving requests. The caller waits for the durable run commit and clean memory publication before success; there is no collection timer. The removal of timing receipts does not remove these waits.

LastStore still writes a new run and stages CURRENT before publication. Both prerequisites must succeed. CURRENT is renamed and its directory synchronized before the new root becomes current. Ordinary file additions precede record updates, and file deletions follow them. Saved recovery work still handles interrupted file deletion.

Compaction, space reservation, held read roots, and poisoned-lock refusals remain. Detailed physical-file diagnostics and read/commit timing receipts are removed. The remaining physical diagnostic totals allocated bytes in the native directories. The backup key-head and decoded-block reuse cache is also removed; bounded authenticated streaming remains.

Source: Native request completion · Commit and publication · Run and CURRENT prerequisites · Durable publication · Bounded streaming · Current file diagnostic

Expiry belongs to its schema

Retention policies and tracking now use the schema name directly. Cross-name retention anchors and alias chains are removed. Manifest retention requires the declaring app to own the schema; an operator override can retain the manifest policy underneath it. Shortening a manifest TTL still requires explicit confirmation.

The expiry worker runs in its own periodic task. It completes a pass and waits 60 seconds by default, with a separate interval setting. It no longer depends on health sampling or its retry telemetry. Small conditional deletion pages and keyed age discovery remain. Explicit retention backfill is removed. The periodic worker still uses the owner’s main database; it does not sweep newly owned named siblings. The old shared-journal binding and its TTL restrictions are removed.

Source: Manifest and operator policies · Schema-owned tracking · Periodic expiry · Keyed expiry discovery

Backup and the narrower restore checks

LastDB owns retention and backup correctness. ExeMem checks account and payment eligibility, routes cloud bytes, and performs cleanup under LastDB’s instructions. It does not interpret database contents or decide independently which backup data is obsolete.

Personal backup retains record runs and uploads stored blob versions separately. Restore creates an empty blob home; later attachment requests fetch and verify their selected version. Legacy Share publications refuse ordinary blob attachments; Files sharing stores chunks as records. Snapshot cleanup, automatic policies, exact accepted change chains, and cloud admission remain. The stopped-home backup command and its final snapshot procedure are removed; captures use a running daemon.

The local snapshot capture checkpoint is now format 6. Resume rejects checkpoints from older formats. Preparing a new capture retires the older local checkpoint and its held files; it does not migrate that checkpoint. These local checkpoints are separate from accepted cloud backups. Home format 15, backup profile 14, snapshot metadata 8, and log metadata 5 remain unchanged.

Source: Capture state format · Prepare and resume · Older capture cleanup

Restore still checks exact captured files and roots, supported format markers, replay-floor and author markers, and the account content-key proof. The full logical walk of schemas, records, alternate keys, deletion stamps, inline files, and blob markers is removed. The admission function now reports zero records checked. A successful restore is not an audit of every record or proof that every attachment is available.

An explicit file read still decrypts the selected bytes and checks their size and hash. Local-reference files remain outside run storage, and their personal cloud upload path is incomplete. A record-only restore cannot establish that those source bytes were backed up.

Source: Restore entry point · Account and marker checks · Captured file binding · Stored blob upload · Attachment reads · Current backup commands

Services and source-only additions

The owner socket and bounded workers remain. Status now reports the build, uptime, worker counters, backup activity, and search-queue state. Request rankings, the minute health sampler, session ledger, alert-check, local-watch route, encrypted query-slice export, and native payment commands are removed. The old derived behind/stale/covered backup health report is removed; detailed backup status still exposes saved policy and job facts.

The cloud client, upload planner, host handlers, socket transport, identity helpers, endpoint profile, environment helper, and storage-policy crates have been folded into their consumers. The diagram describes their roles without treating each source crate as a separate service. Apps & services remains nested in six groups; Disk retains a four-step main path and four detail groups.

The advisory schema service and signed app catalog remain separate. Nine JSON standard-schema declarations now describe social-graph and social records. These declarations are source specifications, not evidence of an installed app or deployed service.

Source: Basic status · Backup status fields · Current socket routes · Cloud client location · Planner location · Standard-schema declarations

Named sync is connected to the daemon

The daemon now runs a named-database sync worker. Owned named stores capture accepted changes before cloud activation. With saved account access and a bound sharing spec, the worker requests signed cloud creation. Only a matching live service reply activates the database. Existing databases require live cutover confirmation; a saved receipt or readiness file is not enough.

The worker refreshes membership revisions and signs database-specific requests. It sends eligible saved changes with stable sequences and exact retry bytes. Private content is withheld; unknown classification blocks that page. Registered signed recipients use their invitation and node key without the publisher’s account key. The owner’s automatic byte-backup worker pauses only when its own database leaves the legacy path. Activation of a named sibling does not pause personal backup.

Personal byte-backup recovery remains separate. Ordinary writes to received named stores are still refused. A publisher does not yet apply other writers’ named entries. The manual DEV load workflow does not run on ordinary pushes and does not establish a PROD recovery result.

Source: Activation and worker · Accepted changes · Signed recipients · Grant refresh · Personal backup · Manual DEV operation

Saved changes share the local commit boundary

Owned named stores save encrypted logical entries for accepted record and schema changes. A pending entry is prepared before physical commit and published after that commit, before memory publication and the local acknowledgement. Interrupted work is checked against its native commit marker. A gap refuses further accepted-log reads and new commits. Earlier data requires snapshot coverage.

Canonical bodies have a 1 MiB cap. Retained bodies and copied file bytes share a 1 GiB spool cap; identity and retry files are separate. The sync worker takes at most eight entries per turn. It advances the local position only after publication or explicit withholding. Personal and received stores do not enable this capture.

Named sync encrypts eligible files separately and uploads them before publishing the record entry. It checks the accepted upload receipt and saves the exact result for retry. Matching local-file references up to 512 MiB can use this path while their original bytes remain available. This path does not release uploaded cloud blobs. The personal local-reference backup gap remains.

Source: Accepted spool · Commit ordering · Named files · Verified upload

Encrypted named recovery and membership

Expired named cursors can recover through an ordered snapshot chain. Replay validates the full chain before writing, including encrypted bindings, previous links, part order, and mutation identities. It applies schema changes, complete records, deletions, and file changes to the selected named store. File objects must pass size and hash checks. Missing objects and conflicting identities stop replay.

Chains allow at most 1,024 snapshots, with a 1 MiB cap per encoded part. Saved attempt and completion markers support interrupted replay. Delivery acknowledgement follows store flush. A registered signed receiver becomes readable only after a durable snapshot or log-only prefix. This path does not replace the personal home and has no new PROD recovery qualification.

Named invitations first update a signed, versioned member list. Read and Submit grants bind recipient node keys to one database. The client allows 98 member rows, including revoked rows. An uncertain update retains its exact signed body for retry. Invitations last 1–168 hours, defaulting to 24; membership itself does not expire. Initial acceptance checks invitation expiry. Later sync uses current membership, and revocation cannot erase an existing local copy. Submit membership does not yet enable ordinary received-store writes.

Named log payloads use authenticated encryption bound to the database, writer, device, sequence, and namespace. File payloads use a separate encryption domain. Invitations contain only the selected database’s key. Saved account identity, environment, and canonical endpoint must agree before member changes.

Source: Named recovery · Chain checks · Replay progress · Separate receiver stores · Member updates · Account and endpoint binding · Encrypted payloads

Named databases are local stores

The owner daemon can create and open named databases beside personal. Each has its own format 15 store and content key derived from the node signing seed and database UUID. A saved registry binds IDs, names, and optional specs. Selected schema, record, and file routes use that store; unknown selectors fail. CLI selection does not change future requests. The SDK returns a separately selected client.

Creation first makes a local store. The separate sync worker can enroll a spec-bound database after live cloud confirmation. The periodic expiry worker and owner administrative reports still use the main database. The graph name is reserved but not provisioned. Other reserved names require matching spec bindings; a binding is not itself an admitted sharing policy.

Sharing rules and saved keyed queries

The current spec catalog admits social and lastdb-files version 1. It lists eligible schemas, fields, and files. Saved queries require source-schema ownership and a different ready, owned, shareable destination with the matching binding. Only eligible fields are copied. Ordinary writes are not all filtered through this catalog.

A saved selection uses known hashes or ranges under one known hash, with optional one-hop links. Limits are 32 reads, 8 links, 256 selected records, and 256 saved queries per source. Truncated reads are refused. Definitions and ledgers each have a 24,000-byte cap. The owner daemon follows durable-write notifications; explicit reconciliation uses the same path.

Destination writes check revisions and file hashes. Removal only targets keys in that query’s previous ledger. The ledger advances after successful work; writes across databases are not one atomic transaction. The reconciler does not construct alternate addresses or itself enroll cloud backup. Its destination writes enter the named store’s accepted-change stream, which the separate sync worker can publish after activation. Legacy publication-home uploaders remain separate. Files import accepts an unbound legacy home or lastdb-files binding, and refuses a social publication.

Source: Owned stores · Registry and creation · Spec catalog · Projection admission · Saved query execution · Conditional writes and removal · Daemon follow

Cutover is an explicit cloud operation

cutover verify checks six supplied evidence files: snapshot, legacy position, final writes, grants, daemon readiness, and delivery readiness. It reports activated:false. It does not fetch the snapshot, inspect deployed services, or run recovery.

cutover request requires an existing DEV or PROD cloud connection and the matching authority key. It signs the exact receipt body for one database, posts to that environment, and accepts only the same committed receipt from the authenticated service. It refuses the primary home and does not change local database data. The reviewed code does not establish that a PROD service accepted a cutover or that a recovery check passed. The daemon now uses the signed path only after its own live activation check.

Source: Evidence checks · Signed request · Node proof · Grant and revision rules

Consolidated storage, backup, and commands

LastDB still admits complete writes, saves the run and CURRENT file list, publishes the matching memory state, and then returns success. File additions precede record changes; file deletions follow them. The homes retain separate file-list commits and interrupted-delete recovery. Warm records still enter after durable publication. Compaction thresholds and read holds remain.

Snapshot and change backups now share a direct streaming planner. Callers provide file readers and save plans; the planner hashes 64 KiB reads into bounded chunks or small-file packs. Transfer batches preserve verified receipts after partial failure. Restore shares page, extent, hash, and spool checks, then opens a fresh record home with an empty blob home. Format 15 and backup profile 14 remain the accepted layout.

Standalone app check, its automatic advice calls, retention backfill, and several convenience CLI commands were removed. App publish still checks a complete typed manifest against the running node. The schema advice service remains separately callable. Source links now point to the consolidated implementations.

Source: Request and ack · Commit ordering · LastStore publication · Compaction · Planner · Transfer batches · Restore staging · Publishing checks

Recovery evidence remains version-specific

Ordinary authenticated restore is enabled in source. The earlier PROD recovery run used revision ebd09268f8d151fb6cc382d8b1f9ac2c82e3420d and format 14, before separate blob paths. It recovered generated records, changes, a deletion, and file bytes across clean restarts. The later DEV recovery run used 4132e14aa5430a9bde5676912f7d6d3acc4c47b9 and checked restored-device sign-in, current-file download, and released-version refusal.

Neither historical result qualifies format 15. This review does not claim a new PROD result, deployed service change, stable release, or primary upgrade. Stable release and signed app publication retain their own CI gates. Guide publication changes only the website.
