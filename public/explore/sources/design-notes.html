Local storage and authorship

Record

A record holds one schema’s fields, primary key, named alternate addresses, one revision, and database-set authorship. Replacement supplies the complete desired state. Omitted fields disappear.

The complete encoded record has a 64 KiB limit, including keys, alternates, one write stamp, authorship, metadata, and file markers. Blob and inline file bytes stay separate. A live record can have no payload fields.

Source: Record

Record authorship

Local writes set created_by at creation and updated_by on each change. Signed-history materialization sets both to the winning writer, or to the proposing member for an incorporation. History separately remembers the earliest writer for proposal ownership checks.

Ordinary local replacements retain their original created_by. Signed materialization instead copies the winner into both author fields and repairs authorship even when fields are unchanged. History ownership uses the earliest valid write by logical clock, node key, and device ID, not arrival order or stored created_by. Arbitrary remote metadata is still omitted.

Source: Record authorship

Warm set

A read by key checks the warm set first. A disk fetch can keep the complete decoded record for a later call.

The default warm limit is 256 MiB. It covers decoded records, their keys, metadata, and file markers. Schema definitions and file bytes stay outside this charge. The least recently used unheld records leave first. Older read views and private writes use disk. A range page can admit its selected records without fetching them a second time.

Source: Warm set

Flush

A flush sends prepared changes through the native disk queue. Requests can share one complete disk commit before each receives success.

When accepted-change capture is enabled, the commit saves those entries before memory publication and the ack. A missing entry or full spool refuses progress. Completed disk work releases writer ownership before notifying waiters. Local success does not confirm a cloud copy. The owned /v1/write route performs a separate signed mirror after this local success; that later step can still fail the API response.

Source: Flush

Run block encryption

Separate derived keys protect each record and record-file home. Owned named databases derive their content keys from the node signing seed and database UUID. Received Share publications use their supplied content key.

Block compression skips inputs below 256 bytes. It is kept only if it saves at least 64 bytes and 10%, including its length header. Encryption still applies when compression is skipped. File sizes, clear footers, and some layout facts remain visible. The replacement signed log serializes payloads directly. Local run encryption does not encrypt those relay entries; the old named-log envelope was removed. The run reader loads and authenticates a complete block before exposing decoded bytes. Decompressed output is capped at 64 MiB; the former two-pass bounded reader is removed.

Source: Run block encryption

Writes and the saved log

Owned write mirroring

After an owned shareable /v1/write commits, the node signs each mutation. It first signs the schema definition when that namespace is new or changed in its history. It appends the signed entries to the authored log, then wakes the relay worker.

The request must name the database ID and that ID must have saved birth material. A name is not resolved here; no ID or no birth material skips the mirror. Other write routes are not connected by this change. Hash and hash-range keys are carried. A ranged hash cannot contain the unit separator; that unsupported key is skipped by the mirror planner. Alternate addresses, arbitrary metadata, and files are omitted. Payload fields are signed, not encrypted. A mirror failure returns 503 after the local commit; it does not roll that commit back. The record batch and its signed entries are not one atomic save.

Source: Owned write mirroring

Signed log and upload cursor

Each database saves every locally signed entry in one authored log. A separate upload cursor counts entries the relay has confirmed. The worker uploads the log after that position.

The files are log-sync/<database-id>/authored.json and uploaded.json. The authored log has a 16 MiB limit and is rewritten on append. Missing files mean an empty log or cursor zero; unreadable or invalid files return an error. A cursor beyond the log length is refused. A full stored count advances the cursor; partial confirmation leaves it unchanged. Locally authored history is saved, but received history and receive positions are not. The separate outbox.json is no longer used.

Source: Signed log and upload cursor

Signed history

A database history contains signed entries from node and device streams. Each stream starts at sequence 1 and links each later entry to its predecessor. Cross-stream references name entries the writer has seen.

The current library retains accepted entries, pending entries, and rejection evidence in memory. The node saves locally authored entries in one log and keeps an upload cursor; it does not persist the full received history. Snapshot-based recovery, log-prefix cleanup, and automatic lagging-device reset were removed.

Source: Signed history

Worker, connection, and status

Background relay worker

The worker uploads owned logs, then pulls open owned shareable databases and processes their proposals. A second upload pass sends new publisher entries in the same turn. It then uploads received logs and pulls those shares. Personal databases upload but are not pulled.

Uploads do not need an open record store. A failed upload or owned pull leaves other databases a turn; one received-pull error still stops later received shares. Each pull starts at sequence 1 and follows page cursors. Failed materialization retries without new entries. There is no saved receive cursor. Publisher device discovery, complete record reconstruction, bundles, and attachments remain limited. The worker uses LASTDB_RELAY_URL when set, otherwise the ExeMem address in saved cloud credentials. Without either, it stays idle.

Source: Background relay worker

Relay client

The node signs log append and read requests with its identity. The request binds the method, path, protocol version, database, body hash, time, and nonce.

The worker uses one relay URL: LASTDB_RELAY_URL overrides the ExeMem address in saved cloud credentials. The old saved relay-url file is no longer consulted. Blob helpers exist but are not called by its sync loop. A successful append means relay storage, not a complete backup. The current data payload is serialized directly; this client adds a signature, not content encryption.

Source: Relay client

Saved cloud credentials

One protected file holds the service address, account access key, and optional checked connection. Account commands, schema-service selection, and the relay worker use its reader.

The reader requires an ordinary private file owned by the current user. It rejects links, oversized files, and empty keys. The saved service address is now the default relay URL; LASTDB_RELAY_URL can override it. Signed entry history remains separate. Their presence is not proof of relay access or backup coverage.

Source: Saved cloud credentials

Cloud readiness

The current database_cloud_state helper reports Enrolled when saved cloud credentials can be read, and NoAccount when they are absent. Grant and link actions use this check.

The previous signed database-create exchange, 30-second enrollment wait, and per-database live confirmation cache are removed. wait_for_enrollment now returns immediately. Enrolled does not establish remote database readiness.

Source: Cloud readiness

Node status

Status reports the running build, uptime, socket workers, and cloud state. Upload turns now record each owned database’s log length, confirmed position, and error. A clean upload clears its upload error; a clean whole turn clears the top-level last_error.

The old detailed backup policy and progress routes remain removed. Received listings have a separate process-local publish report. A clean upload does not clear payment_hold or prove receive completeness. Unreadable state can report fallback counts alongside an error. No error or zero pending entries is not proof of complete backup.

Source: Node status

Finding signed streams

Writer discovery and pulls

The worker reads known publisher device streams first. If none is known, it asks for all devices under the publisher key. It then discovers member writer keys from current and historical Write or Submit grants, including reduced or revoked members.

Reads restart at sequence 1 on each pull; page cursors last only for that call. Once publisher devices are known, the worker does not independently discover every other publisher device. Personal databases are not pulled. Received history is held in memory and fetched again after restart. Hash-range records are supported. Alternate addresses, arbitrary metadata, files, and bundle loading remain incomplete. The old lagging-device reset remains removed.

Source: Writer discovery and pulls

Reference relay

The reference relay keeps log entries by database, writer, device, and sequence. A signed birth and publisher grants supply its access index. It also stores blobs by digest.

The relay checks request signatures and grants; it does not run the complete AcceptEntry algorithm. Appends and reads cap a batch at 90. A read without device_id pages all devices under one writer key. Public any-read still requires a signed caller. A revoked member may request a single publisher device stream to learn the cutoff; writer-wide reads remain refused. This source does not establish an ExeMem deployment or provider placement.

Source: Reference relay

Member writes and publisher checks

Direct member writes

A received /v1/write requires a held Write role before the local commit. After the commit, the node signs the mutations on its own device stream, saves them in the authored log, and wakes upload.

App schema permissions and record conditions still apply. Authoring requires a held birth and no unresolved history dependencies. It carries hash or hash-range keys and JSON fields, with an empty value for deletion. Alternate addresses, arbitrary metadata, and files are omitted. The creator-only check belongs to publisher proposal processing; a direct Write grant is broader. A later role reduction can undo a direct write beyond its device cutoff. The local commit and log append are separate: a later authoring failure can return an error after the local record is saved. Read before deciding to retry. Upload confirmation does not prove every reader applied the entry.

Source: Direct member writes

Publisher incorporation

After pulling proposals, the publisher checks the schema, the expected winning history entry, and the record’s history creator. An accepted change is saved locally, then signed as a publisher entry that cites the proposal.

Create requires absence. Replace and delete require a matching history entry and the proposer must be the history creator. Hash and hash-range keys are supported, without alternate addresses or files. This creator check applies to proposals; direct Write members follow the separate write-grant path. The old configurable per-schema sharing settings remain removed. Refused proposals stay submitted without a discarded receipt. The local write and signed incorporation remain separate saves.

Source: Publisher incorporation

Proposal submission and status

The submissions route accepts a UUID idempotency key and saves a signed proposal in the authored log. Status is submitted, published, or unknown according to the local proposal ledger and held history.

The signed envelope carries mutation_type, expected, and optional record fields, up to 64 KiB. Keys may be hash-only or hash-range. Ranged hashes cannot contain U+001F; non-null files are refused. Create uses absence. Replace and delete map the local revision to a history entry and require the proposer to be its history creator. Submit or Write role is required. HTTP 202 and relay storage do not mean published: that needs an incorporation entry. The idempotency ledger is separate from the log; discarded is not reported.

Source: Proposal submission and status

Local entry validation

AcceptEntry verifies the signature, database binding, predecessor, observed dependencies, logical clock, and writer authority before accepting an entry. Missing dependencies wait. A conflicting signed entry at the same writer sequence freezes that stream.

This protocol validator is implemented. The publisher separately checks proposal record conditions; the removed per-schema sharing settings are not restored. Ordinary record conflicts use whole-record last-writer-wins; a forked signed chain is a different error. Rejection and fork evidence are held in memory, not a durable archive of losing record values. A newly received role reduction also recomputes affected direct-write winners; local records change on materialization.

Source: Local entry validation

Signed membership grants

The publisher signs database roles: Read fetches, Submit proposes, and Write permits direct record entries. A reduction records a cutoff for each member device. When that reduction arrives, history removes the effect of direct member entries beyond those cutoffs.

The signed entries remain in the chain; only their effect on record winners changes. This recomputation covers direct data entries, not loaded bundles or publisher incorporations. Devices absent from a reduction have cutoff zero. Roles apply to the whole database. Public any-read cannot be revoked through this API. Grant replies confirm local authoring, not relay delivery. Only the publisher can change grants.

Source: Signed membership grants

Received records and schema definitions

Received database registration

Accepting an open token saves the database, content key, publisher device ID, and optional local name. It marks an empty receiver store ready to open and wakes the relay worker.

The limit is 32 registrations. An older registration without a publisher device ID can use writer-wide discovery. List state becomes ready when held history has the signed birth; this does not prove every record was applied. Restart requires received history to be fetched again. Read access no longer waits for the removed prefix.json marker.

Source: Received database registration

Signed schema definitions

The publisher signs schema entries into the database history. The owned write mirror emits a definition before data when that namespace is new or changed. Receivers and restore load these definitions before applying records.

Only the publisher can author schema entries. History retains the last accepted definition for each namespace. Loading checks the definition’s name and local schema compatibility. A schema entry does not carry the missing alternate, file, or metadata values for a record. The ordinary worker does not run the existing-record bootstrap helper.

Source: Signed schema definitions

Received record access

The read API selects a registered received database and reads the records already in its local store by key. The obsolete durable-prefix file check has been removed.

A readable store or ready list row does not prove complete synchronization. Ready means the held history has a birth entry, even if later materialization fails. Before data arrives, reads can find no record or no schema. Publisher device discovery, alternate reconstruction, and files remain incomplete.

Source: Received record access

Record materialization

The daemon loads signed schemas, then writes winning JSON records at hash or hash-range keys. Both stored author fields follow the winning writer. When a role reduction voids a direct write, it restores the remaining winner or deletes a key with none.

A live winner needs a declared schema. An undeclared tombstone is skipped. Ranged keys join hash and range with U+001F; the schema tells the adapter how to split them. Alternate addresses, file bytes, and arbitrary remote metadata remain absent. A record is skipped only when fields and both authors match. Writes still use checked local revisions. Retry markers and received history stay in memory.

Source: Record materialization

Member upload status

A received database listing reports publish.pending and publish.lastAttempt. Pending is the last observed count of log entries after the upload cursor. The last attempt records a time, outcome, and relay status when available.

The report lives in memory and resets on restart. Pending is null until observed; the list itself does not open a store. A failed attempt does not refresh the pending count. An upload refusal alone does not undo the local change or drop entries. A later signed role reduction can void a direct write beyond its cutoff. Confirmed means a completed upload of the observed log, not incorporation or delivery to every reader. Owned database listings omit this report.

Source: Member upload status

People controls and consent

People app

People is the separate command-line app for verified contacts, shared album setup, circles, consent codes, and access requests. It asks LastDB for signed grants and reads chain views.

People uses the databases extension and its separate @lastdb/people-client wrapper. It has no browser interface. Shared databases use whole_database mode. The old share_config, set_share_config, and seal_invitation calls are removed. Grant actions on LastDB currently require owner context. App-socket compatibility and automatic received data delivery are not established by this source review.

Source: People app

Shared album setup

People’s shared-albums v1 setup prepares Album, AlbumItem, Photo, and Comment in a whole-database share. It reserves a 64-hex database ID and verifies exact schema definitions.

This is the one supplied setup. Stored schema names still use social/. The database-wide memberWrites file and its setup confirmation step were removed. Setup does not grant roles or establish content sync. A preselected database ID currently has no automatically minted birth material in LastDB, so schema setup alone is not proof of a usable grant chain.

Source: Shared album setup

Reusable circles

A circle keeps verified people and links them to whole-database shares. People previews changes and asks LastDB to author signed grant or revoke entries.

Read presets map to read; nonempty schema presets and all map to submit. A direct person grant can choose write. A schema-named preset is not a per-schema grant. People retains a 98-entry roster-plan cap and up to 50 circles. Changed previews need review again; outside grants need an explicit choice. Updates across people and databases are not one atomic transaction.

Source: Reusable circles

App sharing requests

An app saves a proposed circle link or person grant through People. The owner lists waiting proposals, previews the affected access, then approves or declines with the People command. People saves the outcome and tracks unfinished updates per database.

Requests use an existing owned whole-database share and a stable UUID. Database IDs are now 64-hex values. The same request UUID cannot name different content. Changed previews need review again. The list reads up to 64 indexed pending requests per page. These requests approve changes to access; they do not approve record proposals. Grant receipts describe locally authored signed entries, not completed relay delivery.

Source: App sharing requests

People consent codes

People wraps a locally minted LastDB open token with the database ID, publisher key, and grant receipt. The recipient supplies an independently verified publisher key before accepting it.

The wrapper is unsigned and not encrypted. It carries an open token containing the database content key, so it is sensitive. It is not the old sealed invitation and has no old 24-hour expiry contract. Accepting a new token enables publisher-stream pulling, but does not establish complete received data or readable records.

Source: People consent codes

Recovery and remaining delivery limits

Restore from signed streams

The restore command reads explicitly named owner device streams from sequence 1. It verifies entries locally, materializes winning records into staging, shuts down the stores, and publishes an unused destination.

Restore loads schema definitions from accepted signed entries; it no longer invents v: String schemas. A live record without a declared schema fails. A tombstone for an undeclared namespace is skipped. The record adapter supports hash and hash-range keys, JSON fields, and winner authorship. Alternate addresses, arbitrary metadata, and attachments are not reconstructed. Bundles remain pending. Missing dependencies or rejected entries refuse completion.

Source: Restore from signed streams

History recovery checks

Restore verifies each signed entry and refuses completion if rejection evidence or pending dependencies remain. It publishes staging only after closing the stores.

The caller names the streams. There is no automatic complete-device discovery. The adapter supports a limited hash-record shape and no bundle download or attachment restoration. Earlier snapshot evidence does not qualify this path.

Source: History recovery checks

Recovery identity and connection

Recovery derives the owner signing seed from the phrase and writes it into a private staging home. It creates a fresh device ID. The chosen relay URL is used for reconstruction, not saved into that new home.

Restore checks account context but does not copy connection credentials into the new home. The restored node therefore needs its own connection or relay override for later sync. Saving credentials does not demonstrate complete sync or backup coverage.

Source: Recovery identity and connection

Relay blobs and bundles

The reference relay supports staged blob upload, size and digest verification, and signed download requests. Signed bundle entries can refer to a blob holding many record changes.

The caller must verify and decode bundle bytes. The daemon and restore reader do not connect that step yet. The former encrypted attachment uploader and snapshot-covered object cleanup are gone. Do not infer working attachment backup from the blob API.

Source: Relay blobs and bundles
