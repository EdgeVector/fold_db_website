Source notes and release limits

Source review: 17 November 2026. Merged LastDB revision 4ddf58333b3ed942ab26009d8042912a2eed38ef.

The guide describes 129 parts and 463 connections. This review covers 63 commits after 2e0494f35; completed reviews cover 1381 commits after October 21. Changed code and surrounding callers were examined across the model, memory, disk, flush and ack, deletion, encryption, cloud activation, backup, recovery, and services, including vendored LastStore. Historical operational evidence remains tied to its original source.

Records and keys

A schema owns its records. Canonical field reuse shares definitions, not values. One record carries complete fields and one revision. Primary and named alternate addresses are supplied separately. Replacement supplies the complete new payload; conditional writes protect against overwriting a newer version. Records remain capped at 64 KiB, with large files stored separately.

Ordinary record reads use keys or a range under one hash. The app API can also list a schema’s primary keys with keys_only: true and no key or range. This returns keys, not unfiltered records. Pages default to 100 keys and cap at 1,000. Arbitrary field filters are not available.

App requests and access

The SDK provides read, write, and changes. Reads accept at most 64 items, execute four at a time, and retain request order with per-item errors. A write list commits within one owned database. Creates require absence; replacements and deletes require the read revision. Refusals can name the mutation index and the reason exists, absent, or revision. These /v1 routes do not yet serve received shares.

An installed app with a signed access declaration starts on apps.sock. The launcher obtains an in-memory session naming exact read schemas, write schemas, and extensions. Sessions expire after 24 hours; four may remain live per app, and a new fifth session replaces its oldest. The node caps the total at 1,024. The app socket has four workers, four queued connections, and an 8 MiB body limit.

The declaration needs no separate owner approval. The launcher and install steps do not sandbox programs. Both sockets check the operating-system user, but a same-user program can still use the owner socket. An app session is separate from the one-hour selected-database session used by existing owner routes.

File input names a local regular file outside the LastDB home. The app API does not carry file bytes. A file read can return an existing reference path; the path check detects absence or changed size, not a same-size edit. Reading file bytes performs the separate hash check.

Changed keys and memory

The optional changes extension returns locally stamped record keys and deletions. Entries commit with their records. It retains 250,000 entries and examines at most 500 per page. Save through, even when schema filtering returns no entries. Rebuild the app’s view when id changes or gap is true. This is not record history or the cloud mutation log, and it does not promise to report every remote replay.

The decoded-record warm set defaults to 256 MiB. It includes record keys, metadata, and file markers. Held records can keep it above that target. Schema definitions have a separate cache. File bytes remain outside the warm set. The least recently used unheld records leave first.

Each run home now keeps at most 32 open readers between calls. A reader holds a file handle, cipher, footer, and decoded top block; it retains no data blocks or records. Least recently used readers leave first. Compaction removes retired runs from the pool, while active reads may still hold them. Separately, one read can reuse up to 64 checked lookup blocks, bounded by the smaller of 256 KiB or one-sixteenth of its byte allowance. That block cache ends with the call. These are separate limits, not a total process-memory cap.

Disk, flush, encryption, and deletion

Format 15 remains current. A request privately prepares its changes. The bounded write queue combines requests already waiting, without a collection timer. File additions commit before record changes; removals follow the durable record change. Run completion and CURRENT staging can overlap, but publication waits for both. The disk root and clean memory state publish before the write succeeds.

Run files authenticate encrypted blocks. Content-key derivation and file encryption remain in place. Ordinary reads authenticate a complete block, with a 64 MiB decompressed-output cap. Native snapshot transfer streams files separately. A local file reference leaves the original external file in place; removing the reference does not delete that file.

Deletions remove live records and alternate addresses while retaining the ordering facts needed to reject older replay. Record replacement retires old stored file bytes after the record is durable. Obsolete file-reference metadata bookkeeping and the unused replay-cutoff check are removed. Local deletion does not immediately erase cloud copies. Personal cloud cleanup has its own tracked objects and snapshot coverage; shared uploads remain outside that cleanup path.

Cloud activation and accepted changes

One signed-log worker handles personal, owned named, and registered received databases. Owned uploads require saved account access and a matching live creation response for the database and environment. Local writes finish independently of cloud availability. ExeMem checks eligibility and routes cloud bytes; LastDB decides recovery and retention correctness.

The local accepted-change stream records committed work before upload. Its confirmed upload position and the downloaded cloud position are different sequences. Saved identity bindings and exact retry bytes prevent a retry from silently naming different work. Personal devices reconcile under the same owner key. Whole-database members use the separate proposal inbox.

The first personal snapshot establishes a durable baseline. Explicit native snapshots capture both run homes and their checked file inventory. Covered personal snapshots can queue bounded log cleanup and retryable provider cleanup. A separate ledger tracks confirmed personal file uploads for snapshot-covered deletion. No periodic full-snapshot schedule or general shared-object cleanup is established. The old backup index-log-history command is removed.

Recovery and its limits

Fresh owner restore selects a database and fixes a cloud head. It installs an available native file snapshot, then replays a continuous retained log through that head. It checks access, manifest binding, allowed paths, lengths, hashes, encrypted entries, and required files. The fresh destination is published only after successful shutdown. Without a native base, recovery needs the retained log from its start.

The archived JSON-entry snapshot chain and its install journal are removed. Expired named or received cursors stop; they no longer fall back to that archive. Personal automatic recovery can stage an exact native snapshot and later entries, after first publishing pending local edits. It requires search delivery off and refuses changed source boundaries, external references, unconfirmed writes, or pending deletion. The daemon shuts down before exchanging data directories, retaining the old data in staging.

Native snapshot download requests a service hold where supported. Logical attachment replay still assembles each requested file in memory; response bounds alone are not a total recovery-memory cap. This source review does not establish a new recovery pass or PROD qualification.

Share: proposals and publication

A whole-database share keeps two stored logs under one database ID with independent positions. Active receivers read the whole published database and can submit encrypted proposals, including with an empty write grant. Only the publisher reads and settles pending proposals. Apps display permissions; the publisher’s LastDB enforces them.

The publisher decrypts each proposal and checks current confirmed membership, schema grants, the installed definition, record rules, and the expected record version. A sender’s older roster revision alone no longer causes refusal. A change to another member must not invalidate an otherwise permitted write. Refused proposals are discarded. Accepted changes commit locally and upload under the publisher’s key before settlement.

Proposals support one create, replace, or delete within 96 KiB. HTTP 202 means submitted, not accepted. Stable UUID retry keys bind exact proposals. Standard social/Comment receiver writes must respect verified creator ownership, and receiver deletion is refused. The former 98-member client roster cap is removed; body and service bounds still apply. Private submission status reports submitted, published, discarded, or unknown without proposal content or rejection details.

Social, Medical, and Finance illustrate why separate shared databases are useful. Medical and finance app rules and compliance are not supplied here. Per-reader personal settings that accept or hold published changes remain proposed. Publisher validation is implemented and must not be confused with that proposed feature.

Source: Publisher intake · Settlement order · Current sharing configuration · Roster changes

Social is a separate command-line app

Social now lives in EdgeVector/social. This review reads its implementation at 3c51c60242a37f0c3891c4ff0d1dc639495a22d1. Its browser interface and the Social adapter in the LastDB app SDK are removed. The separate @lastdb/social-client package wraps the installed command.

Use social request list to find proposals, request show to preview access, and request approve --token or request decline to decide. Requests keep stable UUIDs and saved outcomes. Changed previews need review again. Unfinished updates remain separate for each database; changes across databases are not one transaction.

Circles reuse verified people across whole-database shares. Overlapping circles combine grants, outside direct grants need an explicit resolution, and revocation stays until restoration. The shared-albums v1 setup verifies Album, AlbumItem, Photo, and Comment. It reserves a database ID before creation and can explicitly finish missing schemas in an owned collection. Received stores can only be verified. These source findings do not qualify the moved app’s current deployment.

Schemas, installation, and releases

Manifests can declare each field once as a typed object, or use the older list and field maps. Mixing both forms is refused. A restricted app’s activation places its manifest schemas before the app probe runs. Declarations may name schemas from another app’s namespace; identical definitions succeed and incompatible definitions fail.

The schema service accepts signed pushes for already listed app commits. It checks the listing, publisher, commit, and signature. Up to 256 definitions fit within a 1 MiB push. The old scheduled catalog feed and public-manifest fetch are removed. Advice uses pushed definitions and built-in vocabulary. Examples require matching normalized names, compatible supplied types, and compatible descriptions. Vocabulary advice still works when the catalog is unavailable.

App installation searches signed catalogs from API 37 down to the supported minimum, 29, and chooses each app’s highest supported entry. Absent levels are skipped; other retrieval failures stop selection unless a verified cached catalog is available. Separate DEV and PROD profiles supply pinned registry keys. Managed installs retain version folders and rollback; a rollback switches code, not database changes.

CI proves app operations across supported interfaces but no longer signs or republishes app listings. Existing signed entries remain valid. Stable qualification still requires its full one-hour run and normal source, security, exact-source snapshot, provenance, and publication gates. This guide review is not a release, deployment, or primary upgrade.
