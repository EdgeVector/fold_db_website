Source notes and release limits

Source review: 12 November 2026. Merged LastDB revision c6f1cb597ea45a6f2b4721ee6faa9235db9c2547.

The guide describes 116 parts and 386 connections. This review covers ten commits after 5b99448. Completed reviews cover 1197 commits after October 21. The review follows changed implementations and surrounding callers across the model, memory, disk, flush and ack, deletion, encryption, cloud, recovery, and services, including vendored LastStore. The owner byte-backup path is removed. Personal and named databases now use signed logical changes. This is a source review, not a new PROD recovery result or primary upgrade.

One cloud path: the signed database log

The daemon starts one signed-log worker for the personal database, owned named databases, and registered signed receivers. The former owner snapshot scheduler, daily full copies, physical change-backup worker, personal blob uploader, and cloud-release worker are removed. Backup policy, status, list, start, resume, close, and inspect-dependencies commands are removed. The existing backup command group retains connection and fresh-home recovery.

Each owned database needs checked account access and a live signed creation response with the matching database ID, environment, and protocol version. Confirmation is remembered in the process. Private databases need no sharing spec; shareable databases need an admitted binding. The legacy cutover protocol and fallback uploader are removed. Local writes still finish independently of cloud work.

Source: Daemon workers · Database turns · Signed creation · Current commands

Personal capture does not backfill existing data

Owned named stores capture accepted logical changes. Personal capture is selected when the store opens: valid saved cloud credentials turn it on, while missing or unreadable credentials leave it off. Saving credentials later does not change that already-open store’s capture setting.

Fresh-home initialization marks its setup boundary before ordinary writes. An existing home without an accepted log has earlier history and requires snapshot coverage. The publisher refuses a gap or snapshot-required state. The current worker does not create that older-data baseline. A connection or successful local write must not be presented as complete personal backup coverage.

Accepted bodies have a 1 MiB limit. Bodies and copied files share a 1 GiB spool limit; retry files are separate. The publisher reads at most eight entries per turn. It retains exact request bytes and advances local publication progress only after each entry is published or withheld by the sharing policy.

Source: Personal store setup · Fresh initialization · History and coverage · Publication limits

Files travel before the change that names them

Signed sync seals required file bytes with the database key and entry binding. It uploads the object to B2 and saves a verified receipt before appending the encrypted log entry. Stored files and matching local references use this path. The upload input cap is 512 MiB; an external file must remain available and unchanged until upload.

Recovery fetches required objects during replay. It checks the encrypted binding, plaintext size, and hash, then seals the bytes for the local store. The old personal on-demand blob downloader is removed. Signed sync does not release uploaded objects. Retained local upload/release bookkeeping is not an active cloud cleanup worker.

LastDB owns data semantics, retention, and recovery correctness. ExeMem checks eligibility, routes data, and performs cleanup under LastDB’s instructions. This review does not establish deployed cloud cleanup behavior.

Source: Upload and receipt · File replay · Local record/file lifetime · Object transfer

Recovery rebuilds one database in a fresh home

Use lastdb --data-dir /absolute/connection backup restore --database <id> --recovery-phrase-stdin --into /absolute/new-home. The connection home supplies saved account access. The recovery phrase supplies the matching identity. The destination must be an unused absolute path. --stream remains an alias for --database; --latest and cut selection are removed.

Recovery checks owner access and fixes a delivery head. It reads a continuous prefix through that head. If the first cursor has expired, it may install a matching snapshot prefix before continuing. A gap, missing object, conflicting mutation, wrong key, or snapshot beyond the selected head stops recovery.

The CLI builds a private staging home. An owner-key log is replayed into personal; a private named log is registered as recovered. An empty log cannot identify its key from an entry, so it uses the named-store route unless its ID already matches personal. Both stores shut down before the destination is published with a no-replace rename and parent-directory synchronization. A failure cleans up owned staging and leaves the destination unpublished.

The fresh destination keeps its recovery identity but does not receive the connection home’s credentials. backup connect --existing --env dev|prod --api-key-stdin checks and saves an existing credential separately. The older --dev --restored connection action still expects a legacy restore receipt. No operation here changes the user’s primary.

Source: Recovery entry point · Private staging and publication · Owner log selection · Existing account connection

Log snapshots and replay boundaries

Recovery applies required logical snapshots oldest first, then later log entries. Chains allow at most 1,024 snapshots and each encoded part has a 1 MiB cap. Missing links, cycles, identity conflicts, and incomplete prefixes refuse replay. Durable attempt and completion markers support interrupted replay.

Replay resolves the selected database and its content key. Private databases permit unqualified schema names; shared entries require a namespace. Capture is suppressed only for the target store, so recovered changes do not become new outgoing entries. Delivery acknowledgement follows durable replay and flush.

Normal owned-store sync acknowledges only entries from its own writer and device; it holds other writers and devices. Registered receivers replay publisher entries into their separate stores. This is not general multi-device application of changes or app-controlled local approval.

Share: examples, permissions, and local choices

The Share area groups content selection, participants, change delivery, and local views. The intended model lets authorized participants write to a mutation log while each app accepts incoming changes according to its owner’s settings. That local approval step remains proposed. Ordinary received-store writes remain refused; Submit membership alone does not enable the missing submission and approval path.

Social v1 and lastdb-files v1 are admitted sharing specs. Medical, Finance, and Work are examples of possible apps and future settings, not implemented approval controls or compliance claims. Names such as graph, social, medical, finance, and work are now ordinary labels. A spec binding, rather than the name, controls sharing admission. Names use 1–64 ASCII letters, digits, underscores, or hyphens; personal and UUID-shaped names remain unavailable for creation.

Membership authorizes cloud access. Specs limit exportable content. These are separate from deciding whether to accept each incoming change locally. Invitations deliver one database’s content key and signed permission. Read or Submit membership is versioned; the client allows 98 rows including revoked rows. Invitations expire after 1–168 hours, default 24, while membership does not expire with the invitation. Revocation cannot erase an existing local copy.

Source: Names and creation · Supported specs · Membership · Invitations · Implemented acceptance

Selected publication and Files

Saved keyed queries copy eligible fields and files into a different ready, owned, shareable database with the matching spec. Limits remain 32 reads, 8 one-hop links, 256 selected records, and 256 queries per source. Definitions and ledgers each have a 24,000-byte cap. Truncated reads are refused. Conditional destination writes precede ledger advancement; this is not a cross-database transaction and it does not construct alternate addresses.

Files imports require an owned database bound to lastdb-files v1. Each file becomes 32 KiB chunks and a catalog entry. A new file becomes visible after its final durable chunk. The catalog allows 128 files, 256 MiB of bytes, and 32 KiB of text. Saving fetches at most 16 chunks per batch, checks the total size and hash, and refuses an existing output. Signed sync carries the destination’s accepted changes after activation.

Source: Reconciliation · Conditional copies · Files import

Retained legacy readers are separate

Existing legacy publication registrations retain native snapshot and change-chain readers for their verified cache slots. The owner byte-backup producer and the legacy contribution-application loop are removed. Retained capture, planning, grant, and outbox helpers do not establish a running owner uploader or contributor acceptance service.

The native legacy reader supports format 15/profile 14 and validates captured roots, exact files, and required key proofs. It does not audit every logical record or create a runnable owner home. New signed invitations use database replay instead. Old dedicated shared homes and portable-journal layouts remain refused without an automatic migration.

Source: Legacy snapshot reader · Existing cache registrations · Retained native helpers · Storage admission

Records, memory, and keyed reads

A schema owns complete records with independent primary and alternate addresses. Canonical field reuse shares definitions, not values. Replacement supplies the complete new payload against one revision. Omitted fields and metadata disappear. The encoded record cap remains 64 KiB; files have separate storage and limits.

The warm set retains decoded records, their keys, metadata, and file markers. Its default target remains 256 MiB; active holds may keep it above the target. Schema definitions have a separate cache. Prepared native writes retain a 512 MiB allowance. These are not a process-wide memory cap.

Ordinary queries use exact keys, batches of keys, or ranges under one known hash. Scans and arbitrary field filters do not exist. Ascending keyed cursors remain; descending keyed reads use offsets. Owner key listing and internal maintenance are separate from app queries.

Source: Whole records · Warm set · Memory bounds · Keyed reads

Disk, flush, and acknowledgement

A request privately prepares its complete change. A bounded queue combines requests already waiting without a collection timer. File additions commit before record changes; file removals follow them. When logical capture is enabled, accepted entries are saved before memory publication and acknowledgement. A missing entry or full spool refuses progress.

LastStore can finish the new run and stage CURRENT in parallel. It publishes only when both succeed, then synchronizes the directory before making the new root current. The queue publishes matching memory state, releases writer ownership, and notifies waiters. The two homes do not share one atomic file-list update; saved deletion recovery handles interrupted file removal.

This interval consolidates the native pack and LastStore read/range implementations. Captured roots, batch lookup ordering, bounded authenticated reads, and pending-request overlays remain. Metadata reuse is scoped to the read operation. Compaction retains the existing thresholds and retires replaced files only after their last reader releases them. Space reservations account for both the native root and its filesystem. Poisoned locks refuse further unsafe publication.

Source: Private preparation · Queue and completion · Commit ordering · Run and CURRENT prerequisites · Unified reads · Bounded range reads · Compaction · Space reservations

Format, encryption, and deletion

The storage refactor does not change the format: new homes use format 15, native snapshot profile 14, and run frame version 2. Lookup-key protection derives from the home key and key-space identity. Stored files have content encryption plus encrypted local run blocks. Local external references leave their original bytes outside that protection.

Run blocks use authenticated encryption and optional compression. Compression is retained only when it saves at least 64 bytes and 10%, including its length header; small inputs below 256 bytes are skipped. Bounded snapshot reads authenticate a complete block before exposing decoded bytes. File identity checks and decoding limits remain.

Record deletion removes the current record, alternate entries, metadata, and owned files while retaining a deletion stamp. Checked purge forgets that stamp. Expiry belongs to a schema and uses conditional deletion. The periodic expiry worker still visits the main database, not every owned sibling. Compaction and local cleanup do not establish deletion of earlier cloud objects.

Source: Format constants · File protection · Run encryption · Authenticated streaming · Record deletion · Expiry worker

Cloud merge time is bounded by acceptance

The cloud mutation log orders entries by the earlier of author time and acceptance time, then writer and sequence. A future author clock cannot keep its entry ahead indefinitely. Delivery sequence is separate from this merge order. The original author time remains unchanged in the encrypted entry binding.

Local record revisions still guard complete conditional writes. This ordering change does not enable ordinary received-store writes or apply another owner device’s entries during normal sync.

Source: Ordering time · Cloud head decoding · Apply boundary

Services and recovery evidence

The node status route retains build, uptime, socket-worker, and search-queue details. Owner backup activity summaries are removed. Sanitized Lambda error events now include bounded service and function-version tags. Dependency update exclusions do not change runtime behavior.

The daily recovery workflow now calls the signed private-database DEV operation. Its recipe creates isolated data, writes a schema and record through LastDB, checks a snapshot prefix, restores into a fresh home, and reads the record by key. It also checks refusal for an unrelated key and another account generation. The manual recovery workflow is DEV signed-files only; PR mode performs syntax validation.

The former owner byte-backup PROD workflow is deleted. Historical format 14 PROD recovery results do not qualify the new signed path. This review establishes no new PROD pass, stable release, deployment of LastDB services, or primary upgrade. The website’s build and publication have their own required checks.
