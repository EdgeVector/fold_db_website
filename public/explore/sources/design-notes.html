Source notes and release limits

Source review: 8 November 2026. Merged LastDB revision 32ba40cfd.

API 31: guest snapshot staging and exact-key reads; retired native-index route removed. API 29 requests remain supported. The guide describes 143 parts and 539 connections. This publication includes 24 commits after cad4d4b2. Completed reviews cover 1073 commits after October 21.

API 31 and removed compatibility paths

API 31 removes the retired GET /api/native-index/search route. App search and scoped vector routes remain separate. API 29 requests remain supported, but app catalog selection still requires the exact API version. Obsolete alternate-key capability booleans are removed; the current owned-schema, atomic-mutation, compound-key, and independent-key capabilities remain.

An unused local snapshot intent file no longer blocks cloud backup requests. Removing an unused 8 MiB file-coverage reserve lowers the calculated proof and upload memory estimates; it does not establish a measured memory saving or change the 256 MiB warm-set limit. Schema reuse thresholds and native component coverage are now fixed behavior instead of redundant enable switches. Renamed schema resolution helpers preserve their cache and disk-read distinction.

Other removals affect unused manifest fields, an unused registration session token, old benchmark adapters, crash callbacks, and diagnostic ledger fields. A removed boot-log field was a hardcoded false value, not a cloud-backup policy change. The review changes no local flush/ack, deletion, disk format, cloud activation, or owner-restore release rule. Vendored LastStore is unchanged across these 24 commits.

Local file references: usable locally, incomplete personal backup

The owner can attach an existing regular file outside the node home with file: {"source":"coast.jpg","local":true} in a complete mutate request. The CLI resolves the source relative to the request file. Inline placement is refused. The record stores the usual name, size, and hash marker. A separate local-file-refs.json catalog stores the path after the record commits. Neither the path nor the external file is included in the record snapshot.

Registration hashes the file in 64 KiB chunks without a file-size cap. Fetching or sealing it currently loads the complete file and refuses more than 512 MiB. Reads check size and hash and fail if the original changes or disappears. That error does not fall through to a cloud download. Removing or replacing the reference forgets its catalog entry after commit; it never deletes the original. LastDB does not encrypt the original file in place. A catalog-write failure can be reported after the record has committed.

Do not treat a local reference as a recoverable personal cloud attachment. The new snapshot wrapper temporarily seals referenced bytes into the blob home, then removes those rows after preparing capture. Personal capture holds only the record home. The later personal uploader reads stored blob rows and has no local-catalog fallback; removing the temporary rows also removes their pending-upload markers and queues a release. Change backups likewise do not read this catalog. These connected source paths show a gap, even though comments describe backup support. This review did not run a runtime recovery operation for local references.

A successful personal restore validates the record marker’s path, not the availability of every blob. It does not restore local paths. Shared recovery still requires its captured blob entries; the portable file encoder can read and seal an existing local reference, but this review establishes no shared recovery result for that option.

Smaller storage and service changes

New run-home creation now sets the empty runs subdirectory to owner-only permissions (0700), so restore admission does not reject a directory created under a permissive default mask. Existing directories are unchanged. Native namespaces map directly to one collection; the main namespace still uses records. The unused storage-engine selector, per-key crypto selector, legacy import-stamp path, and compatibility helpers were removed without adding a storage mode or changing the record format.

Ed25519 key loading now requires a 32-byte seed; the unused 64-byte compatibility form is refused. Request telemetry no longer accepts X-App-Id as a client-label fallback or advertises an unrecorded cas_precondition phase. Revision conditions still execute. The health alert command always checks degradation after a healthy liveness result; its default slow-request threshold remains five seconds. Blob downloads: device sign-in and file lifetime

An explicit fetch-blob request uses local bytes first. In an ordinary home, a missing version can now be requested from the cloud by database, schema, record key, and immutable file version. Startup and owner connection register this source when saved account credentials are available. A personal home without saved credentials instead returns HTTP 503 with the exact message “sign in to fetch this file”, without calling the cloud. This does not turn on automatic backup. Dedicated shared homes do not use it.

The client requests a B2 download grant for that exact path. Core checks the encryption framing, plaintext size, and hash before returning the file. It saves the downloaded row only if the record still selects the same marker and version. If the record changed during the download, the caller can receive the verified selected bytes without installing them over newer state. The record revision does not change. A missing cloud object returns a missing-file error; unavailable account access or service returns a retryable error.

Personal snapshots now capture the main record home only. Each record blob version uploads separately to its derived B2 path, outside the snapshot inventory. New file commits queue pending uploads; snapshots also queue local versions without an uploaded marker. The worker uploads them before publishing the job, then records acceptance locally. Frozen transfer inputs and receipts survive restart. Requests contain at most 64 paths; the saved plan has no fixed page-count limit.

Record-file deletion queues a release only after the main record change is durable. A job plans releases before capture and sends them before publication. Local release markers clear after acceptance. These releases do not promise that an older recovery point can still download every attachment.

Personal restore creates an empty blob home and validates record file paths instead of downloading their bytes. Inline attachments remain in the main home and are checked during restore. Explicit blob reads need account credentials, verify decrypted size and hash, and save bytes only while the record still selects that version. Shared snapshots and recovery retain their existing eager blob-home path.

The updated personal recovery path passed in DEV. The accepted-main run at 4132e14a completed automatic snapshots, logs, restart, and recovery into fresh homes. Each recovered device signs in using its own device identity with automatic backup off. The procedure checks the exact sign-in message before one file fetch, then verifies current file bytes after sign-in and across two clean boots.

The earlier base-recovery HTTP 404 at 0a148108 is now treated explicitly: a later write replaced and released the old file version. Recovering the earlier record preserves its marker, but fetching that released version must return HTTP 404. The new DEV pass checks this absence; it does not establish file history. The successful PROD run at ebd09268 predates separate blob paths and does not qualify this layout.

Guest permission, snapshot staging, and exact-key reads

The explicit command lastdb admin shared stage-guest now connects the private staging engine. It takes a publisher-signed stream permission, a trusted publisher public key, and a publication-specific content key through noninteractive standard input. The bundle is limited to 4 KiB. No account API key or owner recovery seed is required for this guest path.

The signed permission names one stream, DEV or PROD environment, read operation, and expiry. The client checks its signature and the trusted publisher, then uses the fixed HTTPS endpoint for that environment. This is a bearer permission for the stream’s encrypted snapshot, not a record-level restriction. The content key is separate. The cloud service must enforce expiry; a returned object grant may not outlive the permission.

New staging selects the current accepted independent snapshot. It refuses an active publication or a snapshot with recovery dependencies. Resume keeps the exact saved selection and rechecks it with the service; a changed stream head requires a new stage. The command refuses the primary and accepts no --data-dir. An absent absolute --into path determines where to create the adjacent private workspace; it does not become a runnable destination.

Staging verifies the encrypted inventory, exact files, counts, bytes, schemas, keys, records, and inline files. It installs no identity, account credentials, or restore receipt. Its JSON receipt returns the workspace, verified data path, commit ID, and commit hash. The account-authenticated recipient form still binds an exact grant to one accepted job and digest, but has no user command. Invitation delivery remains unconnected. This source review does not verify guest service deployment or a successful guest operation.

Add --schema PhotoById --key-hash photo-42 --json to read a known record after the whole snapshot is staged. A hash-and-range schema also needs --key-range. The reply contains its stored fields and primary key. --inline adds verified inline bytes as base64 with their marker. A missing record returns null; invalid stored state fails. This command has no alternate-key or range lookup and does not fetch blobs.

The exact read checks the schema’s primary key definition, opens its frozen lookup-key bundle, validates stored key coordinates, and reads the live record under the verified stage guard. Its five-key budget covers one schema, up to two bundle reads, one record, and one inline entry. Read work is bounded at 128 MiB, with separate schema, bundle, record, and inline size limits. It does not start a daemon or write to the staged snapshot.

Inline files and clean snapshot captures

Queries return the complete stored record and file markers, never attachment bytes. An owner file request chooses placement: "inline" for a small file; blob is the default. A blob upload can include a thumbnail in the same mutation. lastdb get --hydrate-inline PATH fetches the queried revision’s inline bytes, checks size and hash, and refuses an existing output path. Inline rows use run-block encryption and stay outside the warm set. Shared replacement logs include their bytes. Record deletion clears the inline row; deleting only the inline file preserves the blob.

New running snapshot captures first compact hidden versions in both record and blob homes. Cleanup ignores ordinary merge thresholds and rechecks under the write gate before retaining the cut. It allows 64 rounds and checks a 15-second budget between rounds. An unfinished cleanup defers capture; it does not publish a dirty cut. Existing captures keep their exact files. Base compaction reuses unaffected key ranges. Older held files and cloud backups have separate lifetimes.

Automatic Backup V2 distinguishes an expired source lease from an uncertain result. It verifies the exact terminal job result before releasing that source and scheduling a fresh snapshot. A temporary admission fence retries only within the same scope. Owner cancellation stays stopped. A shared snapshot abandons and thaws a capture only after a confirmed staging-expired refusal; other transport failures preserve retry state.

A separate manual DEV fresh-account workflow creates a new identity, records its lease, publishes a first snapshot, stops its generated source, and restores that exact snapshot into a fresh home. Its recipe checks keyed records, blob bytes, and two clean boots. A separate interrupted mode leaves cleanup to the owned-account process. This is implemented coverage, not a claim of a successful run or PROD qualification.

App publishing and installation

Normal app installs read the stable or next channel’s public catalog for the node’s exact API version. Each catalog has a registry signature; each entry also has a publisher signature over the app version, Git commit, and interface declaration. A declared search-notice version must match exactly. The node build label is recorded but does not choose the entry.

The installer checks out the full listed Git commit and records it in an install receipt. This path does not use the old version-range preference or require a separate verifier result. Signatures establish who signed which bytes. They do not establish that an app works or limit its user permissions.

Publishing starts from a clean Git checkout and requires an explicit HTTPS registry address and developer account key. The CLI reads its developer signing key from a file and rejects LastSecrets locators. Its embedded LastSecrets key handling has been removed; external credential handling is separate. The publish command records interface versions; it does not itself run a compatibility check.

The CLI keeps verified catalogs outside the database. A failed download can use a valid saved catalog. Lower sequence numbers, or different bytes with the same sequence, cannot replace it. At seven days old, a catalog produces a notice but remains usable. Installation still needs to fetch the app’s source commit.

Normal managed installs now prepare a separate version from the signed catalog, read its install instructions, and switch stable command links after checks. First installation and changed instructions require consent. Brain, LastSecrets, and Search can switch between explicitly trusted owner and CI publisher keys at the expected PROD catalog and GitHub source. Both old and new installs must have pinned trust. Other publisher changes require owner rotation. Inactive installs still prepare code and links but skip health and post-install commands.

On macOS, a managed install installs a minute-by-minute updater. Stable catalog checks are normally hourly while health checks continue; next is checked each poll. Other hosts can invoke the upgrade command. An alternate app root does not install the background updater.

Each app is handled separately. A catalog, receipt, or activation failure is reported for that app while the pass continues with the others. Catalog results, including failures, are reused for apps with the same saved catalog and channel during that pass. A failed app makes the command finish with an error. A failed catalog fetch does not advance its hourly timestamp, so the next poll can retry.

An old install whose saved catalog is a LastSecrets locator stays installed. Background polling reports it as blocked without fetching a secret or choosing a different catalog. An explicit upgrade also rejects that saved locator unless the owner supplies a supported catalog address.

A rollback requires an eligible, healthy previous version. A rejected source commit stays held across automatic polls until a newer commit or explicit install consent. Rollback switches code and links, not database writes or arbitrary install-command effects. Status reports health without triggering rollback.

All app install and upgrade commands now use managed version folders. The separate local development installer, --from/--rev/--dev options, unmanaged install-directory override, and force replacement are removed. The older HostTrack, verifier-log, and schema-service catalog installers remain removed. Use lastdb app list APP for catalog lookup and installed command links to run apps.

Apps declare typed schemas locally

The node builds and loads a direct app declaration without finding or registering it at the schema service. Every field must name a type. Shared writer logs now carry their own typed definitions; shared replay and recovery no longer fetch schema-service pins.

The File and SchemaRef field types, shared-file pointer, and ref_fields schema property are removed. Files belong to records. Ordinary fields still need types; Any remains temporarily in this source revision.

Existing keys and field meanings remain protected. A declaration does not convert existing record values. Shared field definitions still do not share values between schemas.

One schema owns its records

A schema names fields, a primary key, and optional named alternate keys. Each schema owns its record values.

Canonical field reuse shares meaning and type. It does not connect records in different schemas.

A shared record also keeps its accepted definition ID. One stored record holds its primary key, named alternate addresses, fields, one record stamp, metadata, and optional blob and inline file markers. Deletion removes the live value and saves its stamp in a separate applied-delete entry. A blob marker also has an immutable version identified by a writer stream and sequence. The encoded record must fit within 64 KiB, including addresses and both file markers. Empty fields do not make a live record absent.

Each record can own one blob file and one inline file. Both markers describe name, media type, size, and plaintext hash. Locally available blob bytes live in disk-cas; a personal restore starts it empty. Inline bytes have a separate fi row beside the record in disk-run, with a 64 KiB plaintext cap independent of the record cap. A plain replacement preserves both attachments. Identical files on different records occupy separate entries.

Schema advice and app publishing

POST /v1/advice/schema is read-only. It compares a draft with the service’s canonical vocabulary and loaded schemas. It can report names, different meanings, missing types, classifications, and similar schemas. Similarity is a suggestion, not proof that two definitions are interchangeable.

App check and publish print optional advice on stderr. A request waits at most five seconds. A network failure skips the remaining schemas; an unusable reply skips that schema. Advice failure never blocks either command.

Publishing has separate mandatory checks before signing: the manifest must explicitly list its schemas and type each field. The command reads the running node and checks that every app-owned schema appears with the same identity. An empty list is allowed for an app with no owned schemas. This verifies the currently declared schema set, not arbitrary future app behavior.

The embedding runtime comes from a Lambda layer

The Lambda embedding build loads ONNX Runtime from a shared library supplied alongside its model files. It no longer links that runtime into the main function package. This reduces the function package’s size.

ORT_DYLIB_PATH must name an existing runtime library. Model files come from SCHEMA_FASTEMBED_MODEL_DIR, FASTEMBED_CACHE_DIR, or the default /opt/fastembed_cache location. This path does not download the runtime or model during a request. Missing runtime configuration causes embedding initialization to fail; checking that the file exists does not establish that the library is compatible.

The embedding model remains all-MiniLM-L6-v2. Unused built-in model choices are removed from the vendored library. The service already selected this model, so its similarity model is unchanged. Live layer contents and service deployment are outside this source review.

One storage format writer for a home

At startup, one component connects records, schemas, clocks, change notices, and lookup keys to the same home and key context. Ordinary database components receive readers and specific write operations. They no longer hold raw storage writers or open arbitrary storage areas. Physical disk storage and authenticated backup replay keep their own entry points.

Reads and writes check the version-3 record structure: independently stored addresses, one record stamp, and a consistent file marker and version. Deleted values cannot be encoded as live records. Each complete encoded record must fit within 64 KiB. The API rejects repeated primary keys in one mutation batch.

The file writer keeps each encrypted payload and marker together. A plain replacement preserves the existing attachment without reading or rewriting its bytes. A mutate request can instead supply a file source or explicit file: null. The writer checks origin, marker, size, envelope, and nonce. Portable replay and reads also verify the encryption tag, plaintext size, and hash.

The alternate-entry writer binds each saved location to an explicit alternate address and primary target. Its key includes a digest of the primary address. Several records can share one alternate address without replacing each other’s pointers. Both key spaces keep their own range rules. Reads validate membership against stored addresses; continuation carries a primary-record tie-breaker.

Existing generated-home operations now supply complete conditional records. The file recovery operation performs sequential replacements, carrying the exact marker forward. A lost write reply requires a fresh read; the write path no longer looks up a retry receipt. The current format-14 PROD result is described in the backup section below.

The lookup-key writer creates encrypted bundles and their range rules. New key identities are limited to 1,024 bytes, saved metadata and wrap entries to 16 KiB, and the nested bundle and its encrypted form to 4 KiB each. Each primary key space and named alternate key has one bundle with a single hash-protection key. Payload fields have none. Older bundles can still be read; their unused content and range keys are ignored. Stored records and ranges remain protected by run-block encryption.

Restore validates the primary and alternate bundles against their declared range rules, grouped into batches of at most 128 keys. It requires no payload-field bundles. The new comparison identity also invalidates older page cursors: restart those reads from their first page.

Retention sharing follows explicit alias links and earlier schema versions. Reusing a canonical field definition alone does not connect two schemas for expiry.

Schema release, record-file deletion, erase audits, and the replay cutoff use format-owned writers. Field history and all its policy, queue, read, restore, and purge paths are removed. These boundaries do not audit every key at startup. The 256 MiB warm limit and save-before-ack rule remain.

Only format 14 homes

Every new home uses format 14. This release opens and restores only that format.

Each new run-home folder starts with owner-only permissions (0700). Creation does not repair permissions on an existing home.

Older homes, including formats 12 and 13, need their matching program. The current program has no older-home reader or in-place conversion.

Shared sync and recovery in DEV

An enrolled shared database has explicit DEV commands under lastdb admin shared. The writer commands use a stopped non-primary home and saved DEV connection. They install exact schemas, bind a writer, send changes, receive peer changes, and recover a returning writer. Publication uses the running node’s snapshot path. Once bound, the owner can enable automatic upload, peer replay, and publisher snapshots. Member enrollment remains separate.

A bound shared write saves the complete outgoing mutation with its record, file changes, alternate entries, and writer position. Push freezes the exact next batch before transfer. It uploads and verifies all named file versions and the encrypted log before append. Only an exact accepted receipt advances the local upload position. Uncertain acceptance leaves the saved batch available for reconciliation. Retry first repeats its exact append request. An accepted receipt finishes the batch without reupload; only a missing-dependency reply leads to uploading its objects again.

Manual pull or automatic DEV sync verifies retained peer ranges and saves them in a durable inbox. Missing prefixes wait; overlapping or substituted ranges are rejected. Winning records, exact files, alternate entries, applied progress, and removal of completed inbox ranges commit together. A peer behind the retained cloud prefix needs a newer checkpoint. Pull considers every registered peer, starting after the last applied peer. That choice is saved with the applied range, so rotation survives restart.

The dedicated shared layout separates data before snapshot creation. disk-run holds shared records, inline rows, and verified schema definitions; disk-cas holds their blob files. disk-private holds device-only records and files, local author state, outgoing work, inbox state, and bookkeeping. Creation declares 1–64 aliases. Verified peer definitions can add unused canonical schema names to a running shared home. They cannot take over an existing private schema.

A short write barrier captures accepted writer positions and durable file holds together. The publisher hashes the held original files and uploads them unchanged: record data and file lists to R2, record-file data to B2, and the encrypted manifest to R2. No filtered export is built. Publication saves its exact intent. Retry reopens the same hold; submitted work reconciles its receipt before release.

lastdb admin shared restore connects the owner transport and native staged writer. It requires a saved connection, recovery phrase, and a registered device’s separate signing key. The command accepts an explicit DEV or PROD environment, but the verified shared recovery result is DEV only. It checks the selected snapshot and every captured tail, exact schemas, file bytes, and native closure before activating an unused destination. It saves a fresh local stream and does not copy device credentials. Completed activation can resume from its saved workspace.

The inbox allows at most four ranges per peer and applies one complete range at a time. Shared restore also consumes one verified range at a time. It applies whole-record winners before advancing that range’s progress and discards its candidate and file map before the next range. Native writes hold at most 128 records and a bounded file-byte budget. A file must fit the native file-input limit; one large file can use a batch of its own. The former all-tail candidate spool is removed. Shared binding admits 1–64 exact schemas. Protocol views permit at most 1,024 writers. These bounds do not promise end-to-end recovery capacity.

Bound shared schemas refuse existing expiry policies and uncoordinated schema removal. Local file versions remain only while a live record or pending outgoing mutation needs them.

Automatic sync after owner enablement

The DEV daemon can now send local changes, receive peer changes, and publish shared snapshots. Binding saves a private, home-bound configuration with sync disabled. The owner then enables lastdb backup policy on for that shared home. The default change interval is 60 seconds; publisher snapshots default to one day. The saved policy survives restart. Sync accepts 1 second through 7 days; snapshots accept 60 seconds through 7 days.

Upload and download run concurrently. Each direction has a 30-second deadline and processes at most 32 batches or ranges per pass. Upload failure does not prevent download. A failure saves a reason and retries after five seconds. Missing retained history reports that recovery is needed; it never silently rejoins the writer.

Only the publisher schedules full snapshots. Their schedule is independent of the change interval. The worker saves the pending snapshot identity before capture and uses a 90-second operation budget. Interrupted work resumes that snapshot. A terminal abandonment is recorded, its local workspace is cleaned on the next attempt, and a fresh snapshot begins. This does not delete remote objects.

The shared policy and signer are saved in owner-only shared-cloud-sync.json through atomic file replacement. The configuration checks the canonical home, account, device, writer stream, and exact DEV endpoint. Status reports upload and replay progress, the last snapshot, blocked reasons, and any need for manual recovery. These are shared-sync facts, not the ordinary V2 position-coverage comparison.

A returning writer keeps its private data

lastdb admin shared writer … rejoin is an explicit DEV operation for a stopped, already bound, non-primary home. It first pushes pending mutations and their files. The batch limit is 1–32, with 32 as the default. Recovery refuses to continue if any outgoing work remains or if the captured cloud head differs from the exact confirmed upload position.

Rejoin restores the selected snapshot and captured tails into a fresh staging directory. It keeps the existing device’s private records and files, checks the exact schema bindings, and retains the writer’s identity and next sequence. Stale inbox and file-reference bookkeeping is cleared for reconstruction. This differs from fresh recovery, which creates a new local stream and private state.

An unfinished shared snapshot hold blocks rejoin. Activation closes the old runtime while retaining its owner lock, validates the replacement, then atomically exchanges the data directories on the same filesystem. The previous data remains at a reported path. Run-home opens now check that the locked file still matches the path’s inode; this also covers read-only opens. A saved pending automatic snapshot also blocks rejoin. Rejoin remains manual. The lifecycle job at 97d2c254 verified private records and files, retained previous data, and a later write on the same stream.

lastdb admin shared snapshot sends pending changes, holds and publishes the original encrypted shared files, then sends changes through a saved target. Writes continue during upload. Its receipt reports the snapshot, uploaded position, and R2/B2 file counts.

Completed local logs and obsolete file versions are released

A matching cloud receipt advances the uploaded head and removes completed local mutations through the lesser of uploaded and applied progress. In the same native commit it clears their pending file references. Each exact file version tracks live-record use and its last pending local sequence. Only a version with neither use is removed. A peer replacement cannot discard bytes that an older local mutation still needs to upload.

New homes start with this reference tracking ready. Older homes wait for local uploads to catch up, then rebuild it in saved phases over logs, records, and files. Idle manual or automatic DEV upload and peer steps advance at most 64 steps per invocation, checking a two-second budget between steps. Work resumes from its saved phase. Physical run files still follow compaction and hold rules; cloud objects have their own lifetime.

Object reservation and completion retry the same request on RetryLater or OutcomeUnknown, with six bounded delays from 25 to 800 milliseconds and the operation deadline. The provider byte upload stays outside this retry loop.
